## FEAT-061：并发保存的回归测试；组件侧 dispose 竞态审查

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-08-30 |
| 需求描述 | 把 BUG-161 的排查补完另一半（组件侧），并为并发写同一文件加回归测试 |

### 一、组件侧的 dispose 竞态：干净

BUG-161 扫的是 `StateNotifier` 那一半。这轮扫另一半——`State` / `ConsumerState`
的异步方法里，`await` 之后调 `setState` 或用 `context` 却不检查 `mounted`。

**结论：0 处。** 项目里组件侧都已正确检查。

扫描器第一版报了 `editor_tab_bar.saveTab` 一处，查证后是**假阳性**：
它是 `static` 方法，**根本没有 `mounted` 可查**，而且它取 context 是通过
`navigatorKey`、在 `await` 之前完成的。收紧扫描器（排除 static、只看 await
之后的行）后归零。

### 二、并发保存：也是干净的，但值得固化

自动保存跑在定时器上、Ctrl+S 是击键，两次写入可能同时在飞。实测并发写同一文件
10 次：**0 次失败、最终内容是完整的某一次写入（没有被撕裂）、无残留临时文件**。

原因是临时文件名带了**进程号与递增序号**（`$target.${pid}_${_saveCounter++}.mtsave`），
两次同时进行的保存不会用同一个临时文件——这一点是被想到过的，代码注释里也写了。

但"想到过"和"以后不会被改坏"是两回事，所以加了回归测试。
**验证它能失败**：把临时文件名改成固定的 `$target.mtsave`，测试立刻变红。

## FEAT-062：markdown 分隔符出现在内容里的回归测试

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-08-30 |
| 需求描述 | 用"内容里含分隔符"这个视角审查 markdown 解析器，并把结论固化 |

### 为什么查这个

这个视角刚在图表代码里连中两次：BUG-162（节点标签里的箭头让节点消失）、
BUG-163（甘特任务名里的冒号被截断）。markdown 的分隔符更密集，值得同样过一遍。

### 结论：干净

12 种情形逐一检查——表格转义竖线、链接地址含括号、链接标题含引号、
双反引号包住反引号、强调内含星号、图片 alt 含方括号、脚注、
front matter 内容含 `---`、四反引号围栏包住三反引号、标题内含 `#`——
**全部正确**。

### 两处"看起来不对"的，查证后是对的

表格单元格里 `` `a|b` `` 被拆成两格、`[t](http://x.com/a|b)` 也被拆成两格。
直觉上像 bug，但 **GFM 规定表格里的 `|` 即使在行内代码或链接内部也是单元格分隔符，
必须写成 `\|`**。

**用 marked 逐条比对，输出与本项目逐字一致**，包括那个拆开的 `` `a `` / `` b` ``。
所以本项目是对的，**没有去"修"它**。

### 这批测试不是空跑

第一次破坏（在 `parseInline` 里去掉转义处理）测试仍全过——
**是我打错了位置**，表格单元格的转义在 `_parseCells` 里。
打到正确位置后立刻报警，还原后恢复。

## FEAT-064：Word 导出的嵌套格式，打开文件核对真实内容

**日期**：2026-08-30　**优先级**：P2　**难易度**：低　**状态**：已完成

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-08-30 |
| 需求描述 | BUG-166/167 给 Word 导出写了"把外层强调折进每个子 run"的逻辑，但没有测试 |
| 用户场景 | Word 的 run 不能嵌套，折叠逻辑写错的话，导出的会是几个加粗字而不是链接——而现有导出测试只断言文件以 `PK` 开头，那对"格式全丢的文档"同样成立 |
| 实现方案 | 把 `.docx` 当 zip 解开，读出 `word/document.xml`，找到写着指定文字的 `<w:r>`，断言它的属性。为此把 `archive` 从传递依赖提为 dev 依赖（版本与 lock 一致） |
| 涉及文件 | `code/pubspec.yaml`（dev 依赖）、`code/test/services/docx_nesting_test.dart`（新增，4 条） |
| 验收标准 | 加粗里的链接：run 带 `<w:b/>`，且被 `<w:hyperlink>` 包着；加粗的链接文字：同上；斜体套在加粗里：run 同时带 `<w:b/>` 和 `<w:i/>`。去掉折叠那一步后，三条针对性测试确认全部失败；第四条"普通加粗不变"是护栏，两边都过 |

写测试时踩了自己一个坑：用 `String.fromCharCodes` 读 XML，中文全成乱码，
四条测试都"找不到那段文字"。换成 `utf8.decode` 才对。
顺带确认了实现本身没问题——报错里打印的 XML 显示 `<w:b/>`、`<w:hyperlink>`、
颜色与下划线都在。
