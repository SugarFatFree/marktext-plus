## BUG-157：命令行/文件管理器打开的文档没有保存冲突保护

**优先级**：P2　**状态**：已修复　**日期**：2026-08-30

### 现象

双击一个 `.md`（或从命令行传参）打开的文档，**BUG-146 加的保存冲突检测对它完全不生效**：
外部程序改写了这个文件，自动保存仍会直接覆盖，且不会有任何提示。
从菜单、侧边栏、最近文件打开的同一个文件则受保护。

### 根因分析

BUG-149 修复时，我把"磁盘戳跟着内容一起产生"落实到了各个构造点——
**但漏了 `openFilesFromSecondInstance` 这一处**。它是 Windows 单实例回调、
平台通道的 `openFiles`、以及启动时 `drainPendingFiles` 三条路径的共同终点，
也就是所有"从外部打开文件"的入口。

它当场读完内容就构造 `TabInfo`，却没有传 `diskStamp`。
按 BUG-149 定下的语义，没有戳＝没有基准＝不判冲突，所以保护静默失效了——
**而这个标签页看上去和别的完全一样**。

### 排查方式

不是碰巧看到的。逐个列出所有 `TabInfo(` 构造点并检查是否带戳：九处里五处"缺戳"，
但其中四处是 `copyWith` 或"加载中占位"（内容随后由 `loadTabContent` 连戳一起填），
**只有第二实例这一处是真漏**。

### 修复方案

补上 `diskStamp: opened.stamp`，并新增一条**结构守卫测试**：扫描五个文件里所有
把真实内容交给构造器的 `TabInfo(`，若没有 `diskStamp` 就失败。
"先建空壳、稍后填内容"的用法被排除在外，因为那条路径上戳是跟着内容走的。

验证过它能失败：把刚补的那行去掉，测试精确点名 `tab_provider.dart:772`。

### 涉及文件

- `code/lib/providers/tab_provider.dart`
- `code/test/services/save_conflict_test.dart`（+1 条，共 15 条）

## BUG-158：关闭标签页时选择"保存"，会静默覆盖外部改动

**优先级**：P1　**状态**：已修复　**日期**：2026-08-30

### 现象

同一个文档，**按 Ctrl+S 会被拦下并询问，关闭标签页时点"保存"却直接覆盖**——
别的程序在此期间对该文件的改动无声消失。

三个入口都受影响：关闭单个标签页、批量关闭、以及**退出应用时保存全部**。

### 根因分析

BUG-146 给保存加冲突检测时，改的是"菜单里的保存"和"自动保存"两条路径。
`EditorTabBar.saveTab` 是第三条，它走的还是无检查的 `saveDocument`。

而它恰恰是**关闭前那句"要保存吗"点"是"之后走的路径**——用户以为自己在保护工作，
实际上是在覆盖别人的。

### 排查方式

延续上一轮的做法：把 `saveDocument` / `saveDocumentIfUnchanged` 的**全部五个
调用点列出来逐个核实**，而不是等着撞见。其中两个无检查是正当的——
"另存为"到刚选的路径（没有基准可比，且选择器已经问过是否替换）、
以及用户被告知冲突后主动选择的"覆盖"。剩下那个不是。

### 修复方案

已有路径走带检查的版本；冲突时**标签页保持打开且保持已修改状态**——
关闭它会丢掉用户的编辑，换成一个他们从没见过的版本。状态栏挂上与自动保存
同一条告警，Ctrl+S 提供覆盖/重载/稍后再说三个出口。

### 守卫

新增结构测试：扫描三个文件里所有 `FileService.saveDocument(` 调用，
**上方注释未说明"为何有意无条件写"的一律判为不合格**。

这条守卫第一次跑就报了我自己保留的 `else` 分支——它是正当的，
但注释里没写清楚。**我选择把注释补清楚，而不是放宽守卫**。
之后验证：把关闭时的检查退回原样，守卫准确点名那一行。

### 涉及文件

- `code/lib/ui/widgets/editor_tab_bar.dart`、`code/lib/app.dart`
- `code/test/services/save_conflict_test.dart`（+1 条，共 16 条）

## BUG-159：保存刚完成的一瞬间，下一次保存会把自己的写入当成别人改的

**优先级**：P2　**状态**：已修复　**日期**：2026-08-30

### 现象

按 Ctrl+S 保存之后**立刻**再触发一次保存，会被判为"文件已被外部修改"：
保存被拒绝、状态栏挂起告警、自动保存对该文件停摆——
**而实际上改动这个文件的正是本应用自己**。

### 根因分析

`markSaved` 用 `unawaited(refreshDiskStamp(id))` 事后异步刷新磁盘戳。
写盘已经改变了文件的修改时间，而标签页手上还是写盘**之前**的戳，
落在这段窗口里的下一次保存就会比对失败。

**这正是 BUG-149 里我自己判定过的坏模式**——"事后异步补记会造出时序窗口"。
当时把自动保存那条改成了 `await _markSavedWithStamp(...)`，
**`markSaved` 这条漏了**：同一件事在两处实现，有一处没跟上。

### 实测（不是推断）

```
markSaved 之后立刻: 戳是否已过期 = true
等 120ms 之后:      戳是否已过期 = false
```

### 修复方案

`markSaved` 改为 `Future<void>`，**取戳在发布状态之前完成**，
三个调用方（关闭标签页保存、菜单保存、另存为）一并补上 `await`。
**只改函数不补 await 等于窗口还在**，所以改完专门 grep 过全部调用点。

修复后复测：紧接着检查戳已不过期，随后那次保存也能正常写入。

### 验证测试有效

把 `markSaved` 退回"沿用旧戳 + 事后异步补"的写法，该测试立刻变红。

### 涉及文件

- `code/lib/providers/tab_provider.dart`
- `code/lib/ui/widgets/editor_tab_bar.dart`、`code/lib/ui/widgets/app_menu_bar.dart`
- `code/test/services/save_conflict_test.dart`（+1 条，共 17 条）

## BUG-160：导出失败会毁掉被覆盖的那份旧文件

**优先级**：P2　**状态**：已修复　**日期**：2026-08-30

### 现象

导出为 HTML / PDF / Word 时，如果选的是一个**已经存在的文件**（选择器会问"是否替换"），
而导出中途失败（磁盘满、进程被杀、断电）——**旧的那份没了，新的也不完整**。
保存图表 PNG 同理。

### 根因分析

`writeAsString` / `writeAsBytes` **在打开文件的瞬间就把内容清空了**。实测：

```
写前 1000 字节
打开写句柄后 0 字节  <<< 已被截断
```

保存文档那侧早就解决了这个问题——用临时文件 + flush + rename，
注释写得很清楚："A plain writeAsBytes truncates the file and then writes
into it. Killed process, full disk, lost power…"。
**导出这侧是没跟上的那份副本。**

### 修复方案

把那段原子写抽成 `FileService.writeBytesAtomically`，
导出（HTML / PDF / Word）与图表 PNG 保存三处复用。
配置文件（`json_store`）此前已是原子写，无需改动。

图片存储与回收站记录**保持原样**：前者写的是一个刚生成的新路径（没有旧内容可毁），
后者的孤儿记录已在 BUG 记录里说明是无害的。

### 测试上的一次自我纠正

第一版测试把**文件**设成只读来制造失败，结果测试报"原文件被毁了"，
一度以为修复没生效。查证后发现是**测试设计错了**：原子写是在**目录**里建临时文件
再 rename，而 rename 覆盖一个只读文件是会成功的——
**那恰恰说明原子写在工作，不是失败**。改成把**目录**设为不可写才是真正的失败场景。

改对之后验证：退回非原子写，测试立刻报"之前那份导出被毁了"。

### 涉及文件

- `code/lib/services/file_service.dart`（抽出 `writeBytesAtomically`）
- `code/lib/services/export_service.dart`、`code/lib/ui/widgets/mermaid_renderer.dart`
- `code/test/ui/widgets/export_failure_test.dart`（+3 条，共 10 条）

## BUG-161：退出应用时若有目录或文件正在读取，会抛未捕获的异步错误

**优先级**：P2　**状态**：已修复　**日期**：2026-08-30

### 现象

- 打开一个较大的文件夹，读取还没完成就退出应用
- 或双击一批 `.md` 文件，还没全部打开就退出

两种情况都会抛 `Bad state: Tried to use FileNotifier / TabNotifier after
'dispose' was called`。因为这些调用**没有人 await**，异常直接逃逸成
**未捕获的异步错误**——不会被任何东西接住，也不会显示给用户。

### 实测（不是凭形态推断）

构造 40 个子目录 × 20 个文件的树、以及 30 个各 20KB 的文件，
发起读取后立刻 `dispose`：

```
loadDirectory:                 抛出 StateError — Tried to use FileNotifier after dispose
openFilesFromSecondInstance:   抛出 StateError — Tried to use TabNotifier after dispose
```

### 根因分析

`await` 之后直接写 `state`，中间没有检查 notifier 是否还活着。
**这与 BUG-149 是同一形态**——那次是标签页关闭后磁盘戳仍在异步刷新。
当时只修了撞见的那一处，没有回头把同类找全。

`_refreshTree` 也在此列：它有一个"目录已切换"的守卫，但那不是 mounted 检查，
而它是由文件系统监听器触发的——**退出流程不会等它**。

### 修复方案

三处在写 `state` 之前加 `if (!mounted) return;`。

### 守卫

新增结构测试：扫描 `lib/providers` 下所有 `StateNotifier` 子类的 async 方法，
**若在第一个 `await` 之后写 `state` 而中间没有 `mounted` 检查，即判为不合格**。
这样明天新写的方法也在覆盖内。

验证过：去掉刚加的守卫，它精确点名 `file_provider.dart:28` 与
`tab_provider.dart:768`。

### 涉及文件

- `code/lib/providers/file_provider.dart`、`code/lib/providers/tab_provider.dart`
- `code/test/providers/dispose_race_test.dart`（新增，3 条）

## BUG-162：节点标签里写了箭头，这个节点就从图上消失

**优先级**：P1　**状态**：已修复　**日期**：2026-08-30

### 现象

```
graph TD
  A["流程 --> 结束"] --> B
```

**画出来只有一个方框**。节点 A 整个没了，连线也是错的。
在中文文档里用 `-->` 描述流程是很常见的写法。

`--`（双短横）同样触发，`{判断 --> 是}` 这类菱形节点也一样。

### 根因分析

连线是靠一个正则在整行上 `allMatches` 找出来的，**不区分是否在标签内部**。
标签里的 `-->` 被当成真正的箭头，行就被从错误的位置切开了。

### 修复过程中的两次纠正

**第一版：跳过"起点落在标签内"的匹配。** 结果 `X["a -- b"] --> Y`
从"解析错"变成了"整个解析失败"——更糟。

查明原因：正则里 `A -- 标签 --> B` 那一分支**从标签内的 `--` 开始匹配、一直吃到
标签外真正的箭头**。跳过这个匹配时，真箭头已经被它吃掉了，而 `allMatches`
不会回头再找。改为**先把标签区段遮蔽成空格再跑正则**——偏移不变，标签内容不参与匹配。

**第二版：遮蔽了所有引号包围的内容。** 既有测试立刻抓到
`A -- "spoken" --> B` 的**连线标签**被一起遮掉了。
改为**只遮蔽紧跟在节点名之后的括号**（`A[…]` / `A(…)` / `A{…}`），
裸引号不算——那是连线标签的写法。

### 修复方案

`_labelRanges` 找出所有"节点名 + 括号"的区段（处理嵌套与内部引号），
`_withLabelsBlanked` 把区段内容替换成等长空格后交给正则匹配，
切分时仍从原始行上取内容，所以标签文字完整保留。

### 测试

7 条新测试，覆盖：引号内全箭头、中文、裸 `--`、菱形节点、连线标签仍有效、
嵌套方括号、三段链。**验证过能失败**：退回"不遮蔽"，其中 4 条立刻变红。

### 涉及文件

- `code/lib/ui/editor/mermaid/parser/flowchart_parser.dart`
- `code/test/ui/editor/mermaid/label_test.dart`（+7 条，共 27 条）

## BUG-163：甘特图任务名里带冒号会被截断

**优先级**：P2　**状态**：已修复　**日期**：2026-08-30

### 现象

```
gantt
 dateFormat YYYY-MM-DD
 section S
  阶段一: 设计 :a1, 2026-01-01, 3d
```

任务名只剩 `阶段一`，"设计"没了；而且 id 变成了 `设计 :a1`——
**别的任务用 `after a1` 依赖它就找不到了**。

### 根因分析

任务行按 `line.indexOf(':')`（第一个冒号）切成"名字"和"定义"，
不考虑名字里本来就可能有冒号。中文里"阶段一: 设计"是很自然的写法。

**但不能简单改成"最后一个冒号"**——`dateFormat YYYY-MM-DD HH:mm` 时
定义里合法地含有冒号（`2026-01-01 10:30`），改成最后一个会把它切坏。

### 修复方案

判据不是位置，而是**冒号后面跟的是什么**：一个定义总是以
**状态关键字 / `after …` / 日期 / 不含空格的 id** 开头，而名字的后半截不会。
从左往右挑第一个满足这个条件的冒号。

四种定义开头都覆盖到了，含 `done, crit, b1, …` 这种多关键字的形式。

### 测试上的两次自我纠正

1. **第一次探针把一个 bug 误报成了两个。** 输出里 `tasks=[设计, 评审]`
   ——我读成了"两个任务"，实际是**一个名为 `设计, 评审` 的任务**，
   Dart 的列表打印形式完全一样。改成打印数量和带引号的名字才看清。
   逗号那条本来就是对的，**没有去改它**。
2. **最后一条断言写错了。** 我断言"只有无冒号行时任务列表为空"，
   实际是整个甘特图解析返回 null。查证发现**这是既有行为**（修复前后都如此），
   而且合理——一个任务都没有的甘特图确实不成图。改成断言"这样的行不会在真实
   任务旁边多出内容"。

### 涉及文件

- `code/lib/ui/editor/mermaid/parser/gantt_parser.dart`
- `code/test/ui/editor/mermaid/gantt_task_name_test.dart`（新增，8 条）

### 同批查证、结论为干净的

时序图（消息含冒号/箭头、参与者别名含空格）、类图（方法含逗号、关系标签含冒号）、
ER 图、饼图、思维导图、时间线——**这些图型的分隔符处理都没有问题**。

## BUG-164：换行写成的标题被当成正文，底下多出一条分隔线

**日期**：2026-08-30　**优先级**：P2　**状态**：已修复

### 现象

标题写成两行（源文件里手动折行，或从别处粘进来的长标题），下面用 `---` 或 `===`
画线，渲染出来不是标题，而是一段正文加一条水平分隔线：

```
Release notes for
the autumn build
---
```

得到 `<p>Release notes for the autumn build</p><hr>`，应为 `<h2>…</h2>`。
用 `===` 画线更糟——`===` 被当成正文吞进段落，显示成 `Foo Bar ===`。

反向的错也在：四格缩进的代码块下面跟一条 `---`，代码块被吃掉当成了标题。

### 根因

两个方向，同一处代码。

**吃不下多行**：setext 标题只在"下一行是画线"时成立，所以它必须提前一行判断，
写在了块级分支里，只取紧挨画线的**那一行**当标题内容。CommonMark 的规则是画线
关闭它上面**整个段落**。真正拦住多行的是段落聚合循环：`---` 长得像分隔线，循环
在它之前就停了，`---` 随后被分隔线分支消费；`===` 谁都不匹配，直接被当正文吸走。

**吃得太多**：那个提前判断不看缩进。缩进四列的行是代码，不是标题内容。

### 修复方案

1. 段落聚合结束后补一个分支：如果停下来的那行是画线且已经收了正文，整段作为标题
   内容发出。单行的老分支保留——它不需要先聚合段落。
2. 段落循环内新增一个 break：`===` 也要终止段落，它此前不匹配任何块级模式。
3. 单行分支加上 `_indentColumns(line) < 4` 的前置条件。
4. 段落的终止条件抽成 `_startsAnotherBlock`，供聚合循环与大纲提取共用
   （为此把 `_startsTable` / `_parseCells` 改为 static，两者本就不碰实例状态）。

### 连带修正：大纲

大纲提取是这个行为的第二个副本，仍停在单行版：多行标题在大纲里只显示最后一行，
**且行号指向标题的最后一行而非开头**——点击条目会滚到标题末尾。改成同样往回走
整段，行号取段首，文本用空格拼接（大纲条目没有 `maxLines`，塞换行会撑高行高）。
`heading_outline_test.dart` 里"大纲必须与预览一致"的等价断言相应地把软换行折叠成
空格再比，这也正是标题该有的读法。

### 验证

## BUG-165：`* * *` 和 `- - -` 画不出分隔线，被当成了列表

**日期**：2026-08-30　**优先级**：P2　**状态**：已修复

### 现象

手写分隔线最常见的两种写法失效：

```
* * *
- - -
```

`* * *` 渲染成一个内容为 `* *` 的列表项，`- - -` 同理。只有紧挨着写的 `***`
`---` `___` 才认。缩进一到三格的 `***` 也不认（其它块级元素都允许三格缩进）。

写在列表中间的分隔线更怪：`* Foo` / `* * *` / `* Bar` 得到的是一个三项的列表，
中间那项是 `* *`。

### 根因

分隔线正则是 `^(\*{3,}|-{3,}|_{3,})\s*$`——标记之间不许有空格，前面也不许有缩进。
而列表正则 `^[\s]*[-*+]\s+(.+)$` 恰好匹配 `* * *`，于是落进列表分支。

列表中间那种是第二处：顶层分支已经先判分隔线（顺序是对的），但收集列表行的
`_startsListItem` 只问列表正则、不问分隔线正则——**同一行，两个地方给出不同答案**。

### 修复方案

1. 分隔线正则允许标记之间有空格/制表符，并允许最多三列缩进。
2. `_startsListItem` 加上"不是分隔线"的前置条件，让两处对同一行的判断一致。

### 顺带修正：规范测试的归一化漏洞

`commonmark_spec_test.dart` 折掉语法高亮装饰的两条规则是
`' class="hljs"'` 和 `' class="language-x"'`，但高亮代码块上两个类是**写在一起**的
（`class="hljs language-ruby"`），两条规则都不匹配——于是每个带高亮的规范用例都被
记成解析失败。合成一条规则处理整个 class 属性，并成对折掉高亮 `<span>`
（不能无差别删 `</span>`：导出器还会写 `math-inline` 的 span，那样会只剩开标签）。

### 验证

CommonMark 规范用例 355 → 368：分隔线正则本身 +8，归一化修正 +4，
`_startsListItem` +1。下限同步抬到 368。
新增 4 条测试中 3 条在改动前的代码上确认会失败；第 4 条"真列表仍是列表"是护栏
（`* item` 与 `- - -` 只差第一个标记后面跟什么），两边都应通过。

### 涉及文件

- `code/lib/services/markdown_parser.dart`
- `code/test/services/markdown_parser_test.dart`（新增 4 条）
- `code/test/services/commonmark_spec_test.dart`（归一化修正；下限 355 → 368）

## BUG-166：加粗里的链接、斜体里的加粗都渲染不出来

**日期**：2026-08-30　**优先级**：P1　**状态**：已修复

### 现象

强调内部的任何标记都不解析，原样显示成字面量：

| 写法 | 期望 | 实际 |
|------|------|------|
| `**加粗里有 [链接](/url)**` | 加粗 + 可点击的链接 | 加粗的一段，屏幕上显示 `[链接](/url)` |
| `*斜体里有 **加粗** 的词*` | 斜体 + 内部加粗 | 斜体的一段，显示 `**加粗**` |
| `**说明里有 \`代码\`**` | 加粗 + 等宽代码 | 显示反引号 |

预览、HTML 导出、Word 导出、PDF 导出**四个出口全都如此**——因为它们拿到的是同一份
数据。

### 根因

内联模型是扁平的：`InlineSpan` 只有 `type` 和 `text`，没有子节点。一个加粗 span
无法容纳一个链接 span，所以解析器能做的只有把内部原样留成文本。模型注释里其实
早就写明了这一点（README 徽章那种"链接套图片"是靠额外加一个 `linkHref` 字段绕过去
的）。

### 修复方案

1. `InlineSpan` 增加 `children`，默认空。**空表示走原来的扁平路径**，所以绝大多数
   span 的行为一字未变。
2. `parseInline` 拆成两段：外层负责转义替换与最后的还原/实体解码（现在会递归走过
   子节点），内层 `_inlineTokens` 是一遍匹配，强调分支对内部文本递归。
   **递归发生在转义还原之前**——否则 `**a \*b\* c**` 里被转义的星号会在还原后
   被子解析当成真标记。
3. 四个消费方各自接上：HTML 与 PDF 直接渲染子节点；预览把外层强调的样式作为子节点
   的基准样式（所以"斜体里的加粗"两种效果叠加，链接仍可点）；Word 的 run 不能嵌套，
   改成把外层强调用 `copyWith` 折进每个子 run。

### 性能

用户对"轻量、大文件"的要求是硬约束，所以加了廉价前置检查：内部文本不含
`[*_[!\`~<^:$=]` 中任一字符就不递归。实测 306 KB、每段都有强调的文档：

| 文档形态 | 关闭递归 | 开启递归 |
|---|---|---|
| 普通（强调内部无标记） | 260–382 ms | 268–386 ms |
| 极端（每段强调内部都嵌链接/斜体/代码） | — | 377–469 ms |

普通文档在噪声范围内持平；只有每段都嵌套的极端文档慢约 40%。

### 未修的已知限制

`*外层 **内层***` 结尾三个星号连在一起时，加粗分支先匹配走 `**内层**`，外层斜体
根本没形成。这是扁平正则**找不找得到强调**的问题，与本次"找到之后内部怎么解析"
无关，留了一条测试记录当前行为，方便日后动它时有对照。

### 验证

CommonMark 规范用例 368 → 383。新增 10 条测试，其中 5 条在保留模型、仅关闭递归时
确认会失败；另 5 条是护栏（普通强调不产生子节点、转义标记不被当成嵌套、
源文本仍保留、纯加粗的 HTML 与原来完全一致、上述已知限制）。

### 涉及文件

- `code/lib/services/markdown_parser.dart`（模型 + 解析递归）
- `code/lib/services/export_service.dart`（HTML / Word / PDF 三个出口）
- `code/lib/ui/editor/markdown_renderer.dart`（预览）
- `code/test/services/nested_emphasis_test.dart`（新增，10 条）
- `code/test/services/commonmark_spec_test.dart`（下限 368 → 383）
