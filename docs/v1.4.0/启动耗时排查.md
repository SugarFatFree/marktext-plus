# 启动耗时排查指引

用户反馈：v1.2.3 打开文件不到 1 秒，现在要 2 秒多；关闭窗口还会卡一段时间。
为定位是哪一步变慢，应用里加了启动埋点。

## 日志在哪

**优先写在可执行文件旁边** —— 解压出来的目录里，`marktext_plus.exe` 边上就是
`startup-trace.log`，不用去找。只有那个目录不可写时（例如装在
`C:\Program Files` 下）才退回配置目录。

日志文件的第三行会写明它自己的完整路径，所以拿到内容就知道它从哪来。

退回时的配置目录：

| 平台 | 路径 |
|------|------|
| Windows | `%APPDATA%\com.marktextplus\MarkText Plus\startup-trace.log` |
| Linux | `~/.local/share/marktext_plus/startup-trace.log` |
| macOS | `~/Library/Application Support/com.marktextplus.marktextPlus/startup-trace.log` |

Windows 那两层来自 `windows/runner/Runner.rc` 的 `CompanyName` 与 `ProductName`，
**中间那层带空格**。

### 环境变量的写法按 shell 而不同

| 在哪里 | 写法 |
|---|---|
| PowerShell | `$env:APPDATA` |
| cmd | `%APPDATA%` |
| Win + R 对话框 | `%APPDATA%` |

**在 PowerShell 里写 `%APPDATA%` 不会展开**，会被当成普通文件夹名。

PowerShell 直接打印：

```powershell
Get-Content "$env:APPDATA\com.marktextplus\MarkText Plus\startup-trace.log"
```

Win + R 直接用记事本打开：

```
notepad %APPDATA%\com.marktextplus\MarkText Plus\startup-trace.log
```

搜不到的话：

```powershell
Get-ChildItem $env:APPDATA -Recurse -Filter startup-trace.log -ErrorAction SilentlyContinue |
  Select-Object FullName
```

**搜出来是空的本身也是有用的信息** —— 说明程序没走到写日志那一步。

> Windows 的发行版是 GUI 子系统程序，**stdout 不会回到启动它的控制台**，所以
> 日志以文件为准，命令行里看不到是正常的。

## Windows 上用命令行启动并打开文件

CI 每次推送都会产出 Windows 包，产物名 `windows-x64-<commit sha>`，
在仓库的 Actions 页面对应那次运行里下载。解压后是可直接运行的目录。

PowerShell：

```powershell
cd <解压出来的目录>
.\marktext_plus.exe "C:\路径\你的文件.md"
```

cmd：

```bat
cd <解压出来的目录>
marktext_plus.exe "C:\路径\你的文件.md"
```

路径带空格时务必加引号。命令行参数只接受 `.md` / `.markdown` / `.txt`，
其它扩展名会被忽略（这是 `_filterStartupFiles` 的规则）。

跑完之后把 `startup-trace.log` 的内容发回来即可。

## 日志长什么样

每行是「进程启动至今的毫秒数」+「距上一步的增量」+「步骤名」，
**增量大的那一步就是瓶颈**：

```
    12 ms  (+   12 ms)  flutter binding ready
    45 ms  (+   33 ms)  single instance check
   180 ms  (+  135 ms)  window manager ready
   ...
```

## 已埋的步骤

启动：
`flutter binding ready` → `single instance check`（仅 Windows）→
`window manager ready` → `startup args filtered` → `config directory resolved` →
`config loaded` → `provider container built` → `runApp called` →
`window ready to show` → `window shown` → `first frame painted` →
`startup side-effects dispatched` → `loading tab added` → `loading frame painted` →
`file read in isolate` → `decoded` → `content handed to the tab` → `document painted`

关闭：
`close requested` → `window geometry saved` → `window destroyed`

## 头号嫌疑：目录监视器

对比 v1.2.3 与现在的启动路径，最可疑的是 **`OpenDocumentWatcher`（v1.4.0 才有的
「文件被外部改动时自动重载」）**：

- 它为每个打开过的文件的**所在目录**建一个 `Directory.watch()`。Windows 上这走
  `ReadDirectoryChangesW`，每个目录要一个句柄和一个线程，**创建不便宜**。
- 关闭时要逐个 `cancel()`。Windows 上取消目录监视**会拖住进程退出** —— 这与
  「关闭窗口卡一段时间」的现象完全对得上。
- `TabNotifier` 重写了 `state` 的 setter，**每次状态变更都会重新同步一遍监视集合**。
  启动时恢复标签页与侧边栏列表会触发很多次。

所以日志里要重点看这三行：
`restoring N sidebar entries`、`directory watch created in X ms`（会出现多行）、
`cancelled N directory watch(es) in X ms`。

另一处结构性变化：**v1.2.3 是先 `show()` 窗口、再读配置；现在为了恢复窗口几何，
把配置读取挪到了显示之前**。这会拉长「看到第一帧」的时间，看
`config loaded` → `window shown` 这一段的增量。

## 排查时的几个已知可疑点

- `file read in isolate`：每个文件都用 `compute()` 起一个 isolate。小文件上，
  起 isolate 的固定开销可能远大于读取本身。**注意这一条 v1.2.3 就有**，所以它
  即便慢，也不是本次回退的原因，只是绝对值上的浪费。
- `window manager ready` 与 `window shown` 之间：窗口几何、最大化状态的恢复。
- `close requested` → `window destroyed`：几何写盘是异步的，若配置写入变慢
  会直接体现在这里。

拿到日志再定位，不先改。

## 2026-08-28 第二份用户日志：埋点深入到进程级

### 用户反馈的日志（构建来自 `a5c7a0b` 之前）

```
     0 ms  (+    0 ms)  flutter binding ready
    ...
   191 ms  (+   11 ms)  document painted
 18678 ms  (+18487 ms)  close requested
 18774 ms  (+   96 ms)  window geometry saved
 18784 ms  (+   10 ms)  window destroyed
```

用户报告：首次启动并打开文件仍需 2 秒，关闭窗口仍然卡死。

### 从这份日志能确定的

| 结论 | 依据 |
|---|---|
| **Dart 侧不是瓶颈** | 从 binding ready 到 document painted 一共 **191 ms** |
| **约 1.8 秒发生在 Dart 之前** | 用户感知 2 秒，减去 191 ms |
| **关闭的处理只用了 106 ms** | close requested → window destroyed |
| **卡死发生在 `destroy()` 之后** | 日志最后一行就是 window destroyed，之后再无记录 |

### 一次判断失误，以及它引出的改动

我最初根据日志里的 `file read in isolate (16960 bytes)` 判断"用户的包比修复早"。
用户随后说明下载的是 `a5c7a0b`（CI #191）。核对后：

```
$ git show a5c7a0b:code/.../home_screen.dart | grep 'file read'
388:  StartupTrace.mark('file read (${bytes.length} bytes)');   ← 没有 "in isolate"
```

`file read in isolate` 这句话只存在于 `ab1a43e`~`57bd7a0` 之间的构建里。所以那个 exe
**确实不是 #191 的产物** —— 但这件事花了一轮往返才弄清，而且期间我拿着当前源码去解释
一份旧二进制产生的日志。

**改动：日志头写入构建标识。** CI 构建时用 `--dart-define` 注入 `BUILD_SHA` 与
`BUILD_RUN`，日志第三行直接写 `build: a5c7a0b  (CI run #191)`；本机构建则写
`build: local (no BUILD_SHA; this is not a CI build)`。以后不会再出现"照着源码解释
旧日志"的情况。

### 埋点深入到进程级（回应「日志记录同样不够详细」）

原来的埋点最早只能从 `flutter binding ready` 开始 —— 而那 1.8 秒全部发生在它之前，
**现有埋点一个字都覆盖不到**。所以埋点下沉到 Windows runner（`windows/runner/main.cpp`）：

| 新增标记 | 位置 | 覆盖的阶段 |
|---|---|---|
| `MARKTEXT_TRACE_RUNNER_ENTRY` | `wWinMain` 第一行 | 进程创建 → 入口：Windows 加载 exe 与 DLL |
| `MARKTEXT_TRACE_ENGINE_START` | 创建窗口之前 | 入口 → 引擎启动：控制台、COM、命令行 |
| `MARKTEXT_TRACE_WINDOW_CREATED` | 窗口创建之后 | 引擎启动 → 窗口就绪：引擎启动与 AOT 快照加载 |

三个时间戳用 `GetProcessTimes` 取"距进程创建的毫秒数"，通过 `SetEnvironmentVariableW`
留给 Dart，Dart 用 `Platform.environment` 读回来。选环境变量是因为它零成本、在引擎启动前
就已就位，而且两边都不需要知道对方的存在。

这样一份日志会把 1.8 秒拆成三段，**指向三个完全不同的问题**：exe/DLL 加载慢（体积、
杀毒软件扫描）、引擎启动慢（快照大小）、还是 Dart 入口之前有别的东西。

### 关闭卡死：看门狗同时是诊断和兜底

日志停在 `window destroyed`，之后什么都没有 —— 说明卡死发生在这一行之后，
而现有埋点**没有任何手段能看到那一段**。新增 `StartupTrace.armShutdownWatchdog()`，
在 `destroy()` **之前**武装（这样连"destroy 不返回"的情况也覆盖到）：

- 每 100 ms 记一行 `still running Nms after close began`
- 600 ms 后记一行并 `exit(0)`

它同时回答两个问题，而且第二个只有靠第一个才能回答：

1. **卡死是哪一种。** 如果日志里出现这些行，说明 Dart isolate 还活着、而窗口不肯消失
   —— 有东西堵住了 Win32 消息循环。如果日志停在 `window destroyed` 且这些行一条都没有，
   说明 isolate 已经没了，拖住进程的是原生层。这是两个完全不同的问题，**除此之外没有
   任何埋点能把它们区分开**。
2. **不让用户干等。** 所有必须落盘的东西（窗口几何、文档、设置）都在武装之前就写完了，
   所以到了"继续等更糟"的时候，走掉是安全的。

### 顺带修掉的一处

`_saveWindowGeometry` 花了 96 ms，里面是**三次串行的平台通道往返**
（`isMaximized` / `getSize` / `getPosition`）加一次配置写盘。改成 `.wait` 并行，
并把"读窗口边界"和"写配置"拆成两个标记，下一份日志能看出 96 ms 具体花在哪一半。

### 下一步需要用户配合的

**请连续启动两次，把两份日志都发回来。** 这能区分两种完全不同的原因：

- 如果第一次的「进程创建 → 入口」很大而第二次很小 —— 那是 Windows 首次运行新
  可执行文件的固有成本（Defender 扫描、冷页缓存、无预取数据），**不是本项目的代码问题**，
  用户说的正是"首次启动"
- 如果两次都很大 —— 那就是 exe/DLL 体积或引擎启动本身，需要另外处理

### 无法本机验证的部分（如实说明）

`windows/runner/main.cpp` 的改动**在这台机器上无法编译验证**（没有任何 C++ 编译器），
而 `gh` 也已不在这台机器上，CI 结果同样看不到。为把风险压到最低，那段代码：

- **不引入任何新头文件**，只用 `windows.h` 里已有的四个调用
  （`GetProcessTimes`、`GetCurrentProcess`、`GetSystemTimeAsFileTime`、`SetEnvironmentVariableW`）
- **不使用任何字符串格式化函数**（`swprintf_s` 之类），整数转宽字符串是手写的
- 全部集中在一个匿名 namespace 里，万一构建失败，回退只需删掉那一段

## 2026-08-28 为什么装了新包却看不到新日志

### 用户的观察

> 新 exe 包下载安装后，用命令启动没有新的日志。是目录位置变了吗？
>
> 我可以看到 config 文件是有更新的：`…\com.marktextplus\MarkText Plus\config.json`
> 但是日志文件没有：`…\com.marktextplus\MarkText Plus\startup-trace.log`

**config.json 在更新、日志不在同一个目录**——这一条把原因定死了。

### 根因

```dart
static void useDirectory(String directory) {
  for (final candidate in [_beside(Platform.resolvedExecutable), directory]) {
    if (candidate == null) continue;
    _logPath = '$candidate${Platform.pathSeparator}startup-trace.log';
    if (flush()) return;          // ← 写成功就直接返回，配置目录根本没试
  }
  _logPath = null;
}
```

**exe 旁边排在第一位，写成功就返回。**安装版的 exe 在 `C:\Program Files\MarkText Plus\`，
日志就落在那里，而被要日志的人去了配置目录（设置文件在那儿，这是最自然的推断），
一无所获，于是合理地得出"日志根本没写"的结论。

当初把 exe 旁边排在前面是有理由的，注释里也写了：解压包运行的人在程序旁边就能找到，
不用去 `%APPDATA%` 里翻。问题是这个理由只对解压包成立，而对安装版恰好相反。

### 修复

1. **配置目录排第一，而且无条件写。**那个目录由 path_provider 创建，一定存在、一定可写。
2. **不再"写成功就停"，而是所有能写的位置都写一份。**几 KB 的事，从此在哪儿找都能找到。
3. 日志头的 `log:` 那行列出全部路径，用 `|` 分隔。

### 顺带：帮助菜单加「打开诊断日志」

代码注释里早就写着"去 `%APPDATA%` 里翻是它自己的一场小折腾"，但当时的解法是换个位置写，
而不是让应用直接把它指出来。现在帮助菜单里有一项直接在资源管理器里选中那个文件
（Windows 用 `explorer /select,`，macOS 用 `open -R`，Linux 打开所在目录）。

### 另一件值得记下来的事

用户更早一次报「`cd %APPDATA%\com.marktextplus\` 找不到路径」。**PowerShell 不展开
`%APPDATA%`**，那是 cmd 的语法，PowerShell 要写 `$env:APPDATA`。当时我据此以为目录不存在，
方向就偏了一次。

## 2026-08-28 决定性的一份日志：2.53 秒全在 Dart 之前

### 用户日志（安装在 `D:\MarkText Plus`）

```
  2530 ms  (+ 2530 ms)  process start → Dart (shell, exe and DLL loading, engine)
     0 ms  (+    0 ms)  flutter binding ready
    ...
   149 ms  (+   44 ms)  document painted
   389 ms  (+  179 ms)  window shown
  7258 ms  (+ 6869 ms)  close requested
  7311 ms  (+   53 ms)  window geometry saved
  7312 ms  (+    1 ms)  stopping file watches
  7312 ms  (+    0 ms)  file watches stopped
  7317 ms  (+    5 ms)  window destroyed
```

### 这份日志定死的事实

| 事实 | 数字 |
|---|---|
| **Dart 启动之前** | **2530 ms** |
| Dart 侧全部（到窗口显示） | 389 ms |
| 其中文档读取 + 解码 + 交给标签页 | 6 ms |
| 关闭的处理 | 59 ms，且文件监视确实停掉了 |
| 卡死的位置 | `window destroyed` 之后，日志再无一行 |

**结论：此前所有针对 Dart 侧的优化都不可能解决用户的问题。**小文件不再起 isolate、
预览重建收窄、文件树不再每次按键重建 —— 这些都是真实的改进，但它们加起来影响的是那
389 ms，而不是那 2530 ms。方向直到这份日志才看清。

### 排除掉的一个猜测

Windows 侧需要加载的插件 DLL 只有 6 个（desktop_drop、pasteboard、screen_retriever_windows、
url_launcher_windows、window_manager、windows_single_instance）。**不是插件多。**
需要读进来的主要是引擎 DLL、AOT 快照和 ICU 数据。

### 下一步：让一份日志就能回答冷启动问题

2530 ms 有两种完全不同的可能，应对方式完全相反：

- **只有首次启动慢** —— Windows 首次运行新可执行文件的固有成本：Defender 扫描、
  冷页缓存、没有预取数据。用户说的正是「首次启动」，而且装在 `D:` 盘。**这不是代码问题。**
- **每次启动都慢** —— 那是二进制体积或引擎启动本身，需要另外处理。

原来的日志每次运行都覆盖，要回答这个问题得「启动、拷贝、再启动、再拷贝」四步。
现在**日志保留最近 4 次运行**（用 `=== MarkText Plus startup trace ===` 分隔），
启动两次，一份文件就能对比。

`_recentRuns` 的"保留最后 N 段"配了 4 条测试 —— 这种地方差一个就会静默丢掉数据，
而丢掉的恰好是要用来对比的那一段。

### 已找到但尚未动手的一个体积来源

`package:highlight/highlight.dart` 的第一行就是：

```dart
import 'package:highlight/languages/all.dart';
final highlight = Highlight()..registerLanguages(allLanguages);
```

**190 种语言、1.9 MB 源码，全部编进 AOT 快照。**该包提供了 `highlight_core.dart`
（不注册任何语言），改成按需注册可以砍掉其中大部分。

**没有立刻做**，因为：① 砍掉的语言其代码块会失去高亮，是功能回退，需要先确定保留哪些；
② 在还不知道 2530 ms 是不是冷启动 I/O 之前，无法判断减小体积能带来多少。
等下一份两次启动的日志出来再定。

### 关闭卡死

看门狗已在上一轮加好（`armShutdownWatchdog`），但用户这份日志来自更早的构建，所以
`window destroyed` 之后仍然什么都没有。下一个构建会给出答案：那之后如果出现
`still running Nms after close began`，说明 Dart 还活着、是消息循环被堵；一行都没有，
说明拖住进程的是原生层。

## 2026-08-28 两次启动的对比：不是冷启动，是每次都慢

### 数据（build 1fc89c06 / CI #196）

| | 首次启动 | 二次启动 |
|---|---|---|
| **Dart 之前** | **2740 ms** | **2324 ms** |
| Dart 侧到窗口显示 | 598 ms | 186 ms |
| 关闭处理 | 50 ms | 57 ms |

### 结论：推翻上一轮的假设

上一轮我提出两种可能，并倾向于"首次启动的固有成本"（Defender 扫描、冷页缓存、
无预取数据）。**两次启动的数字否定了这个假设**：冷热之差只有约 400 ms，
而**基线就有 2.3 秒**。

**这是结构性的，每次启动都要付。**方向从"是不是环境问题"转为"二进制里到底有多少
东西要加载"。

### 顺便修掉的两处

**① 关闭时的埋点打了两遍。**日志里 `stopping file watches` / `file watches stopped`
各出现两次，看起来像关闭处理跑了两遍。实际是 `stopWatchingFiles()` 内部本来就有这两条
埋点，我在 `home_screen` 的两个分支里又各加了一遍。**埋点自己也会犯"同一件事记两处"
的毛病。**已删掉外层的。

**② runner 埋点没生效。**日志显示 `runner not instrumented`，但
`git show 1fc89c0:…/main.cpp | grep -c RecordStartupMark` = 4 —— 代码确实在构建里。
所以是传递方式的问题：**`SetEnvironmentVariableW` 写进去的值，Dart 的
`Platform.environment` 读不到。**

改用 **Dart 入口参数**：runner 把 `--mt-trace-runner-entry=<ms>` 和
`--mt-trace-engine-start=<ms>` 追加到 `set_dart_entrypoint_arguments`，直接进
`main(List<String> args)`，中间没有任何环节会丢。`_filterStartupFiles` 按扩展名过滤，
这两个参数会被自然忽略，不需要额外处理。

第三个时间戳（窗口创建）不再需要：Dart 自己用 `GetProcessTimes` 得到的
"process → 第一个 Dart 标记"减去 `engine-start`，就是引擎启动加 AOT 快照加载。

### 下一步需要的一个数字

在弄清**二进制里什么最大**之前，任何减体积的动作都是猜。请在 PowerShell 里执行：

```powershell
Get-ChildItem -Recurse "D:\MarkText Plus" |
  Sort-Object Length -Descending |
  Select-Object -First 12 Name, @{n='MB';e={[math]::Round($_.Length/1MB,2)}}
```

以及总体积：

```powershell
"{0:N1} MB" -f ((Get-ChildItem -Recurse "D:\MarkText Plus" | Measure-Object Length -Sum).Sum / 1MB)
```

2.3 秒对应的是"Windows 把这些文件读进内存并完成引擎初始化"。知道是哪几个文件占大头，
才知道该动哪里。

### 已知的一个体积来源（等数据再决定是否动）

`package:highlight/highlight.dart` 一进来就 `registerLanguages(allLanguages)` ——
**190 种语言、1.9 MB 源码**全部编进 AOT 快照。该包提供 `highlight_core.dart` 可按需注册。

**仍然没有动**，理由不变：砍掉的语言其代码块会失去高亮（功能回退），而在不知道
app.so 实际占多大之前，无法判断这能省下多少。上面那两条命令能直接回答这个问题。

## 2026-08-28 runner 埋点终于到达：2.7 秒定位到引擎启动

### 数据（build 297a9ed6 / CI #217，三次连续启动）

```
    90 ms  (+   90 ms)  进程创建 → runner 入口（Windows 加载 exe 和 DLL）
   140 ms  (+   50 ms)  入口 → 引擎启动（控制台、COM、命令行）
  2781 ms  (+ 2641 ms)  引擎启动 → 第一个 Dart 标记
```

三次分别 2641 / 2704 / 2757 ms，**极其稳定**。

### 推翻掉的三个猜测

| 猜测 | 数据 |
|---|---|
| 读 35 MB 的安装目录慢 | **加载 exe 和全部 DLL 只用 90 ms** |
| 杀毒软件扫描（会有明显波动） | 三次相差不到 5% |
| 首次启动的冷缓存成本 | 连续三次都一样 |

**全部时间在「引擎启动 + 加载 13.6 MB 的 AOT 快照」这一段。**

### 已经做的（零功能代价）

构建加上 `--split-debug-info`：把符号表从 AOT 快照里移出去写到旁边，这是唯一
不损失任何功能的减小方式。下一份日志里应用会自己报出新的 app.so 大小。

### 在继续减体积之前必须先回答的问题

那 2.7 秒里，**有多少是加载快照，有多少是别的**？如果大部分是 GPU 表面初始化
（公司机器、远程桌面、虚拟显卡上这一步可以花掉数秒），那么把 app.so 减小
**一点用都没有**，砍掉语法高亮的语言就是白白牺牲功能。

所以在 `window.Create()` 两侧各取一个时间戳 —— 那一步正是创建 Flutter 视图控制器、
启动引擎、加载快照、建立 GPU 表面的地方。

**传递方式用了 FFI**：入口参数在引擎启动之前就交出去了，装不下之后才测到的东西。
runner 把时间戳放在一个导出的全局变量里，Dart 用
`DynamicLibrary.executable().lookup<Int64>('mt_trace_engine')` 读回来。

下一份日志会把那 2.7 秒拆成三段：

```
engine start → creating the view      （插件注册）
creating the view                     （引擎启动、AOT 快照、GPU 表面）
view created → first Dart mark
```

中间那一段的大小，直接决定「减小 app.so」值不值得做。

### 一次自己造成的事故

改 Dart 侧时写了这么一行：

```python
io.open(p,'w').write(io.open(p).read().replace(old,new))
```

`io.open(p,'w')` 打开即截断，**先于内层的读取执行** —— 读到的是空文件，
结果把 `startup_trace.dart` 清成了 0 字节。`dart analyze` 立刻报了 46 个
「Undefined name 'StartupTrace'」，`git checkout` 恢复后重做（先算完再写）。

**这也是「推送前 analyze 必须是最后一步」这条规矩当场兑现的一次**：
如果只跑了测试没跑 analyze，一个空文件不会让任何测试失败 —— 它们根本编译不过，
但那要等到 CI 才发现。

## 2026-08-28 一个被用户直接推翻的结论，以及真正的嫌疑人

### 我错了

上一轮我从三个数据点拟合出「约 186 ms/MB、截距约 160 ms」，换算成 5.4 MB/s 的读取速率，
据此断定是**杀毒软件在逐字节扫描快照**，并建议用户去找 IT 加排除。

用户的回应直接把它推翻了：

> 我用 1.2.3 版本的包就能秒启动秒关闭啊！所有耗时都不到 1 秒

**同一台机器、同样的杀软环境、同样有 app.so 和 20 MB 的引擎 DLL —— 1.2.3 不到 1 秒。**
如果真是按字节扫描，1.2.3 一样会慢。

**错在哪**：我用一个**环境因素**去解释一个**只在新版本出现**的差异。三个数据点确实
拟合出了漂亮的线性关系，但「减体积有效」不等于「体积是根因」—— 两者都可能只是同一个
根因的表现。**手上一直有一个反例（1.2.3 快），而我没有把它放进结论里检验。**

### 真正的嫌疑人

变量只剩两个，而其中一个能解释「只有新版本慢」：

| 变量 | 能否解释 |
|---|---|
| Dart 代码 3.2 万 → 5.2 万行 | 只能解释一部分，且减到 10.4 MB 后仍有 2.1 秒 |
| **Flutter 引擎版本**（1.2.3 建于 2026-06-02，现在 3.47.2） | **能** |

`window.Create()` 里发生三件事：引擎启动、读快照、**建立图形表面**。
新版 Flutter 在 Windows 上默认改用 **Impeller** 渲染后端，而 Impeller 启动时要**构建着色器管线**
—— 在拿不到驱动着色器缓存的机器上，那正是一笔固定的、每次启动都要付的开销，
和实测到的「稳定 2.1 秒、与磁盘缓存无关」完全吻合。

### 做的实验

runner 在引擎启动前设置引擎开关，退回 1.2.3 时代的渲染后端：

```cpp
::SetEnvironmentVariableW(L"FLUTTER_ENGINE_SWITCHES", L"1");
::SetEnvironmentVariableW(L"FLUTTER_ENGINE_SWITCH_1", L"enable-impeller=false");
```

这套机制在本机 SDK 的 `desktop_device.dart` 里得到确认（`FLUTTER_ENGINE_SWITCHES` 是数量、
`FLUTTER_ENGINE_SWITCH_<n>` 是开关本身，`enable-impeller=false` 是桌面端在用的写法）。
不认识这个开关的引擎会忽略它。

日志里会多一行 `renderer: Impeller off`，所以下一份日志能自证跑的是哪条路径。

**这是一次实验，不是定论。**如果「创建视图」那一段掉到几百毫秒，根因就找到了；
如果没变，说明是引擎的其它变化，而**减体积的收益（已从 2700 降到 2116 ms）仍然作数**。
回退只需删掉那两行。

## 2026-08-28：Impeller 假设被实测推翻

同一个二进制（build 59a1ba46）连开四次，前两次 Impeller 开、后两次关：

| 渲染器 | creating the view | Dart 侧 window ready to show |
|---|---|---|
| Impeller **on** | 2154 ms、2130 ms（均 2142） | 109 ms、129 ms |
| Impeller **off** | 2411 ms、2511 ms（均 2461） | 224 ms、324 ms |

**关掉 Impeller 慢约 320 ms，后面的 Dart 侧也跟着慢一倍。** 所以那两秒不是
渲染器，而且我默认关掉 Impeller 的那次改动是负优化，已还原为默认开启，开关
反向保留（`MARKTEXT_IMPELLER=0` 才关）。

### 这轮真正有价值的发现：对照组根本不是同一条流水线出来的

- v1.2.3 发布于 **2026-06-02**；本项目的 CI 是 **2026-08-27** 才加的。
  也就是说用户手上那个"能秒开"的 1.2.3 包**不是 CI 构建的**，是在别的环境、
  用当时的 Flutter SDK 出的。所有慢的包都是 CI 用 3.47.x 构建的。
- 2026-05-15 发布的 **3.44.0** 正是 1.2.3 当时的稳定版。

一直以来我把"1.2.3 快、现在慢"当成同一条件下的对照，其实两者**至少差了一个
引擎大版本和一整套构建环境**。

### 顺带修掉的一处自相矛盾

CI 的 env 里注释写着"Pinned rather than stable：频道会在我们脚下移动，同一份
源码不该产出不同大小和启动开销的引擎"，而值写的就是 `stable`——**根本没固定**。
跨周对比启动日志的前提就是被这个毁掉的。现已固定为 `3.47.2`（正是产生 2.1 秒
那批日志的版本）。

### 下一步实验（已进 CI）

Windows 构建改成两个 SDK 的矩阵：`3.47.2` 与 `3.44.9`，同一份源码出两个安装包，
产物名带 SDK 版本。日志里本来就会打印 `BUILD_SDK`，装完一看就知道是哪个。

三种结果对应三条路：
- **3.44 快、3.47 慢** → 回归在引擎，固定到旧 SDK 先解用户的痛，再向上游报。
- **两个都慢** → 与引擎版本无关，那就只剩构建环境（CI 出的二进制 vs 当初本地
  出的），下一步比对两个包的文件清单与链接方式。
- **两个都快** → 说明变量在这轮 CI 的其它改动里（固定版本本身也可能改变了
  产物），回头逐项二分。
