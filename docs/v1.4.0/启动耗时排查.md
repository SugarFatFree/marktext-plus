# 启动耗时排查指引

用户反馈：v1.2.3 打开文件不到 1 秒，现在要 2 秒多；关闭窗口还会卡一段时间。
为定位是哪一步变慢，应用里加了启动埋点。

## 日志在哪

每次启动都会**重写**一份 `startup-trace.log`，位置是应用的配置目录：

| 平台 | 路径 |
|------|------|
| Windows | `%APPDATA%\com.marktextplus\marktext_plus\startup-trace.log` |
| Linux | `~/.local/share/marktext_plus/startup-trace.log` |
| macOS | `~/Library/Application Support/com.marktextplus.marktextPlus/startup-trace.log` |

准确路径以 `getApplicationSupportDirectory()` 为准；若上表对不上，在文件管理器里
搜 `startup-trace.log` 即可。

> Windows 的发行版是 GUI 子系统程序，**stdout 不会回到启动它的控制台**，所以
> 日志以文件为准，命令行里看不到是正常的。

## Windows 上用命令行启动并打开文件

CI 每次推送都会产出 Windows 包，产物名 `windows-x64-<commit sha>`，
在仓库的 Actions 页面对应那次运行里下载。解压后是可直接运行的目录。

PowerShell：

```powershell
cd <解压出来的目录>
.\marktext_plus.exe "C:\路径\你的文件.md"
```

cmd：

```bat
cd <解压出来的目录>
marktext_plus.exe "C:\路径\你的文件.md"
```

路径带空格时务必加引号。命令行参数只接受 `.md` / `.markdown` / `.txt`，
其它扩展名会被忽略（这是 `_filterStartupFiles` 的规则）。

跑完之后把 `startup-trace.log` 的内容发回来即可。

## 日志长什么样

每行是「进程启动至今的毫秒数」+「距上一步的增量」+「步骤名」，
**增量大的那一步就是瓶颈**：

```
    12 ms  (+   12 ms)  flutter binding ready
    45 ms  (+   33 ms)  single instance check
   180 ms  (+  135 ms)  window manager ready
   ...
```

## 已埋的步骤

启动：
`flutter binding ready` → `single instance check`（仅 Windows）→
`window manager ready` → `startup args filtered` → `config directory resolved` →
`config loaded` → `provider container built` → `runApp called` →
`window ready to show` → `window shown` → `first frame painted` →
`startup side-effects dispatched` → `loading tab added` → `loading frame painted` →
`file read in isolate` → `decoded` → `content handed to the tab` → `document painted`

关闭：
`close requested` → `window geometry saved` → `window destroyed`

## 头号嫌疑：目录监视器

对比 v1.2.3 与现在的启动路径，最可疑的是 **`OpenDocumentWatcher`（v1.4.0 才有的
「文件被外部改动时自动重载」）**：

- 它为每个打开过的文件的**所在目录**建一个 `Directory.watch()`。Windows 上这走
  `ReadDirectoryChangesW`，每个目录要一个句柄和一个线程，**创建不便宜**。
- 关闭时要逐个 `cancel()`。Windows 上取消目录监视**会拖住进程退出** —— 这与
  「关闭窗口卡一段时间」的现象完全对得上。
- `TabNotifier` 重写了 `state` 的 setter，**每次状态变更都会重新同步一遍监视集合**。
  启动时恢复标签页与侧边栏列表会触发很多次。

所以日志里要重点看这三行：
`restoring N sidebar entries`、`directory watch created in X ms`（会出现多行）、
`cancelled N directory watch(es) in X ms`。

另一处结构性变化：**v1.2.3 是先 `show()` 窗口、再读配置；现在为了恢复窗口几何，
把配置读取挪到了显示之前**。这会拉长「看到第一帧」的时间，看
`config loaded` → `window shown` 这一段的增量。

## 排查时的几个已知可疑点

- `file read in isolate`：每个文件都用 `compute()` 起一个 isolate。小文件上，
  起 isolate 的固定开销可能远大于读取本身。**注意这一条 v1.2.3 就有**，所以它
  即便慢，也不是本次回退的原因，只是绝对值上的浪费。
- `window manager ready` 与 `window shown` 之间：窗口几何、最大化状态的恢复。
- `close requested` → `window destroyed`：几何写盘是异步的，若配置写入变慢
  会直接体现在这里。

拿到日志再定位，不先改。
