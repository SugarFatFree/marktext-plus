## FEAT-148：通过 MCP 安装/更新插件

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-11 |
| 需求描述 | `control` 新增动作 `install_plugin`：按插件名从插件市场装一个新插件，或把已装的更新到最新发布。 |
| 用户场景 | 插件改完、CI 出了新的 release 之后，要验证它，得有人打开插件面板、找到它、点安装、再回来跑命令。这一步没有任何判断，只是挡在自动验证前面的一个人手动作。有了这个动作，「装上 → `run_plugin_command` → 看结果」可以一口气走完。 |
| 实现方案 | 走的是**读者点「安装」那一条完全相同的路**：`PluginCatalogService.install` —— HTTPS、比对 release 自己的 SHA-256、解包时的大小上限与拒绝爬出目录的条目，一样不少。新增的只是「不必有人按按钮」。<br>动作枚举加一个值即编译不过，直到 switch 答复它（`McpAction` 的既有设计）。<br>选哪一个插件抽成纯函数 `McpController.chooseForInstall`，不联网就能测。 |
| 涉及文件 | `lib/services/mcp_tools.dart`（枚举 + schema）、`lib/providers/mcp_provider.dart`（`installPlugin` 与 `chooseForInstall`）、`lib/models/plugin_catalog_entry.dart`（`namedBy`） |

**名字怎么对上**——这是整个功能里唯一会出错的地方，也是最值得说的地方：

自动化知道的是插件的 **manifest id**（`run_plugin_command` 只认这个），而插件市场
的条目**从来没见过 manifest**——一条搜索结果是 GitHub 上的一个 release，manifest
在还没人下载的那个压缩包里。三种名字都接受：

| 写法 | 怎么对上 |
|------|---------|
| `com.marktext.ai-assistant`（manifest id） | 绕道已安装插件声明的 `repository`，再和条目的仓库比 |
| `marktext-plus-plugins/ai-assistant` | 直接比仓库 |
| `github.marktext-plus-plugins.ai-assistant` | 目录条目自己的 id |

仓库按**仓库**比而不是按字符串比：`…/x`、`…/x/`、`…/x.git`、`git@github.com:…/x.git`
指的是同一个地方，按字符串比会说它们是四个。大小写忽略，GitHub 就是这么处理的。

**验收标准**

1. 一个名字只对上一个条目 → 装它，答复里带上「装了什么版本、原来是什么版本、从哪个仓库来」。
2. 一个名字对上两个 → **拒绝，不猜**。装错插件是这里唯一会发生而下载校验抓不到的失败
   （到手的包是真的，digest 也对，只是不是你要的那个）。
3. 一个名字谁都不对 → 拒绝，并把目录里实际有什么列出来。只说「没这个插件」分不清
   是打错字还是列表本身就取短了。
4. 名字为空 → 在**碰网络之前**就拒绝。否则一个调用方的笔误会挂到超时，然后归咎于网络。
5. 目录取不到（限流、断网）→ 说清楚是目录读不到，而不是「插件不存在」。

**已知边界**

- 只装**最新**的那个 release，不能指定版本。目录里本来也只有最新的一条。
- 装完会让插件列表失效重载；正在运行的插件进程不受影响，下次运行才用新代码。

## FEAT-149：通过 MCP 更新应用本体

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-11 |
| 需求描述 | `control` 新增动作 `update_app`：解析出一个可安装的构建、下载、比对 SHA-256、交给安装器装上，应用关闭再自行回来。 |
| 用户场景 | 改完缺陷之后要验证它，必须有人到那台机器上下载安装包、点完向导、再把应用打开。**而我在这边没有那台机器的 shell**——这正是这件事必须做进应用里的原因。做完之后：推 dev → CI 出包 → `update_app` → 应用重启 → MCP 自己回来（端口和 token 都在配置文件里，`home_screen` 启动时就 `apply`）→ 接着测。 |
| 实现方案 | 见下面三节。 |
| 涉及文件 | `lib/services/self_update_service.dart`（新增）、`lib/services/mcp_tools.dart`、`lib/providers/mcp_provider.dart` |

**构建从哪里来——两个来源**

| `source` | `ref` | 要 token | 用途 |
|----------|-------|---------|------|
| `release` | 版本标签，空＝最新 | 否 | 读者拿到的那个 |
| `ci` | 短 sha、完整 sha，或分支名（如 `dev`） | **是** | 每次推 dev，CI 已经打好了 `windows-x64-setup-<完整 sha>` |

`ci` 这条是关键：**不必为了测试去发一个版本**。本项目「未经人工测试不得发版」，
而要人工测试就得先装上——原本是个死结。CI 的 artifact 解开了它。
artifact 不是公开的（哪怕仓库是公开的），所以要 token；token 是这次调用的参数，
**不落盘、不进配置**。

**安全上的取舍（必须写下来）**

「下载一个东西并运行它」和「下载**这一个**东西并运行它」是两种不同的权力，只需要后者：

- 仓库是服务里的常量（`SugarFatFree/marktext-plus`），**调用方改不了**。不是任意 URL。
- 下载前先拿到 GitHub 公布的 `digest`，**没有 sha256 就直接拒绝**——不是「先下再说」。
  这是整个功能里唯一一道挡在「网络上来的字节」和「机器上运行的程序」之间的门，
  所以它有自己的测试（`digestOf`），删掉它别的测试全都照样绿。
- 比对不上 → 报出期望值与实得值，并明说「什么都没运行」。
- **拒绝降级**：比当前版本旧的 release 不装（几乎总是标签打错了）。CI 构建以 commit
  命名、不自称版本号，所以这条对它不适用——与其拿空字符串去比较然后把结果当成判断，
  不如明说这条规则在这里不成立。
- MCP 本身仍然是强制 token 的（空 token 直接抛错），这个动作不改变那一点。

**替换正在运行的程序，交给 Inno 而不是自己写**

Windows 上运行中的程序不能覆盖自己的文件。绕开它的那套动作——关掉应用、换文件、
再启动——正是 Inno Setup 已经做对的事。自己再写一份，代价是万一换到一半失败，
读者的编辑器就坏了，**而这台机器上没有任何人能给我一个 shell 去修**。
所以 `apply` 只做一件事：以
`/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /CLOSEAPPLICATIONS /RESTARTAPPLICATIONS`
调起安装器。`/CLOSEAPPLICATIONS` 结束这个进程，`/RESTARTAPPLICATIONS` 把它带回来。

**验收标准**

1. `dryRun` 只说会装什么，不下载、不运行。
2. 架构要对：x64 机器不能拿到 arm64 的安装包。两个文件都以 `-setup.exe` 结尾，
   只按后缀匹配会挑到先出现的那个——而下载校验永远发现不了，包是真的、digest 也对。
3. 没有 sha256 → 拒绝。
4. `source: ci` 而没给 token → **在碰网络之前**拒绝，并说是缺 token。否则 GitHub 回
   404，报出来是「这个提交没被构建过」，看的人会去查 CI 而不是查 token。
5. 比当前旧的 release → 拒绝，并把两个版本号都说出来。
6. 非 Windows → 明说「只写了 Windows」，不是假装成功。
7. **有未保存的标签页 → 拒绝**，并把文件名说出来。`/CLOSEAPPLICATIONS` 是通过
   Restart Manager 结束进程的：它会问，然后不再等。未保存的内容到那一刻就没了，
   而且**整个流程里没有任何一处会察觉到**——编辑器只是版本新了一个、文档少了一篇。
   这一步在联网**之前**做：先跑一趟 GitHub 再拒绝，那个拒绝来得晚，看起来像网络故障。
   `dryRun` 不受这条限制——问「会装什么」在任何时候都是安全的。

**一个只会在第一次使用时暴露的缺陷（已修）**

CI 用 `${{ github.sha }}` 给 artifact 命名，那是**完整 40 位**的哈希：
`windows-x64-setup-a66c89d4a1a01bee6550f098b8dd09b418ca838c`。
而一个人手上拿到的 commit 永远是短的——`git log --oneline`、PR 页面、CI 运行摘要，
给的都是 `a66c89d`。第一版代码直接把 `ref` 拼进名字里去查，命中 0 个，
**而报出来的话是「这个提交没有被构建过」**——看的人会去查 CI，而问题在拼名字。

这是两份清单没人对账的又一例：`ci.yml` 里的命名，和服务里拼名字的那一行，
写在不同的仓库、不同的时候。修法两步：

1. `ref` 先经 `/repos/{owner}/{repo}/commits/{ref}` 解析成完整 sha。
   顺带的好处是**分支名也能用**了：`ref: dev` 装的就是 dev 顶端那次构建的包。
2. 加一条离线守卫：从 `ci.yml` 里读出 artifact 的命名模板，和 `artifactFor`
   拼出来的名字比对。改任何一边都会红。

**下载的上限用「多久没有新数据」，不用「总共多久」**

一次测量差点让我得出错误结论，记下来：先用 curl 拉这个包是 14 MB/s，
再用 Dart 拉是 30 KB/s，看起来像「Dart 的 HttpClient 慢一千倍」。
**隔了几分钟再用 curl 拉，也只有 29 KB/s**——是链路本身变了，两次测量不可比。
（「测量自相矛盾时先怀疑方法」。）

但它顺带暴露了一个真实的形状问题：包是 15–25 MB，链路是读者手上那条。
同一个文件这一分钟 14 MB/s、下一分钟 29 KB/s（八分钟才下完），
**总时长上限设在任何一处，都会误杀一个正在正常工作的下载**。

而「卡住」长什么样是明确的：一个字节都不再来。所以改成 `stalled`（默认 90 秒
没有新数据就放弃）——和 BUG-404 给 AI 流定的是同一个形状。
同时每 4 MB 写一条日志，这样「慢」和「停了」可以靠读日志分辨，不必靠等。

测试是离线的：本地起一个服务器，发完响应头和 16 个字节之后既不再发也不关连接
（`a_server_that_never_answers_test`）。去掉空闲上限，这条测试会挂到超时。

**安装器留下的那份说法（否则失败时什么都看不到）**

更新一旦开始，这个进程就会被关掉——**它本可以报告的一切都随它一起没了**。
失败时从远端看到的只有两种样子：编辑器带着旧版本回来了，或者没回来。
两种都说不出到底是安装器拒绝了、写不进目录、还是压根没被运行。

Inno 自己有 `/LOG`。现在：

1. `apply` 传 `/LOG=<配置目录>/update-install.log`。
2. **下一次启动**读它——那是更新之后编辑器重新存在的第一刻——把结尾三行折成一行
   写进应用日志（`source: update`），然后**删掉文件**，所以它只在产生它的那次更新
   之后报一次，不会以后每次启动都重复。
3. 于是 `read_logs` 就能看到，远程会话和坐在机器前的人看到的是同一句话。

只取结尾三行：Inno 的日志是几千行逐个文件的拷贝记录，没有一行是读日志的人要找的；
结论在末尾。

**解码要宽容**（这一条是写测试时发现的实现缺陷）：Inno 按机器的代码页写日志，
路径里一个带重音的字符就会让严格的 UTF-8 解码抛异常——**一份完好的说明会变成
「could not be read」，而那是比日志本身更糟的答案**。改成 `allowMalformed: true`。

没有更新发生的那次启动，代价是一次 `existsSync`。

**验证**（四个变异，全部被抓住）：不传 `/LOG` → 13 行失败；读完不删 → 10 行；
改回严格解码 → 8 行；返回整份而不是结尾三行 → 11 行。

**必须告诉安装器装到哪里（否则更新会「成功」而什么都没变）**

第一版没有传 `/DIR`，安装器就用自己的默认目录——按用户安装是
`%LocalAppData%\Programs`。而运行中的那份**常常不在那里**：本项目的使用者就把它
装在 D 盘。于是会发生这样一串事，每一步都「正常」：

1. 安装器把新版装进 `%LocalAppData%\Programs`，成功。
2. `/CLOSEAPPLICATIONS` 关掉的是**正在运行的那份**（D 盘的旧版）。
3. `/RESTARTAPPLICATIONS` 把它原样启动回来。
4. `update_app` 报告成功，**回来的还是旧版本**，磁盘上多了一份没人用的新版。

更糟的是两份还不能同时跑：单实例名是写死的 `"marktext_plus_instance"`，
点新的那份只会把旧窗口调到前面，看起来像「新版打不开」。

修法：`apply` 传 `/DIR=<当前可执行文件所在目录>`（`Platform.resolvedExecutable`
的目录）。这样无论读者把它放在哪，更新都是**就地替换正在运行的那一份**。

**已知边界**

- 只有 Windows 能真的装上。Linux 的 deb/rpm 要 root，macOS 要换 .app——都还没写。
- `ci` 来源只认 Windows 的 artifact（CI 也只打这一个安装包）。

## FEAT-150：Windows 安装包改为按用户安装

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-11 |
| 需求描述 | 安装器加 `PrivilegesRequired=lowest`，装到 `%LocalAppData%\Programs\MarkText Plus`。 |
| 用户场景 | 机器级安装（Program Files）要管理员权限，**静默更新时 Windows 会弹 UAC 等人点一下**——那 FEAT-149 就不算无人值守了，人不在电脑前时更新会停在那里。 |
| 实现方案 | `ci.yml` 与 `release.yml` 的 Inno 脚本各加三行：`AppId`（显式 GUID，原先靠 AppName 推导）、`PrivilegesRequired=lowest`、`PrivilegesRequiredOverridesAllowed=commandline`（`/ALLUSERS` 仍可做机器级安装）。`DefaultDirName={autopf}` 不用改——`{autopf}` 在低权限下自己解析成 `%LocalAppData%\Programs`，`HKA` 解析成 HKCU，`{group}` 和 `{autodesktop}` 也都跟着变成当前用户的。 |
| 涉及文件 | `.github/workflows/ci.yml`、`.github/workflows/release.yml` |

**对现有用户的影响（发布说明里必须写）**

已经装在 Program Files 的那一份，新安装器**看不见它**（安装范围不同，卸载信息一个在
HKLM 一个在 HKCU），会当作全新安装装到用户目录去，旧的那份留在原地。
所以升级到这一版的用户需要**手动卸载一次旧的**。这是一次性的代价，换来的是从此
所有更新都不弹 UAC——Chrome、VS Code 默认也是按用户安装，理由相同。

**验收标准**

1. 安装过程不出现 UAC。
2. 文件关联、开始菜单项、桌面快捷方式仍然建立（都落到当前用户下）。
3. `/ALLUSERS` 仍能做机器级安装。

## FEAT-151：启动耗时的明细能被远程会话读到

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-11 |
| 需求描述 | 新增 MCP 工具 `read_startup_trace`，返回 `startup-trace.log` 的内容（含此前几次启动）。 |
| 用户场景 | 从真实使用的日志里只看得到一行：`app root built at 119 ms (+901 ms before Dart)`。**那 901 毫秒是启动感受的大头，而它是一个不可再分的总数。** `StartupTrace` 其实把明细都记了下来——加载 exe 与 DLL、引擎启动、创建视图（AOT 快照 + GPU 表面）——但只写进文件，而 `read_logs` 只读应用日志。 |
| 实现方案 | `StartupTrace.readBack()`：优先读文件（它带着前几次启动，冷启动与热启动的对比正是这份历史存在的理由），读不到就返回内存里这一次的，并**明说这份没落盘**。超过 64 KB 时取**结尾**——当前这次在结尾。<br>工具用 `startupTrace ?? StartupTrace.readBack`，与 `log ?? AppLog.instance` 同一写法，不需要在 provider 里再接一遍。 |
| 涉及文件 | `lib/core/diagnostics/startup_trace.dart`、`lib/services/mcp_tools.dart` |

**这是「写好了却没接上」的一个变体**：明细不是没人记，是记在了一个**远程会话够不到的地方**。
`StartupTrace` 顶部的注释写着「文件是把数字取回来的唯一办法」——这句话对**坐在那台机器前的人**
成立，对通过 MCP 驱动编辑器的会话不成立。而另一处注释又写着「应用日志是远程会话唯一的窗口」。
两句话都对，合起来就是：最有价值的那份明细，远程永远看不到。

**验收标准**

1. 工具的说明里要写清它能回答什么（「before Dart」），否则启动慢的时候没人会想到它。
2. 没有轨迹时返回**一句话**而不是空串——空串读起来像「请求失败」，会把人引向错误的方向。
3. 文件还没落盘时返回内存里的那份，并说明它是内存里的。
4. 超长时取结尾，并说明截掉了多少。

**验证**（三个变异，全部被抓住）：空结果返回空串 → 4 行失败；截断取开头 → 2 行；
内存那份不再说明来源 → 3 行。

## FEAT-152：大文档的第一屏，代价与文档大小脱钩

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-12 |
| 需求描述 | `safePrefix` 惰性切行，只保留走过的那些行；短文档那条判断改为数行尾而不是建列表。 |
| 用户场景 | 「加载快、支持大文件」是这个编辑器的第一条主张。超过 1500 行的文档分两趟显示，先出顶部——**而它在开始之前把整篇切成了行**，于是一份 6.5 MB 的文档要先分配十几万个字符串，其中绝大多数它永远不会看。循环在切点就返回，切行却没有。 |
| 涉及文件 | `lib/services/markdown_parser.dart`、`test/services/safe_prefix_test.dart` |

**实测（同一台机器，取 15 次最快一次）**

| 文档 | 改之前 | 改之后 |
|------|--------|--------|
| 391 KB | — | 797 µs |
| 1.6 MB | **8776 µs** | **649 µs** |
| 6.5 MB | 约 35 ms（按比例） | **657 µs** |

同一份 1.6 MB 文档快 **13 倍**；而更重要的是**它不再随文档变大**——6.5 MB 和 391 KB 一样快。

**它是怎么被发现的（顺序值得记）**

1. 我按第 1 条自查今晚的改动，发现自己给 `safePrefix` 的每一行加了**四次
   `RegExp` 构造**（`.where()` 里的构造函数逐行求值）。
2. A/B 量它：第一次测量**噪声 15%，分不清**（106/84/92 ms）——
   改成取多次最小值才看清：含我那段 12.3 ms，去掉 8.7 ms，**我占了三成**。
3. 修掉（编译一次 + 先用 `line.contains('<')` 廉价挡掉），回到 8.8 ms。
4. **然后想到：套件里没有任何东西会抓到这次退化**——`cost_stays_linear_test`
   管解析和搜索，`safePrefix` 没有预算。于是给它写了一条**性质相反**的守卫：
   解析和搜索要求「代价跟着输入走」，而前缀扫描要求「**代价不跟着输入走**」，
   因为它在切点就返回。
5. **那条守卫第一次跑就红了**：四倍文档花了 3.5 倍时间。不是我的退化——
   是 `_sourceLines` 从一开始就在切整篇。

**行尾的严谨性**：短文档那条判断原本比的是 `lines.length`，改成数行尾之后必须
与 `LineSplitter` 的切法一致——它把 `\n`、`\r\n` 和**单独的 `\r`** 都算行尾。
三种都验过。

**验收标准**

1. 四倍长的文档，前缀扫描的耗时不超过两倍（远低于「读完整篇」的四倍）。
2. 三种行尾的文档都正确切分。
3. 既有 14 条 `safe_prefix_test` 用例全部通过——包括「切点永不落在围栏 /
   front matter / 原始文本 HTML / 数学块内部」。

|------|-------------|------|

**无锚的常见模式没有可测差别。** 带锚的那条从 1 µs 变成 6912 µs，因为它真的找到了

## FEAT-154：正则替换可以放回它捕获到的东西（`$1`、`$&`、`$$`）

| 字段 | 内容 |
|------|------|
| **实现日期** | 2026-09-12 |
| **需求描述** | 开启正则时，替换文本里的 `$1`…`$99` 展开为对应的捕获组，`$&` 为整个匹配，`$$` 为一个字面的 `$` |
| **用户场景** | 这是正则查找替换**唯一**的用途：改写形状而不是改写字符串。把 `[文字](地址)` 变成 `地址: 文字`、把 `- 项` 改成 `* 项` 而保留项的内容——原先只能一处处手工做 |
| **实现方案** | `TextSearch.expandReplacement`：拼法沿用所有其他编辑器用的 JavaScript 约定。分组是用 `matchAsPrefix` 在该位置**重新匹配一次**取得的，而不是从扫描时一路带过来——区间本就来自同一个正则，所以是同一个匹配；而替换文本里没有 `$` 时（多数情况）直接返回，一分代价不付 |
| **涉及文件** | `code/lib/services/text_search_service.dart`、`code/lib/ui/widgets/find_replace_bar.dart`（两个替换路径 + 提示）；`code/test/services/a_regex_replacement_can_use_what_it_captured_test.dart`（14 条）、`code/test/ui/widgets/the_replace_buttons_expand_groups_test.dart`（4 条） |
| **验收标准** | 开正则、查 `\[(.+?)\]\((.+?)\)`、替换为 `$2: $1`：「替换」改一处、「全部替换」改全部；字面查找时 `$1` 仍是 `$1`；`$$5` 得到 `$5`；`$5.00` 保持 `$5.00`；模式里没有的组号（如只有一组时的 `$7`）**原样保留而不是变成空** |

**几处刻意的决定**：

- **组号超出范围时原样保留**，不是悄悄变成空字符串——后者会在用户没察觉的情况下丢字。
- **捕获到空的组变成空**，因为那正是它捕获到的东西。
- **两位数字优先**：有 11 个组时 `$11` 是第 11 组；只有 1 个组时 `$11` 是第 1 组后面跟一个 `1`。
- **只在正则模式下展开**。字面查找里把 `cost` 替换成 `$5` 的人并没有要求分组。

**可发现性**：正则开启时，替换框的提示后面显示 `$1  $&`。用符号而不是句子——
一个没人找得到的能力等于没有这个能力，而在这里写一句话就是为「`$1` 在每种语言里
都一样」这件事再添第 13 份翻译。有一条测试钉住这个提示随开关出现与消失。

**接线也有测试**：服务层的 14 条只证明展开本身对，不证明按钮调用了它。
另外 4 条按下真实的「替换」与「全部替换」按钮——**两个不同的代码路径**
（一个拼接单个区间，一个从后往前拼接全部），只在其中一个里生效的 `$1`
看起来也像是生效了。三次变异各自钉住一条路径。

## FEAT-155：自动化接口的 `save_tab`

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-155 |
| 实现日期 | 2026-09-13 |
| 优先级 | P1 |
| 难易度 | 中 |
| 状态 | 已完成 |

### 需求从哪来

**不是凭空加的，是被卡住之后加的。** BUG-467 让 `close_tab` 拒绝关闭有未保存内容的
标签页，理由是「这一端没有任何东西能按下保存」。当时我在文档里写下：

> 要让自动化能收拾自己的临时标签页，正确的补法是**加一个 `save_tab` 动作**——
> 让「保存」成为那个显式决定，而不是「丢弃」。这条留给下一次。

今天连上用户的 Windows 客户端做验证，第一件事就撞上了它：新建标签页 → `set_content`
→ `close_tab` **被拒绝**（BUG-467 在真机上工作正常），于是那个临时标签页留在了用户的
编辑器里关不掉。**需求是自己撞出来的，不是想出来的。**

### 用户场景

一个自动化调用方（测试脚本、代理）要能完成一整圈：新建标签页 → 写内容 → **保存** →
关闭。缺了保存那一步，它要么丢掉写的东西，要么留下关不掉的标签页。

### 实现方案

`save_tab`，参数与其他动作一致（`tabId`，缺省为当前标签页）。

**没有加「强制丢弃」的开关**，理由与 BUG-467 一致：**能向自动化调用方索取的显式决定
是「留下它」，不是「扔掉它」**。

**保存规则收成一处**：把 `_performAutoSave` 的核心抽成 `TabNotifier.saveToDisk(id)`，
返回具名结果（`saved` / `noFile` / `nothingToWrite` / `conflict` / `failed` / `noTab`）。
自动保存把 `conflict` 变成横幅；MCP 把每一种都翻成一句读者能据以行动的话。
**这样「一次普通保存是什么」只有一份描述**——而在它存在之前，写文档的地方有六处，
正是把那六处并排比较才发现了 BUG-465（三处丢掉了实际写盘的编码）。

| 情形 | 回答 |
|------|------|
| 写成了 | `saved note.md as UTF-8`（**说出实际用的编码**） |
| 没有未保存内容 | `note.md had nothing unsaved`（不是错误） |
| 标签页没有文件 | **拒绝**——这一端没有选择框，凭空造个路径会把读者的文档放到他没选过的地方 |
| 文件在磁盘上变了 | **拒绝**——写下去就替读者决定了哪一份留下 |
| 写失败 | 拒绝并说出是哪个文件 |

### 验收标准

- [x] 写→存→关 这条循环走得通（有一条测试就叫这个名字）
- [x] **没有放松 BUG-467**：同一条测试里先断言未保存时 `close_tab` 仍被拒绝
- [x] 冲突时不覆盖，磁盘上的内容原样保留
- [x] 没有文件的标签页被拒绝，且内容仍在
- [x] 自动保存改走同一个方法后行为不变（全量 3494 通过）

### 涉及文件

- `code/lib/services/mcp_tools.dart`（枚举加一项——**加了就编译不过，直到 switch 答复它**）
- `code/lib/providers/tab_provider.dart`（`saveToDisk` + `SaveOutcome`）
- `code/lib/providers/mcp_provider.dart`
- `code/test/services/mcp_control_does_it_test.dart`（新增 5 条）

### 验证：三次变异

| 变异 | 结果 |
|------|------|
| 保存时不做冲突检查（直接覆盖） | 红 |
| 没有文件也当成功 | 红 |
| 保存后不记录已保存 | 红——**连「写→存→关」那条也一起红**，说明那条循环测的是真的 |

## FEAT-157：预览用什么字体读，现在可以选

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-157 |
| 日期 | 2026-09-13 |
| 优先级 | P2 |
| 难易度 | 低 |
| 状态 | 已完成 |

### 怎么发现的：对账 AppConfig 的 51 个字段 × 设置界面

扫「能改但没人读」和「有人读但改不了」。51 个字段全都有真读者，不在设置界面里的 7 个
都是会话/窗口状态——这一张表是干净的。

**但缓存签名那条线索没干净**：签名里有 `codeFontFamily`、`codeFontSize`、`fontSize`、
`lineHeight`，**没有 `fontFamily`**。顺着查下去，`config.fontFamily` 只出现在
源码窗格（2 处）和插件窗格（1 处）——**预览一次都没读它**，走的是主题的
`platformFontFallback`。

于是：**这个编辑器里，文档被读的那个窗格用什么字体，谁都定不了。**

而那一行设置的中文叫**「正文字体」**，日文「本文フォント」，韩文「본문 글꼴」，
代码注释写的是 "the editor's **body font**"，英文 `@description` 写的是
"the font the editor's **body text** is drawn in"。

> 正文正是在预览里读的。**那三条译文和这句英文描述，承诺的正是它不做的那一半。**

（另外 9 种语言说的是「编辑器字体」——Editor-Schriftart、Fuente del editor、
Шрифт редактора……**限定正确**，所以这不是全员译错，是三条译文越界。）

### 为什么不是「让预览听 `fontFamily` 就行了」

因为它的默认值是 `'monospace'`。让预览听它，**每一个没动过设置的读者**都会得到
等宽的散文预览——为了修一个只影响「改过设置的人」的不一致，把所有人的观感改掉。

两个设置才是对的，而且有先例：VS Code 正是 `editor.fontFamily`（源码）
与 `markdown.preview.fontFamily`（预览）两个。

### 实现方案

| 项 | 做法 |
|---|---|
| 新字段 | `previewFontFamily`，默认 **空串**＝平台默认（没动过设置的人一切不变） |
| 施加点 | 预览子树外层一个 `DefaultTextStyle.merge` |
| 为什么在外层 | 标题、表格、引用、列表标记各自建 `TextStyle` 且**都不写字体族**，一个继承点全覆盖；代码块写了自己的族，于是保持等宽——这正是分两个设置的意义 |
| 为什么 merge 不是 set | 各处样式已带 `fontFamilyFallback`，合并后仍然保留：选了一个缺字形的字体不会画成方框 |
| 空串不合并 | `TextStyle(fontFamily: '')` 会把族**设成空串**，那不等于「不管平台默认」 |
| 不进缓存签名 | 见下 |
| i18n | 新键 `settingsPreviewFontFamily` × 12 种语言；中/日/韩的 `settingsEditorFontFamily` 改为「编辑器字体 / エディターのフォント / 편집기 글꼴」；英文 `@description` 改为编辑窗格 |

### 那条守卫和它的豁免

`block_cache_signature_test` 立刻报红：**「画进块里却不在签名中」**。
它是对的形状——这个仓库为此栽过两次（reload images 无效、代码字号改了不变）。

但这一条确实不该进签名，理由写进了豁免表：

> 外层 `DefaultTextStyle`，每次 build 都重新应用；而且它是 **InheritedWidget**
> ——改了之后框架会把读过它的每个 `Text` 标脏，**缓存里那一份也一样重建**。
> 放进签名反而会为了同一幅画面丢掉并重建全部块。

这一点是**变异查出来的**：我一开始把它加进了签名，去掉签名那一条之后测试仍然全绿
（等价变异）。等价变异证伪了我写下的理由，而正确的机制比它更好。

| 代码块不写自己的族（跟着阅读字体走） | 红，「两个设置分开的意义就在这里」 |

## FEAT-158：自动化接口能把编辑器摆成要检查的那个样子

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-158 |
| 日期 | 2026-09-13 |
| 优先级 | P1 |
| 难易度 | 中 |
| 状态 | 已完成 |

### 怎么发现的：想补主题，被守卫正确地挡住

README 有一节「Where the others are ahead」，自认的四条差距里只有**主题数（32 对 8）**
是可做的，而且 MarkText 本体就在本机，可以照它真实的 CSS 移植而不是自己编配色。

但 `readme_counts_test` 要求**每个主题都得有 `picture/theme/<id>.png`**，12 份 README 都查。
截图需要运行应用并切换主题——而**自动化接口里没有改设置的动作**。于是：

- 我做不了（要么少一张图、要么削弱守卫，两条都不行）；
- 这个缺口本身比主题更值得修。

**FEAT-157 就是现成的例子**：预览字体的人工测试步骤写的是「设置里填一个字体，看预览变没变」。
测试能断言它写出的样式，**不能断言画出来的那幅画**；而我改不了设置，也就没法自己去看。
`save_tab`（FEAT-155）是同一个形状——一个以「现场没有人」为前提的接口，
偏偏缺了让它能独立验证的那一件事。

### 实现方案

| 项 | 做法 |
|---|---|
| 动作 | `set_setting`，参数 `setting`（名字）与 `value`（字符串/数字/真假） |
| 怎么按名字改 | 走 `AppConfig` 自己的 `toJson`/`fromJson` 往返——**不新增第三份字段清单** |
| 先算后写 | 先构造候选配置并校验，**通过才提交**（见下，这是我自己犯过的错） |
| 数值比较 | 数字按数字比：线路上的 `22` 落到 `double` 字段是 `22.0`，同一个答案两种写法 |
| 只动一个字段 | 写入前比对候选与当前的全部字段，别的动了就拒绝并什么都不写 |
| 答复 | 说出它**现在是什么**，调用方不必再问一次 |

### 不放行什么，和为什么

`McpSettings.notOverTheWire`，22 条，每条写了理由。分四类：

| 类 | 例 | 为什么 |
|---|---|---|
| 凭据与它发往哪里 | `aiApiKey`、`aiEndpoint`、`aiProvider`、`aiEnabled`、`aiModel` | 宿主持有密钥，永不经过这个接口；**能改端点就等于能把密钥送去别处** |
| 这次请求进来的那条连接 | `mcpEnabled`、`mcpPort`、`mcpToken` | 关掉/改端口之后**没有任何自动化能再打开它**，只有人能 |
| 记录而非设置 | `recentFiles`、`session*`、`sideBar*`、`lastUpdateCheck`、`skipVersion` | 往记录里写一个标量要么没用要么把记录写坏；`skipVersion` 还会让读者收不到某个版本的更新提示 |
| 由别人写入的状态 | `windowWidth/Height/X/Y`、`isMaximized`、`splitRatio` | 由窗口管理器和拖动写入，设它只存下一个数、什么都不动——那是编辑器说了与事实不符的话 |
| 已有另一条路 | `editMode` | `set_view_mode` 就是做这件事的，一件事两条路是这个仓库一直在删的缺陷 |

### 「拒绝名单」会失效开放，所以把字段清单钉住了

这是一份**拒绝**名单而不是放行名单，因为放行名单会落在 `AppConfig` 后面
（`toJson`/`fromJson` 已经各列了一遍，第三遍必然漂移）。

但拒绝名单**失效方向是开放的**：下个月加一个凭据字段，在没人想起来之前它是可改的。
所以 `mcp_settings_are_classified_test` 把**全部 52 个字段名钉在测试里**，
`AppConfig` 一长就红，加字段的人必须说它归哪一边——
**把「有人记得」换成「测试不给绿」。**

### 一个我自己犯的错，被测试当场抓住

第一版是**先写后校验**：`updateConfig` 之后再看值对不对。于是
`fontSize: "large"` 这种请求会——

1. `fromJson` 把它读成默认值 16，
2. **写进配置文件并保存**，
3. 然后答复「fontSize 取不了 large」。

**读者的字号被这次「被拒绝的」请求改掉了。** 比不拒绝更糟。
测试里那句 `reason: '拒绝了却已经把它写回默认值，那比不拒绝更糟'` 就是它。
改成先算候选、校验通过才提交。

### 涉及文件

- `code/lib/services/mcp_tools.dart`（动作 + `McpSettings.notOverTheWire` + schema 参数）
- `code/lib/providers/mcp_provider.dart`（`_setSetting`、`_sameSettingValue`）
- `code/test/services/a_setting_can_be_changed_over_the_wire_test.dart`（新增 12 条）
- `code/test/services/mcp_settings_are_classified_test.dart`（新增 5 条）

### 真机验证：通过（2026-09-14 17:24）

```
set_setting checkForUpdates=false → checkForUpdates is now false  （随即还原为 true）
set_setting aiApiKey=x            → 拒绝：凭据，永远不经过这个接口
set_setting mcpPort=9999          → 拒绝：换端口等于挂断，而挂断之后没人能重连
set_setting fontSize="large"      → 拒绝：it reads as 16.0 … nothing was written
```

最后一条正是这个功能里我自己犯过又修掉的那个错——**拒绝时一个字都没写进去**，
读者的字号没有被这次「被拒绝的」请求改掉。

### 验收标准

| 变异 | 结果 |
|------|------|
| 不查拒绝名单 | 红 ×3（凭据、端点、连接三条同时红） |
| 先写后校验（我原本的写法） | 红，正是「拒绝了却已经写回默认值」 |
| 数值按严格 JSON 比 | 红，`fontSize: 22` 会被当成「没取到」 |
| 从拒绝名单里删掉 `aiApiKey` | 红（分类守卫），「aiApiKey 可以被远端改写」 |

另：往枚举里加一个值就编译不过（switch 穷尽），这一条是设计使然，不是测试。

## FEAT-159：那个唯一关不掉的外连，现在可以关

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-159 |
| 日期 | 2026-09-14 |
| 优先级 | P1 |
| 难易度 | 低 |
| 状态 | 已完成 |

### 怎么发现的：反过来问「这个编辑器会连哪些主机」

BUG-483 的问法是「哪份清单在对外宣称我们的能力」。**反方向的问法是：
代码里存在、而读者可能不知道的能力有哪些？** 对一个本地编辑器，最该问的是网络。

`grep` 出 lib 里所有 `https?://` 的主机，逐个定性：

| 主机 | 什么时候连 | 读者有选择权吗 |
|------|-----------|---------------|
| `api.openai.com` / `api.anthropic.com` / `openrouter.ai` | 读者配置并使用 AI 时 | ✓ 完全主动 |
| `cdn.jsdelivr.net` | **不连**——它是导出的 HTML 文件里的链接（含数学公式时），有 `html_export_offline_test` 守着 | ✓ |
| `jira.com` | 不连，是 kanban 的示例文本 | — |
| `github.com` / `api.github.com` | **插件市场与下载**：读者主动搜索/安装时 | ✓ |
| `api.github.com` | **启动后的更新检查**：首帧之后自动发出，每 24 小时一次 | **✗ 没有任何开关** |

配置里只有 `lastUpdateCheck`（记上次什么时候查的）和 `skipVersion`（某个版本的提示别再弹）
——**都是记账，不是选择**。`skipVersion` 只让角标闭嘴，请求照发。

**而这个项目自己的姿态是相反的**：MCP 端口「默认关闭、你主动开」；插件的浏览器在权限后面、
去过哪些主机都写日志；导出的 HTML 零外链（只有数学公式那一处，且有测试钉住）。
**唯一一个读者什么都没做就发生的外连，偏偏是唯一没有选择权的那个。**

### 实现方案

| 项 | 做法 |
|---|---|
| 新字段 | `checkForUpdates`，**默认 `true`**——没动过设置的人行为完全不变 |
| 判断抽成函数 | `UpdateService.shouldCheckAutomatically({enabled, lastCheck, now})`：请求本身在测试里发不出去，**它前面的那个决定可以** |
| 顺带修正 | 时钟倒退导致 `lastCheck` 在未来时，原逻辑 `inHours < 24` 会算出负数、**跳过检查**；现在负数当作「这个戳没法用」→ 照常检查（和插件市场缓存同一个道理） |
| 界面 | 设置 → 通用，一个开关（12 种语言） |
| MCP | 可经 `set_setting` 修改（不是凭据、不是这次请求进来的那条连接）；字段清单守卫强制我对它分类 |

### 验证

| 变异 | 结果 |
|------|------|
| 忽略开关（即改动前） | 红，「关掉了还是要去连——那这个开关是装饰」 |
| 默认改成 `false` | 红（会悄悄改掉所有人的行为） |
| 不写进配置文件 | 红，「关掉之后重启又回来了，等于关不掉」 |
| 把界面里那次询问删掉 | 红（源码守卫），「读者的开关就被绕过去了」 |

最后那条是补上的：前四条测的是**函数**，而没有一条测「调用方问了它」。
守卫还断言**顺序**——先发请求再判断等于没判断。

### 留给你的一个编辑决定

README 里目前**没有**一处说「本编辑器会在启动后向 GitHub 查一次新版本」。
设置页那个开关本身是一种披露，但按 BUG-483 的教训，**读者是看 README 决定这类事的**。
要不要在 12 份 README 里加一小节「它会连哪些网络」（把上面那张表写成三四行）？
**这属于对外表述，我不替你定**——和上一轮 MCP 措辞那个问题一起等你的意见。

## FEAT-160：那个弹窗的三个答案，自动化接口现在能给全

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-160 |
| 日期 | 2026-09-14 |
| 优先级 | P1 |
| 难易度 | 低 |
| 状态 | 已完成 |

### 由用户提出

> 「你 mcp 协议应该增加对『未保存的更改』这个弹窗的控制啊！这样你就能随意关闭标签页了！」

### 现状是「三个答案只能给两个」

关一个有未保存内容的标签页，界面问的是三件事——对应 `_UnsavedChoice` 的
`cancel / discard / save`，按钮文字是**取消 / 不保存 / 保存**。

自动化接口能给出其中两个：

| 弹窗的答案 | 自动化接口 |
|-----------|-----------|
| **保存** | `save_tab`（FEAT-155） |
| **取消** | 不调用就是取消 |
| **不保存** | **给不出**——`close_tab` 直接拒绝 |

于是它自己开的草稿标签页，只能由一个坐在键盘前的人来关。
**一个以「现场没有人」为前提的接口，不该需要人来替它收拾。**

### 实现

`close_tab` 新增 `discard`——**就是那个弹窗里「不保存」的那一下**：

```
close_tab {tabId}                   → 有未保存内容时拒绝（原样）
close_tab {tabId, discard: true}    → 关掉，并说出丢了多少字符
```

**拒绝仍然是默认**，理由没变：关掉一个改过的标签页会把它的撤销历史一起带走，
之后没有任何东西能把这个决定退回来——这也正是**每一种人工关闭方式都要先问**的原因。
拒绝的话现在把**两条出路都说出来**（`save_tab` 先写盘，或 `discard: true`），
调用方不必猜。

`discard: false` 不算同意——显式传 false 是调用方在说「别丢」，和不传是同一个立场。

成功时的答复会记账：`closed tab <id>, discarding 12 unsaved characters`。
**这是这次丢弃留下的唯一记录**，所以字数必须出现在里面。

### 涉及文件

- `code/lib/services/mcp_tools.dart`（schema 里的 `discard`，说明它对应弹窗的哪一下）
- `code/lib/providers/mcp_provider.dart`
- `code/test/services/the_unsaved_question_can_be_answered_test.dart`（新增 5 条）

### 验证

| 变异 | 结果 |
|------|------|
| 无条件放行（把守卫拆了） | 红 ×2 |
| 忽略 `discard`（即改动前，永远拒绝） | 红 |
| 不说丢了多少字符 | 红，「这是它唯一留下的账」 |
| 把 `discard: false` 也当成同意 | 红 |

### 真机验证：通过（2026-09-14 17:24）

装上含这次改动的构建之后，在读者机器上完整走了一遍，**代理自己建、自己收拾**：

```
new_tab verify-160.md       → opened tab mcp-…
set_content "twelve chars"  → wrote 12 characters
close_tab                   → not while "verify-160.md" has unsaved work —
                              save_tab writes it first, or pass discard: true
                              to answer the "Don't save" the reader would be asked
close_tab {discard: true}   → closed tab mcp-…, discarding 12 unsaved characters
get_state                   → 只剩读者自己的那份文档
```

拒绝说出了两条出路，丢弃说出了丢掉多少，**并且它把自己开的草稿收拾干净了**
——这正是这个功能存在的理由。

### 一个诚实的限制：它救不了眼前这一次

真机上装着的构建**早于这个改动**（也早于 `save_tab` 和 BUG-474），所以挡在
`update_app` 前面的那个草稿标签页，**这一次仍然需要一个人来处理**。两种做法都只要一步：

- 在它的 × 上点一下、选「不保存」；**或者**
- **退出应用再打开**——会话只持久化**有文件路径**的标签页
  （`_persistSession` 里 `whereType<String>()` 把 null 滤掉了），所以那个无路径的草稿不会回来。

装上含这次改动的构建之后，**这类死锁不会再出现**。

## FEAT-161：`get_state` 说出自己是哪个版本

### 需求描述

`get_state` 在报「有哪些标签页、哪个在前台、占了多少内存、装了哪些插件、
插件的版本是多少」——**唯独不报编辑器自己的版本**。

### 用户场景

自更新（BUG-484 之后）终于能完整跑通：装 → 编辑器自己回来。
**但接下来那个问题在协议里没有答案：回来的是哪个？**

2026-09-14 那次验证是这么做的：SSH 不上去，于是靠**读 Windows 上安装程序自己的日志文件**，

这不是协议提供的能力，换一台机器、换一个代理都做不到。

{ "version": "1.6.2", "viewMode": "preview", ... }

（见 BUG-485——上一次不同源的后果）。

工具描述同步改了：`get_state` 的说明现在以 `"version"` 开头，
并明确写出它的用法——**`update_app` 跑完、编辑器回来之后问它**。
（对外的清单和实现的清单必须是同一份，这是本版本反复踩到的那类缺陷。）

### 验收标准

1. `get_state` 的 `version` 等于 `AppConstants.appVersion`；
2. 且不等于 `dev`——区分「它报的是常量」与「常量本身就是占位符」；
3. 工具描述里写明这个字段与它的用途。

### 涉及文件

- `code/lib/providers/mcp_provider.dart`
- `code/lib/services/mcp_tools.dart`
- `code/test/services/mcp_state_is_true_test.dart`

## FEAT-162：关错了可以拿回来

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-162 |
| 实现日期 | 2026-09-14 |
| 优先级 | P2 |
| 难易度 | 中 |
| 状态 | 已完成 |

### 需求描述

关掉一个标签页之后没有任何办法把它拿回来。浏览器、VS Code、IDEA 全都有这个动作，
这个编辑器没有——要么回侧栏里找那个文件，要么指望它还在「最近文件」里，
要么在打开对话框里把路径敲一遍。

### 用户场景

- 点错了 `×`；
- 用了「关闭其他」「关闭右侧」，多关了一个；
- 自动化接口（MCP）用 `discard: true` 把一个标签页丢掉之后想反悔。

### 实现方案

**记的是路径，不是正文。** 留住最近十个已关文档的文本，会直接推翻这个编辑器
关于内存的主张（已量到：每个渲染块约 63 KB）；而重新打开本来就该显示磁盘上的那一份
——`discard`（「不保存」）留在磁盘上的也正是那一份。

**没存过盘的标签页不记。** 它没有路径，而关掉一个改过的标签页本来就会先问，
所以「不保存」是一个决定，不是手滑。

**记录挂在 `TabNotifier` 对 `state` setter 的覆写上**，和撤销栈的释放、
磁盘监听的同步放在一起，理由也写在那里：**关标签页有六条路，它们只共用这一个窄口。**
（这一条是本库反复验证过的做法——守卫防漏，窄口让漏不可能。）

其他细节：

| 决定 | 理由 |
|------|------|
| 上限 10 条 | 会话没有上限。每条都很小，而「每条都很小」正是这类清单不设限的那个理由 |
| 同一个文件只留一条 | 否则连着关两次同一个文件，按两次才退得过去 |
| 一次关多个时，最右边的先回来 | 就是它们会被依次拿回来的顺序 |
| 回到**原来的位置**，不是追加到末尾 | `addTab` 收了一个可选的 `at:` |
| 读不到（被删/被移走）就**丢掉这一条** | 否则它会永远占着第一位，前面那些永远够不着 |
| **没加载完的标签页不算被关闭** | 会话恢复把每个标签页先建成空的、标为 loading，再逐个读；读不出来的那个会被丢掉，而那一步和「关闭」走的是同一个窄口。不排除的话，编辑器会提出把一份**读者根本没关过、而且读不出来**的文档拿回来。**这是窄口做法的代价**：窄口看得见「有个标签页消失了」，看不见「为什么消失」，所以规则要挂在标签页自己的属性上（`isLoading`）|
| 读者**自己删掉**的文件仍然会进清单 | 它加载完过，`isLoading` 区分不了。按一次会被明确拒绝（答复里有文件名）并就此丢掉，是自愈的。**刻意不在关闭路径上加一次 `existsSync`**——为了一个自愈的小瑕疵给「关闭」加一次文件系统调用，对一个卖速度的编辑器是错的交易 |

### 入口（四个）

| 入口 | 说明 |
|------|------|
| 快捷键 | **Ctrl+Alt+R**。**不是** Ctrl+Shift+T——那个键在这里是任务列表（沿用上游），而快捷键表里那句「不改任何人的习惯」对它同样成立。也**不是**关闭键加修饰键：`Ctrl` 在 macOS 上读作 Command，`Ctrl+Alt+W` 到那边就成了 `Cmd+Option+W`，而那是系统级的「关闭全部窗口」 |

菜单栏常驻，而标签页列表每敲一个字就变一次。

## FEAT-163：窗口可以从外面驱动了

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-163 |
| 实现日期 | 2026-09-15 |
| 优先级 | P1 |
| 难易度 | 中 |
| 状态 | 已完成 |

### 需求描述

> 「mcp 还要支持控制客户端的窗口大小、最大化、最小化」

这条要求**从一开始就在**，而一直没有做。读者整天盯着的那一样东西——窗口本身
——恰好是自动化唯一碰不到的。

### 用户场景

两个，第二个是当下的关键：

1. 代理需要把窗口摆成某个样子再截图（比较布局、录动图）；
2. **人工测试清单里有两条是「把窗口从 1200 拖到 700 再拖到 400，看有没有黄黑条纹」**
   （BUG-479 / BUG-480）。`screenshot` 早就是那只眼睛，缺的是那只手。
   没有这只手，这一版就只能等人坐下来。

### 实现方案

新增动作 `set_window`，参数：

| 参数 | 说明 |
|------|------|
| `state` | `normal` / `maximized` / `minimized` / `fullscreen`（枚举，可选） |
| `width` + `height` | 逻辑像素，**必须成对**（可选） |

几条决定，都写进了代码注释：

- **答复报的是量到的，不是要求的。** 窗口管理器会把尺寸夹到工作区和窗口自身的下限，
  所以「要求的」和「结果的」是两个数——说前者就是这个编辑器在描述一个不存在的窗口。
  实现里是 `await window.read()` 之后再拼答复。
- **先改状态，再改尺寸。** 最大化的窗口会忽略 resize，所以后说的那句必须是落地的那句。
  `resize` 本身也会先取消最大化/全屏，否则同样是在描述一个没动过的窗口。
- **尺寸下限复用 `WindowPlacement.minimumSize`**（480×320），理由也是它那句：
  再小标题栏就抓不稳，而这一端没有任何办法把一个抓不住的窗口还给读者。
- **半个尺寸不是尺寸**：只给 `width` 被拒绝，不去猜另一半。
- **`minimized` 会让 `screenshot` 拍到空的**，这一点写在参数说明里——
  换任何别的状态都能回来。

为了能在没有平台通道的 `flutter test` 里跑，窗口操作收在 `EditorWindow` 接口后面
（`lib/services/editor_window.dart`），真实实现只做转发、不含判断，
所有值得测的逻辑都在调用方。

### 验收标准

1. 四种状态各自生效，答复说出它变成了什么；
2. 不认识的状态被拒绝**并列出四个取值**（由昨天那条 schema 驱动的守卫强制）；
3. 尺寸成对才接受，低于 480×320 被拒绝**且拒绝之前没有改动**；
4. 答复里的尺寸是**量到的**，不是要求的；
5. 状态与尺寸同时给时，尺寸是最后落地的那个；
6. 12 份 README 的动作清单与散文都提到它，且**那个数目是对的**（见 BUG-493）。

## FEAT-164：机器也能在文档上动手了

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-164 |
| 实现日期 | 2026-09-16 |
| 优先级 | P1 |
| 难易度 | 中 |
| 状态 | 已完成 |

### 需求描述

人工测试清单里剩下的那几条，卡的都不是「看不见」，而是**手伸不进去**：

| 清单上的步骤 | 缺的动作 |
|---|---|
| 「Ctrl+B 两次，然后 Ctrl+Z 应当只退掉第二个」（BUG-482） | 跑格式命令、退历史 |
| 「从浏览器复制带标题和列表的网页，用编辑 → 粘贴」（BUG-481） | 往剪贴板放 **HTML** |
| 「打一串字后立刻用菜单撤销，重做应当把字拿回来」（BUG-494） | 退历史、重做 |

四个动作补齐这三样：`format`、`undo`、`redo`、`set_clipboard`。

### 实现方案

**`format`**：54 个命令，取值从 `FormatAction.values` 生成。走的是**菜单和键盘
走的同一条路**（`applyFormat`），不是为自动化另写一条。

这里最要紧的不是「做」，是**「没做就不许说做了」**：

- `applyFormat` 只是**记下一个请求**，由某个窗格在下一帧接手。所以答复前要**等**
  请求被清掉（条件轮询，不是固定 sleep），清掉了才算做了，并报出文档字数的变化。
- 纯预览且没有块在编辑时，**没有任何窗格会接**——这时直接拒绝，并说清怎么办
  （`set_view_mode` 到 source 或 split）。判断向 `FormatTarget` 要，不自己抄一份。
- 等不到就**把请求丢掉**再拒绝。留在那里的话，它会在读者下次切到源码模式的瞬间
  自己触发——一次没人要求、时间也没人选的编辑。

**`undo` / `redo`**：走 `TabNotifier.stepHistory`，**和「编辑 → 撤销」同一个方法**
（这一条是 BUG-494 的结果：那两条路曾经是两份代码，其中一份用了滞后的文本）。
没得退时说「there is nothing to undo」，不假报成功。

**`set_clipboard`**：`content` 放纯文本，`html` 放浏览器会一并留下的那一份。
复用已有的 `ClipboardService.copyWithHtml`——**没有新依赖**，走的正是
「复制为 HTML」用的那条路。而这一份 HTML 正是编辑器粘贴时**先读**的那一份，
所以「从浏览器复制」这件事终于可以在没有浏览器的情况下造出来。

**它换掉的是读者真实的剪贴板**，所以答复里明写「whatever was on it is gone」，
参数说明里也写了。

### 验收标准

1. 预览且无块编辑时 `format` 被拒绝，**且不留下将来会自己触发的请求**；
2. 预览里有块在编辑时**不拒绝**（那一半也要对）；
3. 被接手时报出文档字数的变化；等不到时**丢掉请求**再拒绝；
4. `undo` / `redo` 与菜单同路；没得退时明确说没得退；
5. `set_clipboard` 带 `html` 时走 `copyWithHtml`，不带时走纯文本，两者答复不同；
6. 12 份 README 的动作清单与数目都跟上（数目现在有守卫）。

### 守卫与变异验证

`the_editor_can_be_typed_at_over_the_wire_test`，11 条。**七处变异逐个验证会红**：
去掉「没人接就拒绝」、超时后不清请求、不等就报成功、撤销不区分「没得退」、
忽略 `html`，以及后两条重做过一次——第一次改出的是**编译错误**，
那不算行为失败（这条纪律本仓库记过）。

  它原地改为转发，原有测试不动）

## FEAT-166：让「卡」变成一个能读到的数

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-166 |
| 实现日期 | 2026-09-24 |
| 优先级 | P1 |
| 难易度 | 低 |
| 状态 | 已完成 |

### 需求描述

读者报「打开第二个文件严重卡顿」（BUG-497）。修掉机制那一半之后再量，
剩下的部分**查不下去了**，原因很具体：

| 被计时的东西 | 数值 |
|---|---|
| 预览重画（渲染器自报） | 244 / 248 / 239 / 250 / 320 ms —— **很稳定** |
| 解析（注释里有实测） | 每块 0.02–0.04 ms，800 块约 24 ms |
| 切标签页往返（我从外面量） | 69 / 430 / 78 / 58 / 85 / **1153** ms |

**那一秒既不在重画里，也不在解析里。** 这个编辑器里每样东西都在给**自己的工作**
计时，而卡顿按定义就是**没人计时的那一段**——所以日志里每个数都好看，读者却在卡。

### 实现方案

引擎知道每一帧花了多久（`SchedulerBinding.addTimingsCallback`）。
问它，并且**只在一帧慢到看得见时才说话**。

| 决定 | 理由 |
|------|------|
| 门槛 100 ms | 一帧本该 16 ms；16 不是卡，40 也不是；**十分之一秒是读者开始怀疑窗口没在听他说话的地方** |
| 构建与光栅化**分开报** | 它们是两种毛病：一个是这个编辑器干活太多，一个是画面本身太贵 |
| 一阵卡顿只报一行，并说出**压下了多少帧** | 卡顿不是一帧，是一串；补画一篇大文档会产生几百帧，一帧一行会把日志里其余五百行全挤掉 |
| 时间戳用**引擎自己的**，不读时钟 | 每帧都要判断「离上次多久」，为此每帧读一次时钟是自找的开销 |
| 引擎时间**倒退**时照报 | 那是时基重启，不是「刚报过」；否则它会等一个永不到来的时刻，从此沉默 |

判断逻辑与 Flutter 无关（`SlowFrames`），所以不需要一帧就能测。

### 验收标准

1. 16 ms 的帧不产生日志；400 ms 的帧产生一行，**分别说出构建与光栅化**；
2. 一串慢帧只有一行，并说出压下了多少；
3. **报过的计数不再报第二次**；
4. 引擎时间倒退时不会从此沉默。

### 守卫与变异验证

`slow_frames_test`，6 条。**四处变异**：去掉限流、去掉时间倒退的保护、
把门槛降到 1 ms、不清零被压下的计数。

最后一处**第一次全过**——因为清零只在**第三次上报**时才看得出区别
（报过「还有 19 帧」之后，下一次孤立的慢帧不该再声称那 19 帧）。
补上那个场景之后才咬住。这正是「加一轮测试 ≠ 那一轮走进了要测的路」。

## FEAT-167：关闭也开始自报耗时

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-167 |
| 实现日期 | 2026-09-24 |
| 优先级 | P1 |
| 难易度 | 低 |
| 状态 | 已完成（Dart 侧本机已测，runner 侧由 CI 编译、行为待真机） |

### 需求描述

读者第二次说「关闭应用窗口还是很慢，严重卡顿」。而手上所有证据都说它很快：

| 证据 | 数值 |
|---|---|
| 追踪：`close requested` → `window destroyed` | **35 / 28 / 17 ms** |
| 关闭看门狗（`destroy()` 挂住时每 100 ms 写一行） | **一行都没写过** |
| 退出后的拖尾 | 早先已用 `ExitProcess` 绕开（见 main.cpp 注释） |
| `window_manager` 原生侧收到 WM_CLOSE 后做的事 | 发个事件给 Dart，返回 -1。**没有慢活** |

**每一段被计时的都很快，而读者在等几秒。** 那几秒只可能在两段没人计时的地方：

1. **「点下 ×」→「Dart 收到消息」**（消息在途，或 UI 线程忙得没去取）；
2. **「窗口消失」→「进程真的没了」**（Windows 收尾）。

### 实现方案

**四个数，不是两个。** 让读者关一次窗口要占用他一次操作，答案不该还需要第二次。
四个数把关闭切成三段，而这三段各有不同的修法：

| 段 | 从哪到哪 | 慢在这里意味着 |
|---|---|---|
| 按钮等着被听见 | 消息被投递 → 被处理 | UI 线程忙着，窗口在原地不响应（`setPreventClose(true)`，Dart 不答就不关） |
| 编辑器自己的活 | WM_CLOSE → WM_DESTROY | 追问未保存、存窗口几何、停文件监视、destroy |
| 走完最后一段 | WM_DESTROY → 最后一条指令 | 消息循环收尾 |
| （落在四个数之外） | 最后一条指令之后 | Windows 拆进程：DLL 卸载钩子、200MB 工作集 |

**记的是最后一次 WM_CLOSE，不是第一次。** 第一版写的是「只记第一次」，
理由「被拒绝的关闭后面还会有一次，第一次才是读者按下按钮的时刻」听着站得住，
其实只对它自己那一层成立：关闭可以被拒绝（有未保存内容 → 弹窗 → 读者点取消），
若他五分钟后再关，从第一次算就把这五分钟的**思考**记进了「编辑器自己的活」，
而读到这行数的人会跑去一个根本不干活的处理器里找那五分钟。
「只记第一次」原本要照顾的场景——读者见没反应连点两下——并没有丢：
两次点击都卡在同一段冻结里，第二次报出的队列等待同样看得见。

**仍有一处这边看不出来的**：弹窗那条路上只有一次 WM_CLOSE，读者作答的时间
夹在里面，从 runner 看就是「编辑器自己的活」。追踪分得出（弹窗后的几何保存
标记不同名），所以读到惊人的数字先去对追踪，别追一段属于对话框的分钟数。

**「按钮等着被听见」这一段要靠 Windows 自己记的东西**：`GetMessageTime()` 给出
当前这条消息被投递的时刻，与 `GetTickCount()` 相减就是它在队列里坐了多久。
因此这个取值**必须待在窗口过程调用的那个函数体内**——挪到别处它照样返回一个数，
但那个数说的是另一条消息，而那种错误没人看得出来（已写守卫，见下）。

三个测点都在 runner 里，因为只有它同时看得见这几端：

- `FlutterWindow::MessageHandler` 里，**在交给 Flutter 之前**记下 `WM_CLOSE` 到达的时刻
  与它在队列里等的时长（`window_manager` 会把这条消息挡下来转给 Dart，所以之后再记就晚了）；
- 同一个处理器里记下 `WM_DESTROY`——它是「编辑器在做事」与「进程只是在退出」的分界；
- `ExitProcess` 前一行记下最后时刻，四个数写到 exe 旁边的 `last-exit.log`
  ——那个目录启动追踪已经在写，已知可写。

下次启动 Dart 读出来、写进日志、**然后删掉**（留着的话，此后每次启动都会把同一次关闭当成刚发生的来报）。

进程计时器从 `main.cpp` 搬进了 `utils`：窗口过程也要用它，而复制第二份正是这个仓库一直在删的毛病。

### 这个数会直接指出该修哪一半

| 哪一段是秒 | 该修哪儿 |
|---|---|
| 按钮等着被听见 | UI 线程在关闭那一刻被占着——去查那时在跑什么（慢帧已由 FEAT-166 自报） |
| 编辑器自己的活 | 在 `onWindowClose` 里，Dart 可测可改 |
| 走完最后一段 | 消息循环收尾 |
| **三段都是几十毫秒** | 慢在四个数之外：Windows 拆进程。`ExitProcess` 仍会执行每个 DLL 的卸载钩子，`TerminateProcess` 不会——那才是下一步要试的，但**先量再改** |

### 验收标准

1. 正常关闭后，下次启动日志里有一行说出耗时；
2. **不是关窗口引起的退出**（例如被更新替换）要明说，而**不报任何时长**
   ——那种情况唯一能算的时长是整个运行时长，不是任何人想知道的；
3. 读不懂的内容**放过**，不猜；「队列等待不可信」与「没等」要区分：前者不报这一句，
   **不许当零报**；窗口没被销毁过时三段**不许硬拆**，宁可合成一段；
4. 时长为负（时基异常）**不报**，因为那看起来会像是编辑器的毛病；
5. 读一次就删。

### 守卫与变异验证

**Dart 侧**：`last_exit_test`，4 条，**三处变异**：不检查倒着的时长、
把「没关过窗口」当成一次关闭来算、读不懂也硬给答案。

**runner 侧**：`the_close_is_timed_at_both_ends_test`，4 条。runner 在本机编译不了，
CI 只证明它能编译——**而第一版改动编译完美、什么也没记下来**：
调用落进了「第二次启动把路径转发给正在运行的编辑器」那条分支，
那个进程从来没有窗口、也从来没被要求关闭过。这正是本库最常见的缺陷形状
（写好了却没接上），编译器看不见，所以由这四条断言代替它：

| 断言 | 变异 | 结果 |
|------|------|------|
| 点击在交给 Flutter **之前**被记下 | 删掉 `if (message == WM_CLOSE)` 块 | 红 |
| 记录接在**真正的**最后一条指令前 | 把调用放回转发分支（即真实犯过的错） | **红 2 条** |
| 测量与退出之间不许有别的语句 | 中间插一句 `CoUninitialize()` | 红 |
| 两端读同一个时钟 | 让 main.cpp 再定义一份 | 红 |
| **runner 写的标签＝Dart 读的标签** | 把 `destroyed-ms=` 改名 | 红 |
| WM_DESTROY 也被记下 | 删掉那个块 | 红 |
| 队列等待取在窗口过程调用的函数体内 | 挪到读取函数里去算 | 红 |
| **报的是结束进程的那次关闭** | 改回「只记第一次」 | 红 |
| **两边对这个文件叫什么名字说法一致** | 只改 C++ 那边的名字 | 红 |

第三条不是洁癖：这个数的全部价值在于「它没算进去的，读者也不会再等」，
中间插进任何一句话，它就不再是那个意思了。

倒数第三条是这次最该有的那一条：**一行数据的两端在两种语言里，中间没有编译器
对账**。runner 写了却没人读的标签＝白测一次；Dart 找而 runner 不写的标签＝
句子里静静少一段。这正是本库反复命中的形状，所以测试从两个文件里把标签抽出来
直接比集合，差额写进失败信息。

Dart 侧三处新变异也都咬住：不知道也当零报、没销毁也硬拆、报原始数字而非差值。

**读取端也补了测试。** 原先只测了「那句话怎么说」，而那不是会找错地方、找错名字的
那一半：`readAndForget` 现在接一个 `@visibleForTesting` 的目录，四条测试覆盖
读出来、读完删掉、读不懂也要删掉（否则这个文件会被每次启动读一遍、跳过一遍，
直到这台机器上的安装被删）、以及什么都没有时什么都不说。

**「没有那一行」曾经是三件事**（runner 没写成 / Dart 没读到 / 根本没关过窗口）。
现在 Windows 上找不到文件会写一句 debug，把第一种分出来——这不是假想：
安装器允许装到机器级目录，那里运行中的程序写不进去。

第二条测试的断言我写坏过一次——原本查 `contains('not')`，那是「说清楚了」的代用品
而不是它本身；改成查「without the window being closed」并**要求不含任何时长**之后才算数。
