## FEAT-077：构件互不干扰

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-01 |
| 需求描述 | 把「一种构件不得被旁边的构件弄坏」这条性质做成可执行的测试 |
| 用户场景 | 真实文档从来不是单一构件。BUG-215（引用块之后所有引用式链接失效）就是这么产生的，而规范语料完全抓不到 |
| 优先级 | P2 |
| 难易度 | 低 |

### 缘由

BUG-215 的教训：**CommonMark 语料每个例子只有一种构件**，
解析器可以全部通过，而把两种构件放进同一篇文档就出错。
那个 bug 修复前后规范分数都是 493，纹丝不动——语料里没有一个例子同时含有
引用块和引用式链接。

### 实现方案

19 种构件，每种给出「源码」和「输出里必须出现的特征」。
遍历**全部三元有序组合**（5814 种），拼成文档解析导出，
断言三种构件的特征都还在。

**特征刻意取得宽松**——取构件承载的文字，而不是精确的标签。
两个相邻列表会合并成一个松散列表（这是正确行为），
条目于是从 `<li>x</li>` 变成 `<li><p>x</p></li>`；
特征写死成前者就会在**正确的输出**上误报。

**前置元数据单独验**：它只有在文件最开头才成立，
放进遍历会产生 19 条假阳性。另外补了一条反向断言——
写在文档中间的 `---\ntitle: 甲\n---` **不应该**被当成前置元数据。

### 验收标准

- 5814 个三元组合全部通过
- 撤掉 BUG-215 的修复后，这条测试必须失败（实测 147 个组合报错）
- 单次运行 < 10 秒（实测 7.7 秒）

### 本轮的排查结论

- 全部三元组合**零失败**，构件互扰这一维度目前是干净的
- 顺带核对了解析器的可变实例状态：只有 `_linkDefinitions` 与 `_parseDepth` 两个，
  都已在 BUG-215 中处理，没有第二处会被嵌套解析破坏的状态

### 涉及文件

- `code/test/services/constructs_do_not_interfere_test.dart`（新增，3 条测试 / 5814 个组合）

## FEAT-078：导出的过程与结果都要说出来

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-01 |
| 需求描述 | 导出进行时告诉用户在忙什么，完成后告诉用户文件写到了哪里 |
| 用户场景 | 选完文件名之后，窗口静默冻住几秒，然后什么也没发生——文件其实已经写好了，但用户无从判断 |
| 优先级 | P2 |
| 难易度 | 低 |

### 缘由

本轮在核对「支持大文件」时量了导出的耗时：

| 文档 | HTML | PDF | Word |
|---|---|---|---|
| 6 K 字符 | 173 ms | 720 ms | 128 ms |
| 28 K 字符 | 93 ms | 1003 ms | 226 ms |
| 117 K 字符 | 225 ms | **3043 ms** | 546 ms |

PDF 大致线性增长，外推到 1 MB 约 26 秒。查代码发现：
**失败会弹提示，成功什么也不说，过程中也没有任何进度指示。**
于是大文档导出时，用户看到的就是一个毫无解释的假死窗口。

### 实现方案

`runExport(fileName, work)`：显示一个不可关闭的模态提示 →
让出一帧确保它先画出来 → 执行导出 → 关闭提示 →
成功弹「已导出到 xxx」，失败走原有的失败提示。
HTML / PDF / Word 三个入口统一改为委托给它。

**当时的局限（已在 FEAT-079 解除）**：PDF 导出的繁重部分跑在主 isolate 上，
转圈动画在那段时间里不会转，所以这个改动给到的只是
「一个说明自己在忙什么的窗口」。同一天的 FEAT-079 把 PDF 排版移进了独立
isolate，转圈现在真的会转。

### 一条守卫测试的调整

既有的 `export_failure_test` 用源码扫描保证「导出处理器必须捕获异常」，
它检查的是**机制**（函数体里要有 `try` 和 `reportExportFailure`），
改成委托后这条就失败了。

按**意图**重写：本地捕获**或**委托给 `runExport` 都算合格。
但这样会开一个口子——万一委托目标什么都不做呢？
所以**同时补了一条测试，验证 `runExport` 确实上报失败、也确实说明去向**。
没有这条，放宽就成了漏洞。

### 验收标准

- 三个导出入口都经由 `runExport`
- 12 种语言都有「正在导出…」与「已导出到 {file}」，且后者带上文件名
- 守卫测试仍然能挡住「新增一个不报告失败的导出入口」

### 涉及文件

- `code/lib/app.dart`、`code/lib/ui/widgets/app_menu_bar.dart`
- `code/lib/core/i18n/l10n/app_*.arb`（12 种语言）及生成代码
- `code/test/ui/widgets/export_failure_test.dart`（守卫改按意图检查，新增 2 条）

## FEAT-079：PDF 排版移出主 isolate

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-01 |
| 需求描述 | PDF 导出不得占住窗口线程 |
| 用户场景 | 一份 117 KB 的文档导出 PDF 要 3 秒，1 MB 外推约 26 秒——这段时间窗口完全冻住 |
| 优先级 | P2 |
| 难易度 | 中 |

### 缘由

FEAT-078 加了「正在导出…」的提示，但当时就写明了它的局限：
**PDF 的繁重部分跑在主 isolate 上，转圈动画根本不会转**，
所以那只是「一个说明自己在忙什么的窗口」，不是不卡的窗口。

本轮先验证真正的修法可不可行——**不预设结论，直接把 `pdfBytes` 丢进
`Isolate.run` 跑一次**：

- 能跑通，输出**字节级一致**
- 预热后的公平对比：**独立 isolate 反而更快**（383–456 ms vs 646–674 ms）

所以这不是「用速度换流畅」的取舍，两边都赢。之所以更快，
大概是新 isolate 有干净的新生代堆。

### 实现方案

`pdfBytes` 改为先走 `Isolate.run`，失败则回退到本地计算
（与预览的完整解析同一模式）。原有实现原样保留为 `_pdfBytesHere`，
既给 isolate 提供可执行的目标，也给回退提供落点。

一切输入本就可跨 isolate 传递：markdown 字符串、Mermaid 图片字节、
源文件路径、HTML 开关；返回的是字节。

**回退不会吞掉真实错误**：真正排不出来的文档会在本地重跑时再抛一次，
调用方照样看得到。代价是失败时多做一遍，可以接受。

### 验证

新增 2 条。**断言的不是「用没用 isolate」这个实现细节，
而是用户真正在乎的事：导出期间事件循环还在转。**
用 5 毫秒一次的心跳计数：

| | 用时 | 心跳 |
|---|---|---|
| 走 isolate | 506 ms | **99** |
| 纯等待 500 ms（对照） | 501 ms | 99 |
| 不走 isolate | 683 ms | **0** |

阈值取 20，离两侧都极远。破坏验证时失败信息直接报「心跳 0 次」。

第二条断言字节数不变——isolate 只改变在哪里排版，不改变排出什么。

### 未做的部分

Word 导出（117 KB 约 546 ms）与 HTML（约 225 ms）没有一并改。
它们比 PDF 快一个数量级，收益远小于风险，等有需要再说。

### 涉及文件

- `code/lib/services/export_service.dart`
- `code/test/services/pdf_off_main_isolate_test.dart`（新增，2 条）

## FEAT-080：分屏模式下预览跟随源码区滚动

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-01 |
| 需求描述 | 滚动源码区时，预览滚到对应位置 |
| 用户场景 | **分屏模式此前完全没有滚动同步**——滚动源码区，预览纹丝不动。而"两边看同一处"正是分屏存在的意义 |
| 优先级 | P1 |
| 难易度 | 中 |

### 缺口

查证过程：`split_editor.dart` 里没有任何 scroll 相关代码，
预览的 `SingleChildScrollView` 连滚动控制器都没有，
`editorProvider` 里只有一次性的 `targetScrollLine`（大纲/搜索用）。
**确实是零同步。** VS Code、上游 MarkText、Obsidian、Zettlr 都有这个功能。

### 实现方案

**源码区一侧**：`_onEditorScroll` 里算出视口顶端是第几行。
用的是 `RenderEditable.getPositionForPoint` —— 不是「偏移量 ÷ 行高」，
因为只要有一行换行那个式子就不成立（BUG-211 就是栽在这上面）。
这套能力上一轮做行号对齐时已经具备，直接复用。

**预览一侧**：按**标题锚点**定位，并在两个标题之间做线性插值。

为什么不按比例（源码滚动百分比 → 预览滚动百分比）：
**两边的高度根本不是一回事**。一段 HTML 注释在源码里占四十行、
在预览里占零高度；一张图表是几行源码、半屏图画。按比例会落到离
用户正在写的那句话很远的地方。插值保证在同一节内也是平滑移动，
而不是只在跨过标题时才跳一下。

**只在分屏时生效**：两侧各有一个开关参数
（`reportsScrollPosition` / `followsSource`），单开预览或单开源码时不做任何事。

目前是**单向**的（源码 → 预览）。双向需要处理反馈回环，留作后续。

### 验证

新增 4 条。**关键是第三条**：

前两条（预览跟着动了、落到了正确的小节）我先写完，
然后做破坏验证——去掉同步，两条都失败 ✅；
**但把实现换成"按比例同步"，两条却都通过了**。
合成文档各节高度均匀，两种做法结果差不多，
**这说明这两条断言区分不了我实际做的设计选择，等于没测到重点**。

于是补了第三条：文档里放一段 40 行的 HTML 注释
（源码占位、预览零高度）。按比例同步会把预览滚过头
——破坏验证时实测标题被顶到 y = -533，测试正确失败。

第四条护栏：单开预览时不去追一个不存在的面板。

### 涉及文件

- `code/lib/providers/editor_provider.dart`（新增 `syncSourceLine`）
- `code/lib/ui/editor/source_editor.dart`、`code/lib/ui/editor/markdown_renderer.dart`、
  `code/lib/ui/editor/split_editor.dart`
- `code/test/ui/editor/split_scroll_sync_test.dart`（新增，4 条）

## FEAT-081：分屏滚动同步做成双向

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-01 |
| 需求描述 | 滚动预览时，源码区也跟到对应位置 |
| 用户场景 | 预览是用来读的那一侧，在那边滚动是常态。FEAT-080 只做了源码→预览一个方向 |
| 优先级 | P1 |
| 难易度 | 中 |

### 实现方案

新增 `syncPreviewLine` 通道（与 `syncSourceLine` 方向相反）：

- **预览侧**：滚动时反解出顶端对应的源码行——
  `_contentOffsetForLine` 的逆运算（找到已滚过的那个标题，
  再按在该节中的进度换算回行号）。
- **源码侧**：收到行号后，用 `getLocalRectForCaret(行首)` 求出该行的真实位置，
  换算成滚动偏移。同样不用「行号 × 行高」——换行会让那个式子失效。

**防回环**：任一侧被程序移动时打一个时间戳，
自己的滚动监听在 200 毫秒内看到该戳就不再上报。
谁在被用户滚动，谁就是驱动方。

### 这一轮最值得记的：一条自称在测试抑制、实则没测到的测试

我先加了抑制，也顺手写了一条「两边不会互相追」的测试。做破坏验证时：

1. **去掉反向同步** → 对应测试失败 ✅
2. **去掉防回环抑制** → **全部测试照样通过** ❌

也就是说那条测试**根本没测到抑制**。原因是：驱动预览时，
「行号 → 位置 → 行号」的往返是稳定不动点，即使互相回声也会立刻收敛，
表面上看不出任何异常。

于是我进一步追问：**这个抑制到底有没有必要？**（不排除是我加的多余复杂度。）
逐个构造不对称场景，最终在**驱动源码区滚到底、而预览已被钳制**时找到了：
两侧互相推挤**永不收敛**，测试直接挂死超时。

所以抑制是必需的，而原来那条测试的驱动方向选错了。
改为驱动**源码区**依次走 40% / 80% / 98% / 100%，
每个位置先记下两侧偏移、再泵 30 帧，断言不得自行移动。

**失败模式是挂起而不是断言失败**——这一点写进了测试注释，
免得将来有人看到超时以为是环境问题。

### 涉及文件

- `code/lib/providers/editor_provider.dart`（新增 `syncPreviewLine`）
- `code/lib/ui/editor/source_editor.dart`、`code/lib/ui/editor/markdown_renderer.dart`

## FEAT-083：启动耗时实测入表，并把窗口显示阶段拆细

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-01 |
| 需求描述 | 对比表补上启动耗时；顺带查清一处偶发的启动停顿 |
| 优先级 | P2 |
| 难易度 | 低 |

### 数据来源

用户提供了 Typora 与 MarkText 的手测值（同一台机器，2~3 秒），
并给出了本项目 `startup-trace.log` 里的**四次真实启动记录**。

**这份数据推翻了我此前的判断**：我先前依据 `docs/v1.4.0` 的旧记录
（「创建视图」约 2250 ms）推断本项目也在 2 秒区间，因而拒绝写这一行。
实测显示那之后的优化（AOT 快照瘦身、砍掉 135 种用不上的高亮语言）确实见效，
「创建视图」已降到 278–673 ms。**旧数据当成现状用，会得出相反的结论。**

### 换算方式（容易算错的一点）

追踪日志有**两段时钟**：Dart 之前的部分是「进程创建以来的毫秒数」，
到 `first Dart mark` 之后**重新从 0 开始**。所以总耗时要相加：

| 启动 | Dart 前 | 文档画出 | **合计** |
|---|---|---|---|
| 08-31 09:19 | 1022 | +314 | 1336 ms |
| 08-31 09:32 | 1118 | +293 | 1411 ms |
| 09-01 09:55 | 461 | +234 | 695 ms |
| 09-01 09:56 | 528 | +159 | 687 ms |

**热启动约 0.7 秒、冷启动约 1.4 秒**（差异全在 Windows 的文件缓存上）。
其中本项目自己的 Dart 代码只占 60–320 ms，
其余是 Windows 加载 DLL + 引擎启动 + AOT 快照。这一点写进了 README，
免得把引擎的成本记在自己账上。

### 表格里如实标注了两列证据强度不同

我们的数字是**程序自己记录的**（四次启动、逐阶段），
对方的是**手工掐表**。同一台机器让它们可比，但可信度不对等，
README 里直接写明了这一点。

### 顺带发现的一处偶发停顿

四次启动里有一次，`window ready to show` → `window shown` 花了 **676 ms**，
另外三次分别是 5 / 2 / 13 ms。这一段里有四次 `windowManager` 平台调用
（`setPosition` / `maximize` / `show` / `focus`），单个标记指认不出是哪一次。

**把标记拆成逐次调用**，下一份日志就能直接指名。
这正是这套追踪设施存在的意义——不猜，等数据。
