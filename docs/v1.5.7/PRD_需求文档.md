## FEAT-077：构件互不干扰

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-01 |
| 需求描述 | 把「一种构件不得被旁边的构件弄坏」这条性质做成可执行的测试 |
| 用户场景 | 真实文档从来不是单一构件。BUG-215（引用块之后所有引用式链接失效）就是这么产生的，而规范语料完全抓不到 |
| 优先级 | P2 |
| 难易度 | 低 |

### 缘由

BUG-215 的教训：**CommonMark 语料每个例子只有一种构件**，
解析器可以全部通过，而把两种构件放进同一篇文档就出错。
那个 bug 修复前后规范分数都是 493，纹丝不动——语料里没有一个例子同时含有
引用块和引用式链接。

### 实现方案

19 种构件，每种给出「源码」和「输出里必须出现的特征」。
遍历**全部三元有序组合**（5814 种），拼成文档解析导出，
断言三种构件的特征都还在。

**特征刻意取得宽松**——取构件承载的文字，而不是精确的标签。
两个相邻列表会合并成一个松散列表（这是正确行为），
条目于是从 `<li>x</li>` 变成 `<li><p>x</p></li>`；
特征写死成前者就会在**正确的输出**上误报。

**前置元数据单独验**：它只有在文件最开头才成立，
放进遍历会产生 19 条假阳性。另外补了一条反向断言——
写在文档中间的 `---\ntitle: 甲\n---` **不应该**被当成前置元数据。

### 验收标准

- 5814 个三元组合全部通过
- 撤掉 BUG-215 的修复后，这条测试必须失败（实测 147 个组合报错）
- 单次运行 < 10 秒（实测 7.7 秒）

### 本轮的排查结论

- 全部三元组合**零失败**，构件互扰这一维度目前是干净的
- 顺带核对了解析器的可变实例状态：只有 `_linkDefinitions` 与 `_parseDepth` 两个，
  都已在 BUG-215 中处理，没有第二处会被嵌套解析破坏的状态
