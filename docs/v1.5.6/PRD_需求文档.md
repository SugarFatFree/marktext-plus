## FEAT-065：支持 `<ruby>` 注音

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-08-31 |
| 需求描述 | 内联 HTML 支持 `<ruby>漢<rt>hàn</rt></ruby>`，把读音画在文字上方 |
| 用户场景 | 日文振假名（`<ruby>東京<rt>とうきょう</rt></ruby>`）与中文拼音标注都靠它。本项目支持 12 种语言、用户以中文为主，这是实打实的缺口。此前它被转义成尖括号显示，一篇注音文档读起来就是它自己的源码 |
| 如何发现的 | 拿上游 MarkText 的 e2e 当规格核对。`blocks/html-inline.spec.ts` 明确写着"`<ruby>` 是特例，有自己的 `htmlRuby.ts` 渲染器"。逐条比对我们支持的内联标签白名单——`<u> <mark> <sup> <sub> <kbd>` 等都在，唯独没有 `ruby` |
| 实现方案 | 上游是把 `<ruby>` 原样塞进 DOM 交给浏览器画，我们得自己画：① 新增 `InlineType.ruby`，正文存 `text`、读音存 `title`——**两者必须是同一个 span**，拆成两个会在换行处断开、也会被朗读成两个词；② 内联 HTML 正则新增 ruby 分支，并吃掉 `<rp>` 回退括号（那是给画不出 ruby 的阅读器看的，我们画得出）；③ 四个消费方各按能力实现——预览用 `WidgetSpan` 叠一个 `Column`（读音在上、字号减半、基线居中），HTML 直接输出 `<ruby>` 并补 `<rp>` 括号，Word 与 PDF 无注音能力，退化成 `漢(hàn)` 这种词典式写法而不是丢掉 |
| 涉及文件 | `code/lib/services/markdown_parser.dart`、`code/lib/services/export_service.dart`、`code/lib/ui/editor/markdown_renderer.dart`、`code/test/services/ruby_annotation_test.dart`（新增，7 条）、`code/test/ui/editor/nested_link_gesture_test.dart`（+1 条） |
| 验收标准 | 解析成单个 span；句中位置正确；整词振假名；`<rp>` 被吃掉；**关闭内联 HTML 时仍保持字面**（护栏）；HTML 输出带 `<rp>`；读音里的 `&` 被转义。预览那条断言的是**几何**——读音的底边不低于正文顶边、且字号更小；把读音移到下方后确认报警，不是"有两个 Text 就算过" |

新增枚举值时故意先不改任何 switch，让编译器把四处消费方全列出来——比自己回忆可靠。

| 实现日期 | 2026-08-31 |

| 用户场景 | Mermaid 是本项目的招牌功能，却**没有任何插入入口**——要自己敲 ```` ```mermaid ````、再敲图型首行。标题则是可发现性问题：`##` 只要两键，但刚发现 `/` 的人没理由知道 |

| 涉及文件 | `code/lib/providers/editor_provider.dart`、`code/lib/ui/editor/source_editor.dart`、`code/lib/ui/widgets/slash_menu.dart`、`code/lib/ui/screens/home_screen.dart`、12 个 `.arb`、`code/test/ui/editor/slash_menu_test.dart`（+3 条） |
| 验收标准 | 六个标题都在列表里；Mermaid 可从菜单插入且插入的是能渲染的图（正则取出围栏内容断言非空，不是"有 ```mermaid 就算过"）；`/mermaid`、`/流程图`、`/图表`、`/diagram` 四种输入都能筛到它 |

### 两处判断

**没有照搬上游的顺序。** 上游把六个标题放在最前——它是 WYSIWYG，标题没有别的输入方式。
本项目是源码编辑器，`##` 只要两键。菜单高度 280px，**不滚动只能看到约 5 条**，
六个标题放最前会把表格、代码围栏、图表这些真正难敲的挤出视野。所以标题放末尾，
Mermaid 紧挨代码围栏。这处偏离在代码注释里写明了理由。

**先写错了一句注释。** 我给 Mermaid 那条写的是"高到不用滚动就能看见"，
组件测试点不到它才发现只有约 5 条可见——第 6 条要滚动。注释已改成实话：
靠滚动，或者更快地输入关键词。并补了一条"输入关键词能筛到它"的测试，
那才是真实使用路径。

### 顺带被护栏拦住一次

新增 `FormatAction.mermaidBlock` 后，`command_palette_coverage_test.dart` 立刻报错——
**每个 FormatAction 都必须能从命令面板到达**。这条护栏本身是早先"十七个动作在菜单里
有、在面板里没有"那次留下的，这次正好拦住了同一类遗漏。

## FEAT-067：独占一行的 `<img>` 标签当作图片渲染，并支持尺寸

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-08-31 |
| 需求描述 | `<img src="a.png" width="400">` 这样单独占一行的标签，渲染成图片而不是源码 |
| 用户场景 | markdown 自身**没有**表达图片尺寸的语法，需要指定尺寸的文档只能退回 HTML 标签。此前这类行被当作 HTML 块，在预览里画成灰框里的一行尖括号 |
| 如何发现的 | 顺着上游 `drag/image-resize.spec.ts` 查下去——上游拖拽缩放后写回的正是 `<img … width="N">`。也就是说**上游产出的文档在本编辑器里打不开图**。实测：上游 MarkText 自己的文档里有 **60 处**独占一行的 `<img>` |
| 实现方案 | ① `InlineSpan` 新增 `width`/`height`；② 解析时在 HTML 块分支**之前**识别独占一行的 `<img>`，读出 src/alt/width/height/title 转成图片 span——属性顺序任意、单引号双引号无引号三种写法都支持；③ 预览把尺寸传给 `Image.network`/`Image.file`（只给一边时另一边留给图片自身比例，不去猜）；④ HTML 导出带上尺寸属性 |
| 涉及文件 | `code/lib/services/markdown_parser.dart`、`code/lib/ui/editor/markdown_renderer.dart`、`code/lib/services/export_service.dart`、`code/test/services/image_tag_test.dart`（新增，9 条）、另修订 2 条既有断言 |
| 验收标准 | 三种引号写法、任意属性顺序都能读出 src 与 width；只给 height 也读得出；未写的尺寸保持 null 而不是猜一个；导出带尺寸；`![alt](src)` 完全不受影响 |

### 一处刻意的规范偏离

CommonMark 条件 7 规定"任何独占一行的标签都开启 HTML 块"，`<img>` 现在是例外。
理由：导出仍然产出 `<img>`，往返不变，变的只是**预览把图画出来**——文档写 `<img>`
就是在要一张图。规范用例数不变（396，无退步）。既有的两条断言按新意图更新了，
条件 7 的其余覆盖（`<br>`、`<a href="x">`）原样保留。

### 一处我写错又更正的依据

最初注释里写的是"本项目 README 有 8 处这样的截图"。实际去数才发现，
**README 里那 8 处 `<img>` 全都包在 HTML `<table>` 里**——本次改动对它们无效
（那需要渲染整个 HTML 表格，是另一件大得多的事）。改成据实说明：
依据是上游文档的 60 处，本仓库自己是 0 处。测试里也专门留了一条
"表格里的图仍是 HTML 块"，把这个边界钉住。

|------|------|
| 实现日期 | 2026-08-31 |
| 需求描述 | 惰性续行让列表与引用的块覆盖了不带标记的行，为"取出块 → 写回块"补一层护栏 |
| 用户场景 | 预览里双击一个块编辑，是按**行范围**把源码取出来、编辑完再盖回同一段。范围少一行会把续行丢掉，多一行会把后面的段落吃掉——**这两种都不会被任何解析测试发现**，因为解析结果本身是对的 |
| 实现方案 | 对六种"块比首行长"的形状做往返：列表续行、引用续行、引用内标题后续行、列表空项、步骤下的缩进代码、含空行的 `<pre>`。每个块原样取出再写回，文档必须一字不差；同时断言取出的片段确实出现在原文里 |
| 涉及文件 | `code/test/services/lazy_block_roundtrip_test.dart`（新增，6 条） |
| 验收标准 | 六条全过；把 `sourceOfBlock` 的结束行人为减一之后，六条全部失败 |

### 一处绕开的坑

本想把这些形状加进共用语料 `test/fixtures/showcase.md`，
但那份语料的测试里有 `expect('<ul>'.allMatches(html).length, 3)` 这样的**数量断言**，
另一个测试文件也读它。往共用语料里加内容会连带打破无关断言，
所以改成独立测试文件。

| 实现日期 | 2026-08-31 |
| 需求描述 | 已有的全构件语料只被解析、从未被渲染；补一层渲染冒烟测试 |
| 用户场景 | 解析正确、渲染时抛异常——比如一个没有尺寸的 WidgetSpan、一个拿到负宽度的画笔——用户看到的是一片红屏，而**没有任何测试会失败**。本周改的强调嵌套、`<ruby>` 注音、`<img>` 标签全都在渲染路径上 |
| 实现方案 | 两条：① 把 439 行的 `showcase.md` 整篇喂给 `MarkdownRenderer` 并断言无异常；② 另写一篇把**本周改动涉及的构件放在一起**——标题里的加粗与链接、加粗里套链接/斜体/代码、ruby 注音、带尺寸的 `<img>`、任务项里的加粗链接、换行续写的列表项、续行的引用、表头带格式的表格、mermaid 图——因为相互干扰正是在这种地方出现 |
| 涉及文件 | `code/test/ui/editor/showcase_render_test.dart`（新增，2 条） |
| 验收标准 | 两条都无异常；在 ruby 分支注入一个必抛的异常后，第二条确认失败 |

### 一次无效的验证，以及为什么

第一次注入的是 `span.title!`（把空安全的兜底换成强制解包），测试**没有失败**——
因为那些 ruby span 的 `title` 本来就都不为空，`!` 根本不会抛。
换成无条件 `throw` 才真正验证了这层测试有效。
"改坏它看测试会不会红"，前提是改动真的会坏。

## FEAT-071：换行符不得改变文档含义

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-08-31 |
| 需求描述 | 为"CRLF 与 LF 解析结果必须相同"补一条性质测试 |
| 用户场景 | Windows 是受支持平台，本编辑器打开的文档有一半以 CRLF 结尾。而本轮改动**全都是按行判断的**——列表项在哪结束、引用是否续行、原文标签延伸多远——正是一个游离的 `\r` 会被当成内容、或让匹配落空的地方 |
| 实现方案 | 对十种按行判断的形状，断言 CRLF 版与 LF 版渲染结果**完全相同**；另加一条孤立 `\r`（老式 Mac 换行、或经过损坏转换的文件）。断言的是**性质而非期望输出**，所以规则本身将来怎么改，这条都还成立 |
| 涉及文件 | `code/test/services/line_ending_equivalence_test.dart`（新增，11 条） |
| 验收标准 | 11 条全过；把按行切分从 `LineSplitter` 换成 `split('\n')`（即"把 `\r` 当作内容"）之后，9 条确认失败 |

查证结果：**当前实现没有这方面的缺陷**，六种新行为在 CRLF 下与 LF 完全一致。
这条测试是为将来准备的——既有的 CRLF 测试只覆盖 `replaceBlock` 的写回，
不覆盖解析本身。
