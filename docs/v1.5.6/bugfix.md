## BUG-173：引用式链接的标签里，标记仍显示成字面量

**日期**：2026-08-31　**优先级**：P2　**状态**：已修复

### 现象

`[**下载**][dl]` 渲染成一个链接，但文字是 `**下载**` 带着两对星号。
行内式的 `[**下载**](url)` 在 v1.5.5 已经修好（BUG-167），引用式没有。

### 根因

解析器有**两个**链接分支——行内式 `[text](url)` 和引用式 `[text][label]`。
BUG-167 只改了第一个。这是"同一个规则的第二份副本落后了"在本项目里的第五次，
只不过这次落后的那份是我自己昨天留下的。

### 如何发现的

不是等着踩，而是拿上游 MarkText 的 e2e 测试当规格来核对。
`packages/muya/e2e/tests/blocks/reference-link-image.spec.ts` 列了引用式链接与
引用式图片的六种行为，逐条在本项目上跑了一遍：大小写不敏感、折叠式 `[label][]`、
简写式 `[label]`、缺定义时保持字面、带标题——**五项都正确，只有标签里的标记不解析**。

### 修复方案

引用式分支同样调用 `_nestedSpans(..., insideLink: true)`（`insideLink` 是
BUG-168 加的，防止链接里再套链接产出非法的嵌套锚点）。

### 验证

新增 4 条：两条针对性（span 结构、HTML 输出），去掉嵌套后确认失败；
两条护栏（普通引用链接不产生子节点、未解析的引用仍保持字面）。

### 涉及文件

- `code/lib/services/markdown_parser.dart`
- `code/test/services/nested_emphasis_test.dart`

## BUG-174：图片 alt 里残留 markdown 标记

**日期**：2026-08-31　**优先级**：P2　**状态**：已修复

### 现象

`![一张 **重要** 的图](/img.png)` 导出的 HTML 是 `alt="一张 **重要** 的图"`。

alt 文本的用武之地恰恰是**图加载不出来的时候**——那时屏幕上显示的是它。
让它带着 markdown 标记，等于图片在用源码描述自己。屏幕阅读器读出的也是这个。

### 根因

三个图片分支（行内式、引用式、README 徽章那种"图片套链接"）都把 alt 原样传下去。
CommonMark 规定 alt 取的是内联内容的**纯文本**。

### 修复方案

新增 `_altText`：把 alt 当内联内容解析，再把结果拍平成纯文本
（`![见 [这里](/x)](/img.png)` 的 alt 是"见 这里"）。没有标记时原样返回，
不产生额外开销。三个分支统一走它。

### 验证

CommonMark 规范用例 388 → 396（本条与 BUG-173 合计 +8）。
新增 4 条：三条针对性（行内式 alt、alt 里的链接、引用式 alt），去掉拍平后确认失败；
一条护栏（普通 alt 不变）。

### 涉及文件

- `code/lib/services/markdown_parser.dart`
- `code/test/services/nested_emphasis_test.dart`
- `code/test/services/commonmark_spec_test.dart`（下限 388 → 396）

## BUG-175：代码块里展示的链接定义会真的生效

**日期**：2026-08-31　**优先级**：P2　**状态**：已修复

### 现象

一篇讲 markdown 的文档，在代码块里举例：

````
教程里举个例子：

```markdown
[示例]: https://example.com
```

正文里写 [示例] 不该变成链接。
````

最后那句里的 `[示例]` **真的变成了链接**，指向代码块里那个示例地址。
读者看不出发生了什么，只会觉得文档里莫名其妙多了个链接。

反过来也一样别扭：把定义写进代码块想"注释掉"它，它照样生效。

### 根因

链接定义是在解析开始前**先扫一遍全文**收集的——因为引用可以写在定义上面。
这一趟扫描逐行匹配定义的正则，**完全不知道代码围栏的存在**。
缩进代码块反而没事（定义正则要求缩进不超过三格，四格缩进不匹配），
只有围栏代码块会泄漏。

### 修复方案

收集时跟踪围栏状态：``` 与 ~~~ 都算，且**只有同字符、不短于开围栏的行才算闭合**
（```` 里嵌 ``` 是文档展示围栏本身的写法，内层那个不能当作外层的结束）。
围栏内的行一律跳过。

### 顺带修正：重复定义应"先者胜出"

同一个标签定义两次时我们取了后者，CommonMark 规定取前者。
文档里出现重复定义本身是笔误，取后者等于让笔误赢。大小写不同视为同一标签。

### 验证

CommonMark 规范用例 396 → 399。新增 8 条测试，分两次验证：
只回退"先者胜出"时那 2 条失败，只回退"围栏感知"时那 4 条失败，
护栏 2 条（围栏之后的定义仍有效、普通定义不受影响）两边都过。

### 涉及文件

- `code/lib/services/markdown_parser.dart`
- `code/test/services/link_definition_scope_test.dart`（新增，8 条）
- `code/test/services/commonmark_spec_test.dart`（下限 396 → 399）

## BUG-176：折行的段落里，跨行的强调不生效

**日期**：2026-08-31　**优先级**：P2　**状态**：已修复

### 现象

```
*强调跨了
一行*
```

渲染成字面星号，不是斜体。加粗、下划线写法同理。
**同一句话，折不折行结果不同**——这才是最费解的地方：写在一行好用，
按 80 列折了行就失效。中文文档手动折行、以及各种自动折行的文件都会遇到。

### 根因

强调的内容用 `.*?` 匹配，而 `.` 不匹配换行符。

### 修复方案

改成 `[\s\S]*?`。范围仍然限于一个块——`parseInline` 是逐块调用的，
所以空行、列表项、代码块边界依然会截断，不会跨段落乱配。

### 修完立刻踩到的回归

单字符强调 `*甲*` 坏了。内容模式写作 `([^\s].*?[^\s]|[^\s])`——多字符分支在前，
单字符分支在后。此前多字符分支被换行挡住，找不到配对就退回单字符分支；
一旦允许跨行，它就一路找到段落更下面的另一个 `*` 配对，把中间全吞了。
`这里 *甲*，⏎下一行 *乙*。` 变成了一个从"甲"横跨到"乙"的斜体。

把两个分支的顺序调过来（单字符在前）即可，规范用例数不受影响。
中文里单字符强调很常见，这条如果漏掉会很显眼。

### 关于一处行为变化

`价格 3*4 元，⏎另一行 5*6 元。` 现在会把中间配成斜体。
但**同一句写在一行时，改动前就已经这样了**——数字间的星号按 CommonMark
的 flanking 规则本来就能开闭强调。所以这不是新引入的误配倾向，
而是消除了"折行与否结果不同"的差异。测试里把这一点写成了性质断言。

### 验证

CommonMark 规范用例 399 → 406。新增 9 条测试：4 条跨行生效、3 条边界仍能截断
（空行、代码跨度、列表项）、1 条单字符强调、1 条"折行不改变含义"的性质断言。
把分支顺序换回去后，单字符那 2 条确认失败。

### 涉及文件

- `code/lib/services/markdown_parser.dart`
- `code/test/services/emphasis_across_lines_test.dart`（新增，9 条）
- `code/test/services/commonmark_spec_test.dart`（下限 399 → 406）
