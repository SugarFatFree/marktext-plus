## BUG-173：引用式链接的标签里，标记仍显示成字面量

**日期**：2026-08-31　**优先级**：P2　**状态**：已修复

### 现象

`[**下载**][dl]` 渲染成一个链接，但文字是 `**下载**` 带着两对星号。
行内式的 `[**下载**](url)` 在 v1.5.5 已经修好（BUG-167），引用式没有。

### 根因

解析器有**两个**链接分支——行内式 `[text](url)` 和引用式 `[text][label]`。
BUG-167 只改了第一个。这是"同一个规则的第二份副本落后了"在本项目里的第五次，
只不过这次落后的那份是我自己昨天留下的。

### 如何发现的

不是等着踩，而是拿上游 MarkText 的 e2e 测试当规格来核对。
`packages/muya/e2e/tests/blocks/reference-link-image.spec.ts` 列了引用式链接与
引用式图片的六种行为，逐条在本项目上跑了一遍：大小写不敏感、折叠式 `[label][]`、
简写式 `[label]`、缺定义时保持字面、带标题——**五项都正确，只有标签里的标记不解析**。

### 修复方案

引用式分支同样调用 `_nestedSpans(..., insideLink: true)`（`insideLink` 是
BUG-168 加的，防止链接里再套链接产出非法的嵌套锚点）。

### 验证

新增 4 条：两条针对性（span 结构、HTML 输出），去掉嵌套后确认失败；
两条护栏（普通引用链接不产生子节点、未解析的引用仍保持字面）。

### 涉及文件

- `code/lib/services/markdown_parser.dart`
- `code/test/services/nested_emphasis_test.dart`

## BUG-174：图片 alt 里残留 markdown 标记

**日期**：2026-08-31　**优先级**：P2　**状态**：已修复

### 现象

`![一张 **重要** 的图](/img.png)` 导出的 HTML 是 `alt="一张 **重要** 的图"`。

alt 文本的用武之地恰恰是**图加载不出来的时候**——那时屏幕上显示的是它。
让它带着 markdown 标记，等于图片在用源码描述自己。屏幕阅读器读出的也是这个。

### 根因

三个图片分支（行内式、引用式、README 徽章那种"图片套链接"）都把 alt 原样传下去。
CommonMark 规定 alt 取的是内联内容的**纯文本**。

### 修复方案

新增 `_altText`：把 alt 当内联内容解析，再把结果拍平成纯文本
（`![见 [这里](/x)](/img.png)` 的 alt 是"见 这里"）。没有标记时原样返回，
不产生额外开销。三个分支统一走它。

### 验证

CommonMark 规范用例 388 → 396（本条与 BUG-173 合计 +8）。
新增 4 条：三条针对性（行内式 alt、alt 里的链接、引用式 alt），去掉拍平后确认失败；
一条护栏（普通 alt 不变）。

### 涉及文件

- `code/lib/services/markdown_parser.dart`
- `code/test/services/nested_emphasis_test.dart`
- `code/test/services/commonmark_spec_test.dart`（下限 388 → 396）

## BUG-175：代码块里展示的链接定义会真的生效

**日期**：2026-08-31　**优先级**：P2　**状态**：已修复

### 现象

一篇讲 markdown 的文档，在代码块里举例：

````
教程里举个例子：

```markdown
[示例]: https://example.com
```

正文里写 [示例] 不该变成链接。
````

最后那句里的 `[示例]` **真的变成了链接**，指向代码块里那个示例地址。
读者看不出发生了什么，只会觉得文档里莫名其妙多了个链接。

反过来也一样别扭：把定义写进代码块想"注释掉"它，它照样生效。

### 根因

链接定义是在解析开始前**先扫一遍全文**收集的——因为引用可以写在定义上面。
这一趟扫描逐行匹配定义的正则，**完全不知道代码围栏的存在**。
缩进代码块反而没事（定义正则要求缩进不超过三格，四格缩进不匹配），
只有围栏代码块会泄漏。

### 修复方案

收集时跟踪围栏状态：``` 与 ~~~ 都算，且**只有同字符、不短于开围栏的行才算闭合**
（```` 里嵌 ``` 是文档展示围栏本身的写法，内层那个不能当作外层的结束）。
围栏内的行一律跳过。

### 顺带修正：重复定义应"先者胜出"

同一个标签定义两次时我们取了后者，CommonMark 规定取前者。
文档里出现重复定义本身是笔误，取后者等于让笔误赢。大小写不同视为同一标签。

### 验证

CommonMark 规范用例 396 → 399。新增 8 条测试，分两次验证：
只回退"先者胜出"时那 2 条失败，只回退"围栏感知"时那 4 条失败，
护栏 2 条（围栏之后的定义仍有效、普通定义不受影响）两边都过。

### 涉及文件

- `code/lib/services/markdown_parser.dart`
- `code/test/services/link_definition_scope_test.dart`（新增，8 条）
- `code/test/services/commonmark_spec_test.dart`（下限 396 → 399）

## BUG-176：折行的段落里，跨行的强调不生效

**日期**：2026-08-31　**优先级**：P2　**状态**：已修复

### 现象

```
*强调跨了
一行*
```

渲染成字面星号，不是斜体。加粗、下划线写法同理。
**同一句话，折不折行结果不同**——这才是最费解的地方：写在一行好用，
按 80 列折了行就失效。中文文档手动折行、以及各种自动折行的文件都会遇到。

### 根因

强调的内容用 `.*?` 匹配，而 `.` 不匹配换行符。

### 修复方案

改成 `[\s\S]*?`。范围仍然限于一个块——`parseInline` 是逐块调用的，
所以空行、列表项、代码块边界依然会截断，不会跨段落乱配。

### 修完立刻踩到的回归

单字符强调 `*甲*` 坏了。内容模式写作 `([^\s].*?[^\s]|[^\s])`——多字符分支在前，
单字符分支在后。此前多字符分支被换行挡住，找不到配对就退回单字符分支；
一旦允许跨行，它就一路找到段落更下面的另一个 `*` 配对，把中间全吞了。
`这里 *甲*，⏎下一行 *乙*。` 变成了一个从"甲"横跨到"乙"的斜体。

把两个分支的顺序调过来（单字符在前）即可，规范用例数不受影响。
中文里单字符强调很常见，这条如果漏掉会很显眼。

### 关于一处行为变化

`价格 3*4 元，⏎另一行 5*6 元。` 现在会把中间配成斜体。
但**同一句写在一行时，改动前就已经这样了**——数字间的星号按 CommonMark
的 flanking 规则本来就能开闭强调。所以这不是新引入的误配倾向，
而是消除了"折行与否结果不同"的差异。测试里把这一点写成了性质断言。

### 验证

CommonMark 规范用例 399 → 406。新增 9 条测试：4 条跨行生效、3 条边界仍能截断
（空行、代码跨度、列表项）、1 条单字符强调、1 条"折行不改变含义"的性质断言。
把分支顺序换回去后，单字符那 2 条确认失败。

### 涉及文件

- `code/lib/services/markdown_parser.dart`
- `code/test/services/emphasis_across_lines_test.dart`（新增，9 条）
- `code/test/services/commonmark_spec_test.dart`（下限 399 → 406）

## BUG-177：`<tel:…>`、`<file:///…>` 等尖括号地址不成链；`<MAILTO:…>` 成了坏链接

**日期**：2026-08-31　**优先级**：P2　**状态**：已修复

### 现象

尖括号写法只认 `http`/`https`/`ftp`/`mailto` 四种协议，其余一律显示成尖括号文本：

- `<tel:+8613800138000>` —— 手机上点了能拨号的写法
- `<file:///home/me/notes.md>` —— 指向本地文件
- `<vscode://file/tmp/a.dart:12>` —— 编辑器自己的跳转链接
- `<localhost:5001/foo>` —— 内网地址
- `<irc://…>`、`<made-up-scheme://…>`

更糟的是 `<MAILTO:FOO@BAR.BAZ>`（大写）：协议名匹配是大小写敏感的，
四种协议都没命中，于是落到**邮箱地址**分支，被再加了一个前缀，
变成 `mailto:MAILTO:FOO@BAR.BAZ` —— 一个点了什么也打不开的坏链接。

### 根因

协议写死成 `(?:https?|ftp|mailto)`。CommonMark 的规则是任意协议：
字母开头，后跟字母数字与 `+.-`，总长 2–32，然后一个冒号。

### 修复方案

改成 `[a-zA-Z][a-zA-Z0-9+.\-]{1,31}:[^<>\s]*`。这条分支排在邮箱分支之前，
所以带协议的写法（含大写 `MAILTO:`）会先被它接住，不会再被当成裸邮箱。

### 验证

CommonMark 规范用例 406 → 411。新增 11 条：7 条各种协议、1 条大写 MAILTO、
3 条护栏——普通 `<foo@example.com>` 仍加 `mailto:` 前缀、
HTML 标签（`<span style="color:red">` 里也有冒号）不被当成协议、
`<https://foo.bar/baz bim>` 里有空格不成链。换回旧正则后 8 条确认失败。

### 涉及文件

- `code/lib/services/markdown_parser.dart`
- `code/test/services/autolink_scheme_test.dart`（新增，11 条）
- `code/test/services/commonmark_spec_test.dart`（下限 406 → 411）

## BUG-178：步骤下面用缩进写的代码块，缩进被吃掉变成普通段落

**日期**：2026-08-31　**优先级**：P2　**状态**：已修复

### 现象

```
- foo

      bar
```

`bar` 应当是列表项里的一段**代码**（缩进 6 格 = 内容列 2 格 + 代码所需的 4 格），
渲染出来却是普通段落：等宽字体没了、缩进没了、多行代码的对齐也没了。

### 根因

剥离列表项缩进的 `_dedent` 按**这些行共同拥有的缩进**来剥。
carried 块只有一行、缩进 6 格，公共缩进就是 6，于是全剥光，
"让它成为代码块"的那 4 格也一起没了。
规范的规则是只剥到该项的**内容列**。

### 修复方案

改成剥 `min(内容列, 公共缩进)`。取 min 是为了保住原注释关心的那件事——
列表项里的围栏与引用要能被认出来；同时对缩进少于内容列的松散写法也不会过度剥离。

## BUG-180：标记连写时强调解析错误（改用定界符算法）

**日期**：2026-08-31　**优先级**：P1　**状态**：已修复

### 现象

标记挨在一起时，强调解析得不对。这些都是日常写法：

| 写法 | 应为 | 实际 |
|------|------|------|
| `*外层 **内层***` | 斜体套加粗 | 字面星号，外层斜体没形成 |
| `***加粗** 其余*` | 斜体套加粗 | 加粗里混进一个星号 |
| `_外 _内_ 层_` | 斜体套斜体 | 下划线漏在文字里 |
| `__甲, __乙__, 丙__` | 加粗套加粗 | 下划线漏在文字里 |
| `foo***bar***baz` | `<em><strong>` | 里外颠倒成 `<strong><em>` |

反向也有错：`*$*alpha.` 不该成强调（一侧是标点一侧是字母），我们把它变成了斜体。

### 为什么值得动大手术

先用 **marked**（上游 MarkText 依赖的解析器）逐条比对：**上面每一条 marked 都是对的**。
所以这不是规范洁癖，是与上游的真实差距。同时也甄别出 `* a *` 上游同样输出列表——
那条"失败"两边一致，不是缺口，没有改。

### 根因

单个正则表达不了这件事。`*外层 **内层***` 与 `***加粗** 其余*` 的字符序列同构，
区别只在于**段落里每一处标记两侧是什么**。CommonMark 因此规定的是一套算法而非模式：
先收集所有定界符run，再反复"用最靠左的可闭合者去配最近的可开启者"。

### 修复方案

新增 `lib/services/inline_emphasis.dart`，实现该算法：

- **flanking 判定**：一个 run 能否开启/闭合，取决于两侧是空白、标点还是普通字符；
  `_` 的规则比 `*` 严（所以 `snake_case_name` 不会被拆开）。
- **三的规则**：当一侧既能开又能闭时，两个 run 的长度之和不得是 3 的倍数
  （除非两者都是）。少了它 `foo***bar***baz` 就会里外颠倒。
- **在最后一步运行**：代码跨度、链接、内联 HTML 都已解析完毕，对本算法就是不可分的
  原子——强调可以包住它们，而它们内部的星号再也不会被误认成标记。

原正则里那六个强调分支**保留但改为永不匹配**（`(?!)`），因为总正则有 40 个捕获组、
其中还有按绝对编号的反向引用 `\17`，删掉分支会让后面所有组号错位。
随后把那六个已成死代码的处理分支、以及不再由任何路径产生的 `InlineType.boldItalic`
一并删除——**新增枚举值时靠编译器列出全部消费方，删除时同样奏效**，它一次点出 7 处。

### 中途踩到并修掉的两个问题

1. **性能回退**：病态输入 `'*a' * 10000` 从原来的几十毫秒涨到 **2947ms**，
   被既有的病态输入测试当场拦住（预算 2000ms）。原因不是搜索，而是我用 `List`
   存 token——每合成一个强调都要 `removeRange`/`insert`，搬移后续全部元素，
   1 万个定界符就是 O(n²)。改成双向链表，并加上 `openersBottom` 上界（记录某类
   闭合者向前搜索的下界，避免未配对时重复扫描）。改后该测试恢复通过。
2. **isolate 依赖检查误报**：`large_document_cost_test` 断言"解析器的 import 全部

   "解析器不能依赖 Flutter"。改成**递归跟随 import**、只拒绝 `package:flutter`，
   并断言检查确实走进了新文件——否则拆分反而会让这道防线失效。

`<b>a *b* c</b>` 以前保持字面（因为斜体先匹配、把文本切碎，标签配不上）。
现在标签生效**且**内部强调也生效：`<strong>a <em>b</em> c</strong>`，与 marked 一致。

## BUG-181：`<pre>`/`<script>`/`<style>`/`<textarea>` 里有空行就被拦腰截断

**日期**：2026-08-31　**优先级**：P2　**状态**：已修复

### 现象

```

</pre>

## BUG-182：选中带句末标点的中文按 Ctrl+B，加粗不生效

**日期**：2026-08-31　**优先级**：P1　**状态**：已修复

### 现象

选中「删除分派了，重命名没有。」按 Ctrl+B，得到
`**删除分派了，重命名没有。**又是……` —— **这段不是粗体**，屏幕上就是两对星号。

同类还有：选中带书名号/引号的词组（`前面**「加粗」**后面`）、英文
`**bold.**after`。共同点是**标记紧贴标点、外侧又是文字**。

### 这不是解析器的 bug

先查证：`**加粗。**后面` 在 **marked**（上游 MarkText 用的解析器）与 GitHub 上
**同样不是粗体**。CommonMark 的 flanking 规则规定：闭合标记若前面是标点、
后面又是文字，则既不能开也不能闭。我们此前的宽松匹配才是偏离——
BUG-180 换成规范算法后，这条差异才显出来。

**发现方式**：BUG-180 是很深的改动，改完拿仓库自己的 132 篇文档做了一次针对性
体检（扫描"渲染后仍残留成对 `**`"）。命中 17 处，全部是这个形状——本项目自己的
bugfix 文档和启动耗时排查文档里就有。它们在 GitHub 上本来也不是粗体。

### 所以真正该修的是编辑器

用户选一句话（**中文句子几乎总是以 `。` 结尾**）按 Ctrl+B，编辑器却生成了一段
渲染不出来的标记——这是编辑器的责任。修复方案：加粗/斜体时把选区首尾的
**空白与句读标点挪到标记外面**，`**加粗。**后面` 变成 `**加粗**。后面`，
读起来一样，而且真的是粗体。

### 中途踩到并修掉的问题

第一版用"格式所定义的标点"整段范围来裁剪，立刻被既有测试拦下：
`**bold**` 整体施加斜体时，`*` 本身被当标点裁掉，结果**剥掉一层**而不是加一层。
更危险的是我自己想到并验证的另一种：选中 `见[链接](url)` 加粗会把尾部 `)`
裁到外面，**留下一个不再是链接的链接**。

改成**明确列举句读标点**（中西文句号逗号顿号分号冒号叹号问号、省略号破折号、
各种引号书名号括号），把 markdown 语法字符全部排除在外。两种情况都补了护栏测试。

### 验证

新增 10 条：4 条"Ctrl+B 产出的标记确实能渲染"（中文句号、中文引号、英文句号、
尾随空格），6 条护栏——普通文字不变、纯标点选区原样包裹、
**行内代码保留标点**（代码跨度没有 flanking 规则）、取消加粗仍然有效、
**链接不被破坏**、`**bold**` 施加斜体是嵌套而非剥离。
关闭裁剪后 4 条确认失败。

## BUG-189：源码区把不会渲染的强调染成粗体，两个面板互相矛盾

**日期**：2026-08-31　**优先级**：P2　**状态**：已修复

### 现象

分屏时，源码区把 `**加粗。**后面接中文` 染成粗体，预览里却是两对星号。
**编辑器自己前后矛盾**，而读者无从判断哪边是对的。

同样的还有 `**bold.**after`、`前面**「加粗」**后面`、`*斜体。*后面`。

### 根因

语法高亮有**自己的一套模式**（`\*\*(.+?)\*\*`），不含 flanking 规则——
又一处"同一件事的第二份副本"。BUG-180 让解析器改用规范算法之后，这个差距才显出来。

### 修复方案

**不再造第三份判断**：把解析器里的 flanking 规则抽成公开函数
`emphasisFlanking(before:, after:, char:)`，解析器与高亮器共用同一份。
高亮器为每个匹配加一道校验，不通过就跳过、继续往后找。

两处细节：

1. 斜体模式 `\*(.+?)\*` 会从 `**加粗。**` 中间咬出 `**加粗。*` 来染色。
   加上"两侧不与相邻星号相连"的约束（`(?<!\*)\*(?!\*)`）。
2. **删除线不套 flanking**。本项目的解析器对 `~~文字。~~后面` 是有意宽松的
   （BUG-183 的取舍），高亮若按 GitHub 的严格规则来，就会反过来与本项目的预览矛盾。

## BUG-193：链接地址被算进字数

## BUG-194：文档顶部的元数据和注释被算进字数

**日期**：2026-08-31　**优先级**：P2　**状态**：已修复

### 现象

接 BUG-193，同一类问题还有两处不可见内容被计入字数：

| 内容 | 实际字数 | 可见文字 |
|------|---------|---------|
| `---\ntitle: 我的文档标题\nauthor: 某人\ntags: 甲 乙 丙\n---\n\n正文一句话。` | 19 | 5 |
| `正文<!-- 这是给编辑看的注释文字 -->结束` | 15 | 4 |
| `正文有[链接][a]。\n\n[a]: https://example.com "标题在这里"` | 15 | 6 |

一份有 YAML 头的文档，光是标题、作者、标签就凭空多出十几个词；
写给自己看的注释也照计不误。

### 修复方案

仍保持单趟扫描：

- **元数据块**：位置固定在开头、以已知分隔符结束，所以开扫前先量出它有多少个
  码点，循环里跳过。分隔符判定复用解析器的 `isFrontMatterOpener`——不另立一套。
  **没有闭合分隔符时视为不是元数据块**，否则一行看着像开头的 `---`
  就会把整篇文档吞掉。
- **HTML 注释**：靠"刚刚看过的四个字符"识别 `<!--`，无需前瞻；
  而 `<!--` 本身不含词字符，所以识别出来时并没有误计过任何词。

### 引用定义行：先判断为"留待后续"，重看之后当轮做掉了

第一版把它列为未做，理由是"要跳过它必须先把标签里的词记进待定账"。
重看时发现这个理由**只对标签那一个词成立**：定义行里绝大部分词是**地址和标题**
（`[a]: https://example.com "标题在这里"` 的 15 个词里，标签只占 1 个），
而它们都在 `]:` 之后——识别到冒号时再跳到行尾，成本极低。

于是当轮补上：**行首**（只允许前导空格）出现的标签、且以 `]:` 收尾时，
跳过该行余下部分。行中的 `见[注一]: 说明` 不受影响——只有独占一行的标签才是定义。

标签本身仍计入 1 个词。这是有意留下的：把它也去掉才需要那套待定账机制，
而 1 个词与十几个词不是一回事。

### 性能

681 KB、含元数据头、1.2 万条注释与链接的文档：7–19 ms，与改动前同量级。

### 验证

新增 9 条。分别关掉三处跳过：元数据失败 1 条，注释失败 2 条，引用定义失败 2 条。
3 条护栏——未闭合的 `---` 不吞文档、未闭合的注释不吞文档、
`---` 作为标题下划线时不当作元数据（只有第一行才能开启元数据块）。

## BUG-196：没有 BOM 的 UTF-16 文件被当成 Latin-1，中文全成乱码

**日期**：2026-08-31　**优先级**：P2　**状态**：已修复

### 现象

UTF-16 编码但**不带字节序标记**的 .md 文件，打开后每个汉字都变成两段乱码。
记事本另存 UTF-16 会写 BOM，但很多导出工具不写。

文件能打开、看着像坏了——**这种状态下一旦保存，就把乱码写死了**。

### 根因

编码探测只认带 BOM 的 UTF-16，其余走 UTF-8 → GBK → Latin-1。
UTF-16 的字节在 UTF-8 下解不出来，GBK 形状也不匹配，最后落到 Latin-1
（它接受任何字节，所以永远"成功"）。

### 修复方案

文本编码不会出现零字节，而 UTF-16 里到处都是——每个 ASCII 字符都带一个，
且**固定落在字节对的同一侧**。markdown 永远含 ASCII（`#`、换行、方括号），
所以总有信号可看。

判据：零字节偏在一侧、且占比不低于 5%（防单个杂散零字节定调）。

### 两处试错

1. 最初要求"另一侧一个零都没有"，实测失败：`一` 是 U+4E00，低字节就是 0x00，
   会落在另一侧——而这是中文里最常用的字之一。
2. 改成 10 倍比例仍然过严，同样因为 `一` 这类字。最终定为 **2 倍**：
   小端序里奇数位是高字节（ASCII 必零、汉字必非零），偶数位是低字节
   （只有码点以 `00` 结尾的字才零），两者量级差得开。

### 一条写明边界的测试

纯中文、几乎不含 ASCII 的短文本仍然判不出来（信号来自 ASCII 带来的零字节）。
这条**写成了测试**而不是隐去：真实 markdown 总有 `#`、方括号、空行，
所以正常文档没问题；边界是个决定，不该是个意外。

### 验证

新增 8 条：小端、大端、含 `一` 的文档、以及反例——UTF-8 中文、纯 ASCII、
太短的文件、奇数长度（UTF-16 不可能是奇数字节）。

## BUG-198：GBK 笔记里打一个 emoji，保存后整篇文档变成乱码

**日期**：2026-08-31　**优先级**：P1　**状态**：已修复

### 现象

一份 GBK 编码的老笔记，在里面打一个 emoji（或任何 GBK 装不下的字符）再保存，
**下次打开时整篇文档都是乱码**——不是丢了那个 emoji，是丢了整个文件的可读性。

### 根因

保存时的代码本意是对的，注释写着"GBK 装不下的字符就改写 UTF-8，
这样字符还在；拒绝保存反而更糟"。但它**依赖编码器抛异常**：

```dart
try {
  return charset.gbk.encode(content);   // 以为它会抛
} catch (_) {
  return utf8.encode(content);          // 于是退回 UTF-8
}
```

而 `charset.gbk.encode` 遇到 emoji **不抛异常**，它返回一串
**GBK 自己都读不回来的字节**（解码时报 `Bad GBK encoding 0xf620`）。
于是文件照写不误，下次打开：UTF-8 解不出 → GBK 解不出 → 退到 Latin-1 → 满屏乱码。

**一个装不下的字符，代价是它周围的所有内容。**

### 修复方案

不再等编码器抱怨，而是**读回来对一遍**：编码成 GBK 后立刻解码，
与原文不一致就改写 UTF-8。判据从"有没有抛异常"变成"这些字节能不能还原成原文"。

### 代价

692K 字符的文档，多出的那次解码约 40 ms；保存本就是磁盘操作，可以接受。

### 顺带查证

Latin-1 那条分支没有同样的问题——`latin1.encode` 对超出范围的字符**确实会抛**
`ArgumentError`，退回 UTF-8 的逻辑一直是有效的。实测确认。

### 验证

新增 5 条：3 条针对性（emoji、生僻字、GBK 没有的货币符号），
把校验回退成"只捕异常"后全部失败；2 条护栏——**普通中文仍旧写成 GBK**，
不能因为怕出错就把所有 GBK 文件都转成 UTF-8。

## BUG-200：对缩进标题设置级别，旧标记被留在正文里

### 现象

一行 `   ## 标题`（前面三个空格）在预览里就是二级标题。
把光标放上去按 Ctrl+3，期望它变成三级标题，实际得到：

```
###    ## 标题
```

—— 一个三级标题，正文是 `## 标题`。用户的标题被吃进了自己的正文。

同一行按「转为正文」则**毫无反应**：菜单项点了没效果。
格式栏显示的当前级别也是 0（正文），和预览里画出来的二级标题对不上。

### 根因分析

标题动作自带一份规则 `RegExp(r'^(#{1,6})\s+')`，
比解析器的 `_headingRe`（`^ {0,3}(#{1,6})(?:\s+(.*?))?(?:\s+#+)?\s*$`）**窄**。
两者不一致的每一行都会出错：

| 行 | 预览 | 标题动作看到的 |
|---|---|---|
| `   ## 标题` | 二级标题（Markdown 允许最多三列缩进） | 正文 |
| `#` | 空标题（打字过程中必然经过的状态） | 正文 |
| `# 标题 #` | 标题，正文是 `标题` | 正文是 `标题 #` |

动作把这些行当正文，于是在前面**再加一个标记**，原来的标记就留在了文本里。

这是本版本反复出现的同一类问题：**一条规则被抄了好几份，其中一份没跟上**。
`headingLevelOf` 早先已经为语法高亮抽出来共享过一次，这里是第三份漏网的副本。

### 修复方案

- 解析器新增 `headingTextOf(String line)`，与 `headingLevelOf` 同源
  （都走 `_headingRe`），返回标题正文，非标题返回 null。
- `SourceEditor.applyHeadingLevel(line, level)` 抽成静态方法（可直接测），
  正文一律取自解析器：`headingTextOf(line) ?? line`。
- `_currentHeadingLevel()` 改用 `MarkdownParser.headingLevelOf`。
- 「清除格式」里的第四份副本 `^#{1,6}\s+` 一并改为 `^ {0,3}#{1,6}(?:[ \t]+|$)`，
  既认缩进标题，也不会把 `#标签` 的 `#` 当标记剥掉。
- 局部的 `_headingPrefixRe` 删除。

### 验证

新增 10 条。断言不只比对字符串，还**把结果交回解析器**确认它真的成了三级标题；
`#标签` 与 `####### 七` 两条护栏先断言"预览不把它当标题"，再断言动作不去动它。

把 `applyHeadingLevel` 换回旧的 `^(#{1,6})\s+`，4 条失败，
实际输出正是 `###    ## 标题`。

### 涉及文件

- `code/lib/services/markdown_parser.dart`、`code/lib/ui/editor/source_editor.dart`
- `code/test/ui/editor/heading_level_test.dart`（新增，10 条）

## BUG-201：简写引用链接的文字不解析加粗，`**` 直接显示出来

### 现象

把网址集中放在文末是很常见的写法：

```markdown
请先阅读[**下载说明**]，再继续。

[**下载说明**]: /docs/download
```

预览里这个链接显示为 `**下载说明**`——两对星号明晃晃地留在链接文字里。
换成 `[**下载说明**](/docs/download)` 写在行内就是正常的粗体。

图片同理：`![**图**]` 的 alt 文本是 `**图**`，
而 alt 是图片加载失败时给读者看的文字，不该是 Markdown 源码。

### 根因分析

Markdown 写链接有四种形式，解析器里是四个独立分支：

| 形式 | 写法 | 链接文字是否解析 |
|---|---|---|
| 行内 | `[t](/url)` | ✅ |
| 完整引用 | `[t][label]` | ✅ |
| 折叠引用 | `[t][]` | ✅ |
| **简写引用** | `[t]` | ❌ |

前三个分支都调用 `_nestedSpans(..., insideLink: true)` 解析链接文字，
第四个 `_addShortcutReference` 只填了 `text: label`。

这是本版本第三次遇到同一个模式了。更说明问题的是：完整引用那个分支的注释里
**就写着这个 bug 当初是怎么修的**——「两个链接分支里的第二个……它还在把标记
当字符读，所以同一个 `[**Download**][dl]` 星号露在外面」。当时修了第二个，
第三个（简写形式）漏掉了。

### 修复方案

- `_addShortcutReference` 增加 `depth` 参数。
- 链接分支补 `children: _nestedSpans(label, depth, insideLink: true)`，
  与另外三个分支完全一致（`insideLink` 保证链接套链接被拆平，不会产生嵌套 `<a>`）。
- 图片分支的 alt 改用 `_altText(label, depth)`，与其它图片形式一致。

### 验证

新增 12 条。核心是**四种形式写同一句话，断言输出完全相同**——
这样任何一个分支再掉队都会立刻暴露，而不是只测被修的那一个。
护栏三条：无定义的 `[sic]` 仍是字面文字、纯文字简写链接不受影响、
简写链接里再套链接不产生嵌套 `<a>`。

去掉 `children` 后 4 条失败，输出正是 `<a href="/url">**下载**</a>`；
CommonMark 棘轮同时从 476 掉回 473，说明这 3 分确实来自本次修改。

### 影响

CommonMark 一致性 **473 → 476**，下限同步提到 476。

### 涉及文件

- `code/lib/services/markdown_parser.dart`
- `code/test/services/shortcut_reference_test.dart`（新增，12 条）
- `code/test/services/commonmark_spec_test.dart`（下限 473 → 476）

## BUG-202：列表项下不空行写代码块，整块被吞成行内代码

### 现象

安装步骤几乎都是这么写的：

```markdown
- 安装依赖
  ```bash
  npm i
  ```
- 完成
```

预览里得到的是：

```html
<li>安装依赖 <code>bash npm i </code></li>
```

代码块变成了**行内代码**，语言标记 `bash` 混进了正文，代码本身被压成一行。
引用块同样：`- 注意` 下面的 `> 这里有坑` 里，`>` 直接以字面形式显示。
列表项下写标题也一样不生效。

**中间空一行就完全正常**——这正是它长期没被发现的原因：
看起来像是「排版习惯问题」，而不是 bug。

### 根因分析

`_buildListItems` 里这一句：

```dart
// The item's own text runs to the first blank line
final blank = block.indexWhere((line) => line.trim().isEmpty);
```

「项目自身的文字一直延伸到第一个空行」——但空行只是**结束一个项目文字的诸多方式
中最常见的那一种**。没有空行时，围栏行、引用行、标题行都被并进同一段文字，
然后交给行内解析器，于是 ` ``` ` 被当成了行内代码的分隔符。

而「什么样的行自成一块」这条规则解析器里早就有了：`_startsAnotherBlock`，
段落循环、大纲提取、惰性续行三处都在用它。这里是第四个没用上的地方。

### 修复方案

- 先按项目文字的起始列 `_contentColumn` 把后续行去缩进，得到 `body`
  （必须先去缩进：深层嵌套项下的标题带 4 个以上空格，不去缩进就匹配不上标题规则）。
- 在 `body` 上用 `_startsAnotherBlock` 找第一个自成一块的行作为切点。
- 切点之前是项目自身的文字，之后交给 `parse()` 当作它携带的块。
- `_shiftSpans` 的行号偏移随切点走（原来是 `blank + 1`）。

### 验证

新增 10 条，覆盖无序项、有序步骤、任务项、深层嵌套项下的代码块，
以及引用块和标题。三条护栏：折行的长句子仍然拼成一句、嵌套子列表仍然嵌套、
普通列表逐字节不变。

把切点改回「只在空行处切」后，6 条行为失败 + CommonMark 棘轮回落，
3 条护栏两边都过。

### 影响

CommonMark 一致性 **476 → 478**，下限同步提到 478。

### 涉及文件

- `code/lib/services/markdown_parser.dart`
- `code/test/services/list_item_blocks_under_text_test.dart`（新增，10 条）
- `code/test/services/commonmark_spec_test.dart`（下限 476 → 478）

## BUG-203：HTML 注释在预览里以字面形式显示出来

### 现象

```markdown
正文一

<!-- TODO: 这段待补充 -->

正文二
```

预览里中间那行显示为 `<!-- TODO: 这段待补充 -->`——注释按定义就是不该被看见的，
这是它唯一不能出现的样子。导出到 PDF、Word 里同样带着。

注释在真实文档里到处都是：待办标记、`<!-- prettier-ignore -->`、
Hexo 的 `<!-- more -->`、许可证头、临时藏起来的段落。

### 根因分析

`_htmlBlockStartRe` 是 `^<([a-zA-Z]…)`，要求 `<` 后面跟字母，
所以 `<!--` 压根不进 HTML 块分支，只能落到段落里被转义显示。
CommonMark 把注释列为 HTML 块的第二类。

### 修复方案

- 解析器识别 `<!--` 开头（允许最多三列缩进）的块，止于含 `-->` 的那一行。
- `HtmlBlockNode` 增加 `isComment`。预览返回 `SizedBox.shrink()`
  （仍占一个位置，保证预览的块编号与源码对得上）；PDF 与 Word 跳过；
  富文本复制返回空串；**HTML 导出照原样输出**——原样输出才使它仍然是注释，
  CommonMark 的期望输出也正是如此。

**一个刻意的偏离**：未闭合的 `<!--` 不按规范吞掉后文，而是留作普通段落。
这是实时编辑器，`<!--` 是每条注释打到一半时必经的状态，
在光标下方把整页清空比多显示四个字符糟糕得多。

### 验证

新增 9 条（与 BUG-204 合一个文件）。两条护栏：未闭合的注释不吞后文、
代码块里的注释仍是代码。

## BUG-204：`<details>` 折叠块的收尾标签漏成一段字面文字

### 现象

README 里最常见的折叠块：

```markdown
<details>
<summary>点击展开</summary>

内容

</details>
```

`<details>`、`<summary>` 和中间的 markdown 都正常，但末尾的 `</details>`
变成了一段 `&lt;/details&gt;`——折叠块没有闭合，后面的内容全在框内。

### 根因分析

同一条 `_htmlBlockStartRe` 只认开标签。HTML 块在空行处结束
（这是刻意的，正是它让 `<details>` 里的 markdown 仍按 markdown 解析），

### 修复方案

`_htmlBlockStartRe` 与 `_htmlTagAloneRe` 都改为接受 `</`。
块收集逻辑无需改动：闭合标签行自身就含有 `closeTag`，
会被判定为「自成一块」，恰好只吃一行。

### 验证

`</a>`，也就是本次要改掉的行为。该测试的真实意图是「两个标签之间的标题和
正文不被吞掉」，所以断言改写为直接表达这一点：标题内容为 `Middle`、
唯一的段落是 `prose`、最后一个节点是 HTML 块。意图保住了，顺带把它写得更准。

### 影响（BUG-203 + BUG-204 合计）

## BUG-205：表格单元格被反复解析——导出无视设置，预览每次重建重解析

### 现象

两个看似无关、实则同源的问题。

**其一（正确性）**：打开「启用 HTML」后，
`| A | 甲<br>乙 |` 在预览里正确换行，导出到 HTML / PDF / Word 却变成字面的
`&lt;br&gt;`。单元格内换行正是 `<br>` 在 markdown 里最主要的用途。

**其二（性能）**：一张 500×5 的表格，**预览每次重建都要重新解析全部单元格，
耗时 23 ms**——超过一帧（16.7ms）的预算，而且光标移动、主题切换、搜索都会触发重建。
作为对照，整篇文档完整解析一次只要 5 ms，也就是说这份重复解析的代价是
整篇解析的 4.6 倍，每次重建付一遍。

### 根因分析

**表格单元格是唯一以「未解析的源码」形式存储的结构**。
其它块都在 `MarkdownNode` 上带着 `inlineSpans`，唯独 `TableNode` 只存 `List<String>`，
于是四个读取方各自重新解析一遍：

| 读取方 | 用的解析器 | 跟随设置？ |
|---|---|---|
| 预览 | `_inlineParser`（按设置构造） | ✅ 但每次 build 都重解析 |
| HTML 导出 | `ExportService._cellParser` | ❌ 写死默认配置 |
| PDF 导出 | 同上 | ❌ |
| Word 导出 | 同上 | ❌ |

`_cellParser` 是个 `static final MarkdownParser()`，构造时用的是默认参数，
完全无视调用方一路传进来的 `enableHtml`。

代码里那条注释本身就透露了这种脆弱：
「单元格在导出解析之前一直是原始文本，所以这里必须问导出会问的同一个解析器——
用别的方式读单元格会和最终写进文件的内容不一致」。

### 修复方案

不是把设置再多传一层，而是**消除重复解析本身**：
`TableNode` 增加 `headerSpans` 与 `rowSpans`，在解析文档时一次性算好，
四个读取方都用它。

- 新增 `cellSpans(row, column)` 与 `headerSpansAt(column)`，
  越界返回空——这个边界判断原来在四个调用点各写了一遍。
- 源码字符串保留：编辑表格（增删行列、改对齐）操作的是它。
- `ExportService._cellParser` 删除。

这样配置只在解析时读一次，读取方不可能再各说各话。

### 验证

新增 6 条。正确性：同一份表格，`enableHtml` 开时导出含 `<br>`、关时含 `&lt;br&gt;`。
性能：500×5 的表格读取全部单元格 100 遍，预算 300 ms
（真实值约 11 ms，重新解析则是 1356 ms，余量两个数量级，不受机器抖动影响）。

两半分别破坏验证：把导出改回写死配置的解析器 → 正确性那条失败；
把 `cellSpans` 改成每次重新解析 → 性能那条失败（1356 ms vs 300 ms 预算）。

### 影响

单次预览重建读取全部单元格：**23 ms → 0.11 ms**（约 209 倍）。

### 涉及文件

- `code/lib/services/markdown_parser.dart`、`code/lib/services/export_service.dart`、
  `code/lib/ui/editor/markdown_renderer.dart`
- `code/test/services/table_cell_spans_test.dart`（新增，6 条）

## BUG-206：代码块每次预览重建都重新跑一遍语法高亮

### 现象

一篇有 20 个普通代码块（每块约 1KB）的文档，**每次预览重建要花 28 ms 在语法高亮上**，
超过一帧 16.7 ms 的预算。单个 20 000 字符（高亮的尺寸上限）的块自己就要 16 ms。

而「重建」是很频繁的事：移动光标、切换主题、在查找框里按一个键都会触发。

### 根因分析

沿用 BUG-205 的视角继续查——**还有什么是每次重建都在重算、而答案根本没变的**。

`CodeHighlighting` 没有任何缓存，`_buildHighlightedCodeSpans` 每次都重新跑一遍高亮器。
更要命的是预览的布局是 **`SingleChildScrollView` + `Column`**（不是惰性列表），
所以**整篇文档的每个块每次都会被构建**，不只是可见的那几个——
50 个代码块的文档每次重建就要 70 ms。

### 修复方案

`CodeHighlighting.highlight(code, language:)`，按「语言 + 源码」缓存高亮结果。

**有界**（这一点对「占用低」很关键）：按已缓存的源码字符数计，上限 128 KB，
超出就从最久未使用的开始淘汰（Dart 的 Map 保持插入序，命中时重新插入即置于末尾，
所以队首恰好是最久未用的）。反复被问到的就是屏幕上那些，远在预算之内。

缓存对象只读——两个调用方（预览、HTML 导出）都只遍历 `nodes`，不修改。

### 验证

新增 5 条：同一块返回同一个对象（不是新算的）、语言是键的一部分、
20 块 × 10 次重建的计时预算、缓存有界、未知语言不抛异常。

**一处需要说明的调整**：计时那条最初用的代码块只有约 120 字符，
破坏缓存后 200 次重解析仍在预算内——**这个断言区分不了两种假设，等于没测**。
把块放大到约 1 KB（README 里代码块的真实尺寸）后，破坏态 130 ms、通过态 <1 ms，
预算取 40 ms：是通过态的 40 倍、破坏态的三分之一，慢机器不会误报、退化一定会报。

### 影响

20 个代码块的文档，单次预览重建的高亮开销 **28 ms → 0.12 ms**。
连同 BUG-205 的表格（23 ms → 0.11 ms），一次重建省下约 51 ms。

### 顺带查清但不是问题的

## BUG-207：鼠标划过一个链接就重建整篇预览

### 现象

预览底部有一条小横幅，显示鼠标当前悬停的链接地址。
它是用 `setState` 驱动的，而 `setState` 会重建**整篇文档的每一个块**。

在一份 2500 段（每段一个链接）的文档上实测：
**鼠标每划过一个链接卡顿 279 ms，移开再来一次**。
横幅本身只是角落里的一个小部件。

### 定位过程

这一轮本来是要回答上一轮留下的问题：预览的 `Column`（非惰性列表）
到底值不值得改成惰性渲染。先把曲线量出来：

| 块数 | 源码 | 单次重建 |
|---|---|---|
| 150 | 3 KB | 48 ms |
| 600 | 13 KB | 84 ms |
| 2400 | 52 KB | 324 ms |
| 4800 | 107 KB | **686 ms** |

严格线性，约 **0.14 ms/块**。

**一处必须记下的测量陷阱**：第一次测出来的曲线在 600 块之后是平的，
我一度怀疑「大文档预览会截断内容」。真相是大文档的完整解析走
`Isolate.run`，而 widget test 跑在 FakeAsync 环境里，**isolate 的结果永远不会回来**，
所以测的只是安全前缀。用 `tester.runAsync` 让 isolate 真正跑完，曲线才正确，
块数也确认是 1600/1600 全部画出——**没有截断**。

再按块类型拆，定位这 0.14 ms 花在哪：

| 内容 | 每块 |
|---|---|
| 纯段落 | 45 µs |
| 仅粗体 | 43 µs |
| 仅行内代码 | 39 µs |
| **一个链接** | **114 µs** |
| 三个链接 | 187 µs |

粗体和行内代码不花钱，**代价全在链接上**。逐项排除：
去掉悬停回调 → 无变化；去掉 `TextSpan.recognizer` → 114 µs 降到 41 µs，
与纯段落持平。所以是 Flutter 要为带手势的文本片段额外算命中区域，
而链接必须能点，这部分绕不开。

但这条线索指向了真正的问题：**既然每次重建都这么贵，什么在触发重建？**
`_showLinkHint` / `_hideLinkHint` 走 `setState`——鼠标划过链接就是一次全量重建。

### 修复方案

- `_hoveredLink` 从 `setState` 驱动的字段改为 `ValueNotifier<String?>`；
  横幅用 `ValueListenableBuilder` 单独订阅，悬停只重建横幅本身。
- 顺带：`TapGestureRecognizer` 原来每次重建都新建、上一批在下次 build 开头销毁。
  改为按链接地址缓存复用，build 结束时清掉文档里已不存在的地址。
  这既省了开销，也消除了「一次点击进行中时识别器恰好被销毁」的隐患。

### 验证

新增 1 条计时测试（2500 段文档）：修复后 31 ms、改回 `setState` 267 ms，
预算取 120 ms——是通过态的 4 倍、破坏态的四分之一。
既有的 4 条链接悬停测试全部照常通过，说明横幅功能本身没受影响。

### 影响

2500 段文档，鼠标划过一个链接：**279 ms → 31 ms**（9 倍）。

### 仍然存在、需要单独处理的

单次全量重建在 4800 块时仍是 686 ms。根因是预览用
`SingleChildScrollView + Column` 一次性构建全部块，不是惰性列表。
改成惰性渲染会牵动滚动同步（`Scrollable.ensureVisible` 依赖离屏的 GlobalKey）、
以及 `SelectionArea` 的跨屏选择，属于需要单独一轮、且要仔细做回归的改动。
本条修掉的是**最频繁的那个触发源**。

## BUG-208：选中文字后粘贴带格式的内容，会残留一截原始文本

### 现象

从浏览器里复制一段带格式的内容（表格、列表），**先选中编辑器里的一段文字再粘贴**，
结果是：粘贴内容的开头残留了一截未转换的原始文本，
而转换后的 markdown 覆盖掉了选区后面本来存在的文字。

光标不选中任何东西直接粘贴则完全正常——这是它一直没被发现的原因。

### 根因分析

粘贴的处理方式是：先让框架把剪贴板的纯文本版本贴进去，
再由编辑器把它替换成从 HTML 版本转换来的 markdown。
要替换就得知道刚才贴进去的是哪一段，而这段代码是：

```dart
final lengthBefore = _controller.text.length;   // 粘贴前，选区还在
...
final inserted = text.length - lengthBefore;
```

`lengthBefore` 是**选区还在时**的长度。粘贴后：

```
新长度 = 旧长度 − 选区长度 + 粘贴长度
```

所以 `text.length - lengthBefore` 得到的是**净增量**，
比真实粘贴长度**少了整整一个选区长度**。

举例：文档 100 字，选中 5 字，粘贴 20 字 → 新长度 115，
算出 `inserted = 15`，于是把 `[5, 20)` 换成 markdown——
可粘贴内容实际占据 `[5, 25)`。结果开头 15 个字被换掉、**后 5 个残留**，
同时替换文本又**吃掉了选区之后的原有内容**。

只有选区为空时 `选区长度 = 0`，这个式子才恰好正确。

### 修复方案

抽成可直接测试的纯函数 `SourceEditor.pastedRange`，
显式把选区长度加回去：

```dart
final removed = selectionEnd - selectionStart;
final pasted  = lengthAfter - lengthBefore + removed;
```

### 验证

新增 4 条，覆盖：空选区、有选区、粘贴内容比选区短、什么也没贴进来。
改回旧算式后「有选区」与「粘贴更短」两条失败，空选区那条两边都过——
恰好说明了这个 bug 为什么能长期存在。

- `code/lib/ui/editor/source_editor.dart`
- `code/test/ui/editor/paste_link_test.dart`（新增，与 FEAT-074 合一个文件）

## BUG-209：大文档预览要十几秒才画完

### 现象

先把「支持大文件」这条承诺端到端实测了一遍：

| 文件 | 读盘+编码探测 | 解析 | 保存 |
|---|---|---|---|
| 1.7 MB | 31 ms | 1553 ms | 33 ms |
| 8.3 MB | 120 ms | 6086 ms | 110 ms |
| 33 MB | 361 ms | 23198 ms | 527 ms |

读和写都很快，解析约 1.1 MB/s，且在**另一个 isolate** 上跑、不冻结界面。
真正的问题在预览：

| 块数 | 源码 | 首帧 | 全部画完 |
|---|---|---|---|
| 600 | 12 KB | 883 ms | 2.5 s |
| 2400 | 51 KB | 112 ms | 3.5 s |
| 9600 | 216 KB | 77 ms | **18.5 s** |

首帧很快（渐进渲染起了作用），但之后每一帧都在把**已渲染的全部块重新构建一遍**。

### 根因分析

预览的块放在 `SingleChildScrollView + Column` 里，**不是惰性列表**，
所以每次 `build` 都会把每个块的 widget 重新造一遍——而渐进渲染期间，
「每次」就是连续几十帧。

**先排除了两条不该走的路**：
- 解析器本身：`parseInline` 单次 4µs、一张 2×2 表格 62µs，没有热点；
  而且记忆中记着「正则提取」和「快速路径」两条优化**此前已被证伪**，不再重试。
- 改成惰性列表：这是正解，但会牵动滚动同步
  （`Scrollable.ensureVisible` 依赖离屏的 GlobalKey）与 `SelectionArea` 的跨屏选择，
  需要单独一轮并仔细回归。

### 修复方案

**块的 widget 按节点身份缓存。** Flutter 在 `identical(新widget, 旧widget)` 时
`Element.update` 会直接返回，不重建子树；未被标脏的 `RenderObject` 在约束不变时
`layout()` 也会提前返回。Column、选择、滚动同步一律不动。

失效策略故意保守：**一个「渲染签名」，任何一项变化就整体丢弃缓存**——
节点列表、主题、字号、行高、代码块换行与行号、行内 HTML 开关、明暗、
是否只读、正在编辑的块、搜索状态。宁可多重建，也不能让过期的块留在屏幕上。

**搜索进行时完全不缓存**：匹配项的编号是在构建各个块的过程中累加出来的，
从缓存里拿的块不会参与计数，那之后每一处匹配的编号都会错位。

**一处必须一并处理的隐患**：上一轮把链接的手势识别器改成了跨重建复用，
清扫依据是「本次构建中每个链接都会来要一次识别器」。有了块缓存，
从缓存里出来的块**不会来要**，照旧清扫就会销毁仍在屏幕上的识别器。
所以清扫改为只在「整篇重建」的那一次进行——签名里含节点列表，
文档一变就必然整篇重建，时机正好。

### 效果

单次预览重建：

| 块数 | 之前 | 之后 |
|---|---|---|
| 600 | 84 ms | **36.5 ms** |
| 2400 | 324 ms | **105 ms** |
| 4800 | 686 ms | **237 ms** |

约 **2.5~3 倍**，每块从 0.14 ms 降到 0.05 ms。

**仍然是 O(n)**：Column 每帧仍要遍历全部子节点做差分、逐个调用布局（虽然会提前返回）、
以及绘制。要把它变成 O(可见块)，还是得改惰性列表。首次完整渲染的改善因此有限
（18.5 s → 17.3 s），本条改善的是**此后每一次重建**。

### 验证

新增 5 条针对**失效**的测试——这是本改动唯一可能出错的地方：
改文字、末尾加块、改字号、换主题、搜索高亮与编号。
把签名缩到只剩节点列表后，字号与主题两条失败，失败信息直接说「块却是从缓存里拿的旧的」。

**两处我自己的测试错误**（都不是代码问题）：
- `await settings.updateConfig(...)` 会挂死——它要写磁盘，而 `testWidgets` 的
  FakeAsync 环境里 `dart:io` 的 future 永不完成。改为不 await（状态是同步更新的）。
- 主题那条一开始传了 `'Midnight'`，而合法的主题 id 是驼峰式的 `'midnight'`，
  `getTokens` 回落到了默认值，颜色自然没变。

## BUG-210：大文档里点大纲靠后的标题，跳到别处且不会纠正

### 现象

打开一个较长的文档，**立刻**在大纲里点一个靠后的标题——
预览滚到了一个完全不相干的位置（大致是当时已渲染部分的末尾），
目标标题并不可见，而且**此后再也不会自行纠正**。

实测：400 小节的文档，只走一帧后请求滚到第 390 节，
预览停在 offset 4580 处（约第 40 节），目标标题不可见，滚动请求已被清空。

### 根因分析

三件事叠在一起：

1. **大纲列的是整篇文档的标题**（`headingOutline` 读全文），
   而预览的滚动锚点 `_headingKeys` **只包含已渲染的块**。
   长文档是一批一批画上去的，靠后的标题此刻还没有 key。
2. `_keyForLine` **有回退逻辑**：找不到精确的行就返回上方最近的标题。
   这条回退本身是对的（搜索命中落在普通行上，跳到上方标题即可），
   但它让「还没画出来」和「找到了」变得无法区分。
3. `_scrollToTargetLine` **无论成败都会 `clearScrollTarget()`**，
   所以没有任何重试的机会。

更隐蔽的一层：长文档一开始**只解析了前缀**（`safePrefix`），
所以即使把已解析的部分全画出来，目标块仍然不存在——
而回退又会给出一个「看起来有效」的 key，把请求消耗掉。

### 修复方案

- **先画到目标行再找 key**：新增 `_renderUpTo(line)`，
  把渐进渲染的前沿一次推进到覆盖该行的块，然后在下一帧重试。
  只有真正推进了才重试，因此不会无限递归。
- **前缀之外不接受回退**：若整篇解析尚未完成、且请求的行超出已解析范围，
  **不清空请求也不滚动**，直接返回等待。
- `_adoptFullParse` 在整篇解析到达后，若仍有待处理的滚动请求，
  在下一帧重新发起。

### 验证

新增 2 条：长文档（只走一帧、目标尚未绘制）与短文档（一帧内画完，原本就正常的路径）。
断言不是「在树里」——修好之后所有块都在树里，那个断言恒真——
而是**目标标题的渲染盒确实落在视口内**。

去掉这两处修改后，长文档那条失败，信息为「目标标题在视口下方，没滚到」。

### 定位过程中的一处自我纠正

第一版修复只加了「先画到目标」，测试仍然失败。
我一度以为是重试链没跑通，实际是**前缀**这一层：
`_renderUpTo` 把前缀全画完就到头了，回退随即给出一个有效 key，
滚到前缀末尾并清空了请求。**是回退掩盖了「块还不存在」这件事**，
所以第二处修改才是关键。

另外探针里 `find.text('第 390 节')` 一直返回 false，让我误以为标题没画出来——
标题是富文本，必须用 `findRichText: true`。

### 补充：分屏时的一处交互（同一未发布版本内修正）

上面的修复让预览在等待整篇解析时**保留**滚动请求。
但源码区**也**监听同一个 `targetScrollLine`，并且**它一滚完就会清空**——
所以 `_adoptFullParse` 回头去 provider 里读时已经是 null，重试落空，
分屏模式下预览根本不会跟着大纲走。

改为把待处理的行号记在渲染器自己的状态里（`_pendingScrollLine`），
不再依赖一个另一个组件会清掉的共享值。

## BUG-211：只要有一行换行，源码区的行号就与文本错位

### 现象

源码区左侧的行号从某处开始就不再对应它旁边的文本，并且越往下偏得越多。

实测（一个会换行的中文段落）：

```
文本「第三行」  y = 216.0
行号「3」      y =  62.5      →  错开 153 像素
```

**Markdown 的段落通常就是一整行长文本**，所以只要文档里有一个正常段落就会发生；
而行号槽是**无条件显示的**，没有开关可以躲开。

### 根因分析

行号槽是 `ListView.builder` + `itemExtent: 字号 × 行高`，**每个逻辑行固定一格**；
而正文的 `TextField` 是 `maxLines: null` 且宽度有界，**长行会软换行占多个视觉行**。

「一个逻辑行 = 一格固定高度」这个前提，只在没有任何一行换行时才成立。

### 修复方案

**行号的位置直接来自编辑器真实的文本布局**，不再自己推算：

- 从 `_fieldKey` 向下找到 `RenderEditable`（真正完成排版的那个渲染对象）。
- 用 `getPositionForPoint` 求出视口顶端落在第几行，再借助已有的
  `_ensureLineStarts` / `_positionOf`（行首偏移缓存 + 二分查找）定位起始行。
- 从该行向下逐行调用 `getLocalRectForCaret(行首)` 取得每行的真实纵坐标，
  一直取到视口底端为止。
- 行号槽从「滚动的等高列表」改为「按测得坐标摆放的 Stack」。

**只算可见范围**：五百万字符的文档没有理由去问布局那些没人在看的行。
`_gutterScrollController`（原来用于与正文同步滚动）随之删除——
位置既然是绝对测出来的，就不需要两个滚动视图互相追。

### 验证

新增 4 条：换行段落之后的行仍对齐、无换行文档仍对齐、滚动后仍对齐、
五千行的文档只画出屏幕上的那些行号（<120 个）。
断言用的是**文本与行号的屏幕坐标之差 ≤ 1 像素**。

把定位换回「按固定行高排布」后 3 条失败；第 4 条（只画可见行号）与位置无关，
两边都过，符合预期。

修复后三行的实测偏差均为 **0.0 像素**。

### 涉及文件

- `code/lib/ui/editor/source_editor.dart`
- `code/test/ui/editor/gutter_alignment_test.dart`（新增，4 条）
