# 性能基线（2026-09-09 实机测量）

「轻量级、秒启动、占用低、加载快、支持大文件」是这个编辑器的第一条主张。
在此之前没有可对照的数：改动是否牺牲了大文件表现，无从判断。这份文档记下
一次实机测量的结果和**复现办法**，供以后对比。

测量在真实运行的应用上通过自动化接口进行（开标签 → 读日志里的 `preview drew` 行），
不是本机跑测试。

## 一、渲染耗时

**2026-09-09 18:52 重测**，运行的构建已包含 BUG-361 的修复，所以这批数是可信的
（此前那批里 312 KB 那行报的是前缀，无法与其余行相比）。

| 文档 | 整篇块数 | 日志报出 | 绘制耗时 | 每块 |
|------|---------|---------|---------|------|
| 9 KB | 301 | 301 ✓ | 102 ms | 0.34 ms |
| 38 KB | 541 | 541 ✓ | 331 ms | 0.61 ms |
| 163 KB | 2281 | 2281 ✓ | 2337 ms | 1.02 ms |
| 516 KB | 7201 | 7201 ✓ | 3579 ms | 0.50 ms |

**两件事同时被这批数确认：**

1. **日志现在报的是整篇。** 四个规模的「报出块数」与「整篇块数」全部相等——
   BUG-361 修好了，而它此前恰恰只在大文档上说假话
2. **每块耗时不随规模增长**（0.34–1.02 ms，无单调上升）。这正是
   `cost_stays_linear_test` 在本机保证的线性，在实机上再次得到印证

以后若某次改动让「每块」这一列明显上升，就是退化。**注意看的是这一列，
不是总耗时**——总耗时本来就该随文档变长。

> 单次测量的抖动不小（同一台机器上 0.34 与 1.02 相差三倍），所以判断退化要看
> 趋势和多次测量，不要拿单个数字说话。

## 二、常驻内存

**2026-09-09 重测**（应用刚启动不久，比上一批的起点干净得多）：

| 文档 | 常驻内存 |
|------|---------|
| 9 KB | 208 MB |
| 38 KB | 176 MB |
| 163 KB | 344 MB |
| 516 KB | 774 MB |

一篇 516 KB 的文档期间到 774 MB。此前那批的起点是 1391 MB——那台实例被自动化
连续驱动了很久，**不是冷启动后的占用**；这一批更接近正常使用。

早先做过的开关实验（90 KB 文档反复开关四轮，较起点 +23 / +84 / +78 / +86 MB）
仍然成立：**头两轮涨、之后走平，没有逐轮泄漏的迹象**。

## 三、怎么复现

1. 应用运行中，通过 MCP 的 `control` 动作 `new_tab` 送入指定大小的文档
2. 等几秒，用 `read_logs` 找 `preview drew N blocks in N ms (N MB resident)`
3. 关掉标签，另开一篇小文档触发一次绘制，读它报的常驻内存

要点：**每篇文档只会留下一条 `preview drew` 行**，且必须确认读到的是这次的、
不是上一篇的——按时间戳对，不要只取末尾一条。
