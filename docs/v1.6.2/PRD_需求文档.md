## FEAT-126：单个插件窗格可以上下分割，方向由插件选

| 字段 | 内容 |

| 实现日期 | 2026-09-07 |
| 需求描述 | 标签页里只有一个插件窗格时，除了左右分割，还要能上下分割。默认左右；插件自己选；读者可以翻转。官方插件的 AI 写作与 AI 纠错用上下 |
| 用户场景 | 让模型改写一段话，改写结果与原文并排时是两条窄栏，要在两栏之间来回看才能对照。放在下面则行宽相同，眼睛往下扫就能比较——这正是 diff 工具把两版上下放的理由 |
| 实现方案 | 插件用它填的槽位表达方向：`bottom` 是上下，其它是左右（默认）。读者用窗格标题栏那个 `swap_vert` 按钮翻转，翻转后以读者的选择为准（`_paneBelow` 记住它）。三宫格早就有这个按钮，只是二宫格原先没有可翻的东西 |
| 涉及文件 | `lib/ui/widgets/plugin_panes.dart`；`test/ui/widgets/plugin_panes_layout_test.dart`；插件仓库 `plugin.lua`；`.claude/CLAUDE.md` |
| 验收标准 | 只填 `bottom` → 文档在上、窗格在下，宽度不被切；填 `right` 或 `corner` → 左右分割，高度不被切；两种形态下标题栏都有翻转按钮，按了真的换向 |

### 这条改掉了一条写着「定死，别再改」的规范

`.claude/CLAUDE.md` 原文是「**只填一个窗格时一律左右分割**——一个窗格就是一个窗格，不管它自称什么」，还有「二宫格没有第二行……所以那两种形态下不画这个按钮」。

那条理由对**哪一个**窗格成立（只填 `corner` 不该留两个空格子），对**哪个方向**不成立。人工测试指出来之后规范跟着改了，并在 CLAUDE.md 里写明了改动日期和原因——否则下一轮我会按旧规范把它改回去。

**还有一条测试的名字就是那条旧决定**：`one pane splits the width, whichever slot it claimed`。它现在叫 `one pane goes under the document when it asked for bottom`，注释里留着它原先为什么那样写。

## FEAT-127：插件可以画自己的界面（声明式组件树，第一期）

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-07 |
| 需求描述 | 插件此前只能返回字符串，编辑器把它当文本画出来。一个表单、一组选择、一个按钮都做不到。本期让插件返回一棵描述界面的树，由编辑器渲染成自己的 widget |
| 用户场景 | AI 写作需要「说明写什么」的输入框加几个常用建议；任何插件想做一个多字段的表单，此前都只能靠编辑器自带的单行提问一路问下去 |
| 实现方案 | 见下 |
| 涉及文件 | `lib/services/plugin_ui.dart`（新建）、`plugin_script_runtime.dart`、`plugin_js_runtime.dart`、`plugin_command_service.dart`、`lib/ui/widgets/plugin_ui_view.dart`（新建）、`plugin_tip.dart`、`plugin_command_actions.dart`、`lib/providers/plugin_provider.dart`；SDK 两份模块与 README |
| 验收标准 | Lua 与 JS 返回同样形状得到同样的树；按钮带回它旁边所有输入的值；换一棵树等于换一张表单；树过深、过大或含不认识的节点时整棵拒绝并报错 |

### 为什么不是 WebView

方案与取舍写在 `docs/design/plugin-drawn-ui.md`。一句话：**WebView 每个实例是一份浏览器上下文**，内存和启动时间直接撞上这个编辑器的卖点，而且 Linux 上不一定装了 `libwebkit2gtk`。组件树是编辑器自己的 widget——**启动零代价，自动跟主题，画不出容器之外**。

WebView 仍会作为逃生舱做进来（第三期），但它是可选的、懒加载的，而且网络要走宿主的本地代理以便记日志和走系统代理。

### 节点与事件

七种节点：`text` / `input` / `chips` / `button` / `row` / `column` / `spacer`。每个节点是一张只有一个键的表。

按下按钮或选中一个 chip，插件的 `on_event(ctx, id, values)` 被调用，`values` 是**这棵树里所有输入按 id 排好**的表。插件不必记住自己一步之前画了什么——那份状态编辑器本来就有，让插件再存一份，两份第一次重建就会不一致。

### 边界

| 限制 | 值 | 理由 |
|---|---|---|
| 嵌套深度 | 12 | 解析是递归的，**插件不该决定编辑器用多少栈** |
| 节点总数 | 500 | 一棵百万节点的树画不完 |
| 不认识的节点 | 拒绝整棵 | 见下 |

**拒绝整棵而不是跳过坏的那个**：半张表单比没有表单更糟——读者会把看得见的填完，然后去按一个根本没画出来的按钮。

节点的拼写没有构造器保护，也不需要：拼错会让整棵树被拒绝并抛出错误，这比一个只保证函数名对、字段名照样不检查的构造器更强。

### 变异

| 变异 | 结果 |
|---|---|
| 去掉深度限制 | 7 条挂 |
| 一个坏孩子只跳过不拒绝整棵树 | 8 条挂 |
| 按钮不带输入的值 | 点名「否则插件得自己记住一步之前画过什么」 |

有一条测试差点白写：两棵内容相同的 `const` 树会被 Dart 规范化成**同一个对象**，而视图正确地把「同一个对象」当作同一张表单——测试因此不加 `const`，理由写在注释里。

## FEAT-128：插件画的界面出现在启动它的那个容器里

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-07 |
| 需求描述 | 第一期把插件画的树统一放进悬浮卡片。但读者是从右侧边栏的抽屉点开的，答案却跑到卡片上——**他在看的是抽屉** |
| 实现方案 | `_run` 加第二个出口 `PluginUiSink`：能自己画的容器提供它，拿到树并返回读者用完之后的事件；不提供的仍然走卡片 |
| 涉及文件 | `lib/ui/widgets/plugin_command_actions.dart`、`right_side_bar.dart`；`test/ui/widgets/right_sidebar_test.dart` |
| 验收标准 | 从抽屉启动的命令，树画在抽屉里；输入的值随按钮回到插件；结果落回抽屉。从菜单或右键启动的仍画在卡片里 |

### 一条流程，两个出口

这是第一期那个 `PluginTextSink` 的同一个办法：**没有把流程复制一份到抽屉**。`_run` 现在有两个可选出口——文本一个、树一个——都不提供时一切照旧（卡片、宫格）。

抽屉关掉或切换面板时，等在树上的那次运行会被告知（`complete(null)`），和读者关掉提问卡片是同一回事。一个没人提交的表单就是一个被放弃的表单，不能让运行永远等下去。

### 端到端测试

装一个真的返回树的插件、点开抽屉、断言输入框出现在抽屉里、填字、按按钮、断言插件收到了 `id` 和输入值、结果回到抽屉。这条测试跑的是完整链路：lua 脚本 → 解析 → 渲染 → 事件 → 脚本 → 显示。

### 同一期补的三种节点

| 节点 | 为什么 |
|---|---|
| `select` | 选项多到 chips 放不下时的下拉框。**区别是地方够不够，而插件知道自己有多少地方** |
| `checkbox` | 值以 `"true"` / `"false"` 送回——插件收到的一切都是字符串，三种运行时才读得一样 |
| `markdown` | **这个最值得有**。插件要说的话通常本身就是一份文档（改写、翻译、摘要），此前只能当纯文本画出来，`##` 和 `**` 都露在外面。现在用编辑器自己的渲染器画，插件的答案看起来就像它所关于的那份文档 |

### `image`：先说不做，然后改了

第一轮我把 `image` 排除在外，理由是「网络图片会绕开权限系统」。**这个理由站不住**——用户已经决定放开插件的网络能力，前提是宿主能监听并走系统代理。那么正确的做法不是禁止，而是**让它可观测**。

`source` 三选一：

| 形式 | 从哪来 |
|---|---|
| `data:` URI | 就地解码，什么都不出这台机器 |
| 相对路径 | 插件自己的目录里；**绝对路径拒绝**——读用户磁盘上的文件是 `workspace.read` 的事，那是单独要的 |
| `http(s)` | **编辑器去取，不是插件**：跟着系统代理走，并把主机名、状态码、大小、耗时写进那个插件的日志 |

**只记主机名，不记路径**：查询串里可能带着插件送出去的东西，日志该说清「去了哪里」，而不该变成文档的第二份副本。

顺带加了 `ui.webview` 权限（WebView 本体在后面），它**隐含 `network.request`**并在权限列表里一起显示——网页视图里的页面想取什么取什么，一个只说「打开网页视图」的清单描述的是比实际授予的更小的东西，而读者是照着这份清单做决定的。

写文档时发现一个 API 用错：`UriData.fromString` 是**从内容构造** data URI，不是解析它——它老老实实返回了字符串 `"data:image/png;base64,…"` 本身的字节。测试当场抓到，换成 `UriData.parse`。

## FEAT-129：插件的网络经宿主、留日志、跟系统代理

> **先说清楚当前是什么状态。** 需求达成了，但**承载它的不是这个代理**。
>
> `PluginProxy` 是为 WebView 建的，而 WebView 本体在 `012eefd` 被 CI 退回
> （`desktop_webview_window` 要 webkit2gtk-4.0，现代发行版只有 4.1）。所以它
> **实现完整、测试齐全、production 零调用者**。
>
> 今天真正让插件流量「经宿主、留日志、跟系统代理」的是另外两处：
> `PluginImageLoader`（图片节点与 markdown 节点里的远程图片，检查
> `network.request`、只记主机名、走系统代理）和 `SystemProxyHttpOverrides`
> （进程级默认，覆盖 `Image.network` 和 `package:http` 这些够不到的调用点）。
>
> **手测时不必去找代理的行为**——没有插件能触发它。等 WebView 回来时它就位。
> 这段写在这里，是因为「写好了没接上」是本仓库出现过六次的模式，第七次至少要
> 在最显眼的地方自己说出来。

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-07 |
| 需求描述 | 允许插件自己联网（含将来的 WebView），但**主应用必须能监听它的请求，且插件的网络要走系统代理**——这样才好抓日志分析 |
| 实现方案 | 一个只监听 `127.0.0.1` 的本地代理：WebView 指向它，它再按系统代理设置转发出去。每个请求写进那个插件自己的日志 |
| 涉及文件 | `lib/services/plugin_proxy.dart`（新建，**当前无调用者**）；`test/services/plugin_proxy_test.dart`（新建）。实际承载：`lib/services/plugin_image_loader.dart`、`lib/core/net/system_proxy.dart` |
| 验收标准 | 普通 http 请求被转发且主机名进日志；CONNECT 隧道能双向搬字节且上下行字节数进日志；连不上时也留下记录；只监听回环 |

### 为什么是本地代理，而不是各平台的拦截 API

三个桌面平台的 WebView 拦截方式互不相同——WebView2 有 `WebResourceRequested`，WKWebView 要 scheme handler，WebKitGTK 发信号。**本地代理是三家都已经会说的那一种**，而且一次实现处处适用。

它同时买到两件事：系统代理（由宿主统一转发，而不是每个 WebView 自己找出路）和日志（每个请求都要从这里过）。

### 日志记得到什么，记不到什么

| 形式 | 有 | 没有 |
|---|---|---|
| `http` | 方法、主机、状态码、字节数、耗时 | — |
| `https`（CONNECT） | 主机、端口、上下行字节数、耗时 | **内容** |

看不到内容是 CONNECT 的性质：应答之后全是页面自己的 TLS。要看内容得做 MITM 自签证书，那既重又是真实的安全风险，**而「这个插件跟哪台服务器说了话」才是读者真正会问的问题**。想让宿主看全的插件可以走 `network.request`，那条路本来就是宿主代发。

**只记主机名，不记路径**——与图片加载同一条理由：查询串里可能带着插件送出去的东西。

### 三个真问题，都是测试当场抓的

**一个 Socket 只能被监听一次。** `_serve` 用 `await for` 读完请求头，`_tunnel` 再去 `client.forEach`——隧道能建立、能回「200 Connection established」，然后一个字节都不转发。改成把 `StreamSubscription` 交接下去。

**`transfer-encoding: chunked` 不能原样转发。** Dart 的 `HttpClient` 在交给我之前已经解码了分块，把那个头照抄出去，客户端就拿未编码的数据当分块解析——`104 is expected to be a Hex digit`。逐跳的响应头现在都跳过，用 `Connection: close` 标记结束。

**一条测不出东西的断言。** 我本来写「从 `0.0.0.0` 连不上代理端口」来证明只监听回环——但同一台机器上 `0.0.0.0` 解析到的就是回环，**这条断言两种实现都会通过**。改成让代理暴露 `address` 直接断言。今天第二次遇到这个形状（上一次是 `slot` 的默认值）。

### 还有一次被守卫拦住

`unawaited_guard_test` 要求每个 `unawaited(...)` 上方写明为什么不等——我写代理时两处都没写。那个守卫的注释写着「'发起后不等' 已经两次被证明是缺陷而不是选择」，这次是第三次有人（我）想不写理由就用它。

### 变异

| 变异 | 结果 |
|---|---|
| CONNECT 之后不转发客户端字节 | 4 条挂 |
| 不记日志 | 5 条挂 |
| 把路径也记进日志 | 5 条挂——这条专门验证「只记主机名」不是说说而已 |

| 字段 | 内容 |

## FEAT-132：让「大文件表现」可测量

| 字段 | 内容 |
|------|------|
| **实现日期** | 2026-09-08 |
| **需求描述** | 「加载快、支持大文件」是这个编辑器的第一条主张，而没有任何东西记录它是否成立 |
| **用户场景** | 有人说「大文档卡」，或者一次改动让它变慢了，双方都拿不出数字 |

### 起因：一次失败的测量

读者授权用 MCP 连他的机器，于是第一次能在真机上量大文档。
造了 11 万字符（176 KB）的文档，量「切到预览」的往返时间：

| 文档大小 | 切到预览 |
|---------|---------|
| 0 | 111 ms |
| 4 000 | 100 ms |
| 30 000 | **3 128 ms** |
| 111 300 | **266 ms** |

**11 万字符比 3 万字符快十倍。** 同一台机器，前后隔几秒。

这不是文档的代价——**预览是跨帧填充的**（首批 50 块，之后每帧翻倍），
所以从外面提问，量到的是「这个问题落在了哪一帧」。三秒和四分之一秒
都是等一个帧边界，跟文档没关系。

**从外面测不出来。** 而编辑器自己什么也不说。

### 实现方案

填充开始时起一只表，填满时记一行：

```
[DEBUG] [preview] preview drew 300 blocks in 47 ms
```

- **块数和毫秒都要**：只说耗时，两次测量之间没法比
- `debug` 级：查日志的人要得到它，读插件输出的人不被它打扰
- **一次批就画完的文档不记**——没有填充可计时，
  而每个短文档都留一行「0 ms」是噪声

### 涉及文件

`lib/ui/editor/markdown_renderer.dart`；
`test/ui/editor/preview_reports_its_cost_test.dart`（新增，3 条）

### 验收标准

- [x] 需要填充的文档留下恰好一条，含块数与毫秒
- [x] 一批画完的文档什么也不留
- [x] 只说一次，不是每帧一次
- [x] 变异「填完不报告」→ 红

### 老实说

另外两处变异**没有被守住**：不清空秒表、小文档也起表——两者删掉行为都不变，
它们是防御性的（防止秒表被下一份文档复用、少一次分配）。
留着，但不假装它们被验证过。

## FEAT-134：第三条主张也有了数字

| 字段 | 内容 |
|------|------|
| **实现日期** | 2026-09-08 |
| **需求描述** | 「占用低」是三条主张里唯一还没有任何测量的 |
| **用户场景** | 「打开那份大文档花了多少内存」——以前无从回答；两个版本之间胖没胖，也无从比较 |

### 三条主张，逐条对账

| 主张 | 测量 |
|------|------|
| 秒启动 | FEAT-133：里程碑进日志，带毫秒 |
| 加载快 / 大文件 | FEAT-132：预览画完报块数与毫秒 |
| **占用低** | **本条** |

`ProcessInfo.currentRss` 在这台机器上读得到（实测 159 MB）。
把它接在**已有的那两条日志**后面，不新增日志点、不上定时器：

```
[INFO ] [startup] home screen first build at 412 ms (159 MB resident)
[DEBUG] [preview] preview drew 1200 blocks in 47 ms (203 MB resident)
```

**为什么接在已有的行上**：一个孤零零的内存数字回答不了任何问题。
有用的是「做完这件事之后占了多少」。

### 两个判断

- **读不到就什么都不说**。`currentRss` 在没有实现的平台上返回 0 而不是抛异常，
  而日志里的「0 MB」读起来像一次测量，不像一次缺席
- **单位换算要有守卫**：一个 100 GB 的读数说明除错了，不是编辑器胖了

### 涉及文件

`lib/core/diagnostics/resident_memory.dart`（新增）；
`lib/core/diagnostics/startup_trace.dart`；`lib/ui/editor/markdown_renderer.dart`；
`test/core/diagnostics/resident_memory_test.dart`（新增）

### 写测试时踩的坑（值得记）

第一版断言写的是 `isNot(contains('0 MB resident'))`。
**"150 MB resident" 里就含有 "0 MB resident"**——单独跑那个文件时机器报了个非整数，
测试绿；跑全量时报数正好以 0 结尾，测试红。

一个只在「读数恰好整十」时才失败的断言。改成比较整串，并另外断言 `megabytes()` 不为 0。

### 这些测量本身要多贵（要求 1）

读一次 RSS 实测 **10.4 微秒**（本机 1 万次 104 ms）。

| 位置 | 每次运行调几次 | 代价 |
|------|--------------|------|
| 启动里程碑 | 2 | 21 µs / 约 400 ms 的启动 = **0.005%** |
| 预览画完 | 每份文档 1 | 10 µs |

可忽略——**但不是免费的**。放进 `build` 或按键处理里就会有感觉，
而那时「占用低」这条主张会被描述它的东西拖慢。

所以有一条守卫**数调用点，且数的是精确值（2）不是上限**：
留了余量的限制会让第一个新增者悄悄通过，而那正是最该读到这段说明的人。
第三个调用者不一定是错的——它是「先来读这段」的信号。
（两个方向都变异过：加一处、以及删到零变成死代码。）

### 老实说

「读到 0 就返回 null」那个分支**变异存活**——这台机器读得到 RSS，
造不出返回 0 的条件。理由写在测试注释里，不假装它被验证过。

## FEAT-135：`[见下文](#结论)` 点了要能跳过去

| 字段 | 内容 |
|------|------|
| **实现日期** | 2026-09-08 |
| **需求描述** | 指向本文档标题的链接，点击后滚动到那个标题 |
| **用户场景** | 长文档里写「详见[部署步骤](#部署步骤)」——这是 Markdown 的标准用法，而点了没有任何反应 |

### 之前发生了什么

`_followLink` 分三类处理：危险 scheme 拒绝、http/mailto/tel 交给系统、**其余当文件路径**。

`#结论` 落进第三类：拼成 `<文档目录>/#结论`，`File.existsSync()` 为假，
**直接 `return`**——静默，没有任何提示。

而所需的能力**早就有了**：大纲点一个标题就调 `scrollToLine`，
预览和源码窗格都会跟着滚。缺的只是从锚点到行号这一步。

### 实现

**`MarkdownParser.lineForAnchor(source, href)`** —— 建在 `headingOutline` 上，
不新写一份标题识别，所以「这个锚点跳得到」等价于「大纲里列得出」。

锚点名按 GitHub 的规则构造（小写、空格转连字符、标点丢掉），
因为那是写这种链接的人心里想的规则。**但不丢它不认识的字符**——
否则每一个中文、日文、阿拉伯文、俄文标题都将无法到达。

重名标题跳第一个。GitHub 会给后面的加 `-1`、`-2`；没有那套规则时，
**跳到第一个也好过跳不到**。

百分号编码要先解码（编辑器自动生成的锚点会编码非 ASCII），
但**解码失败要能容忍**——`Uri.decodeComponent` 对未编码的中文会抛异常，
而未编码正是人手写的形式。

### 顺带把「链接该怎么处理」提了出来

原来这个判断埋在 handler 里，测它需要：渲染好的段落、span 树、
按住的修饰键、await 的异步调用。**所以它从来没被测过**——
锚点这个分支缺失了很久，没有任何东西会发现。

现在是 `linkKindOf(href) → LinkKind`（refused / anchor / launchable / path），
widget 只做分发。四个分支一次全覆盖，其中三个此前一条测试都没有。

### 涉及文件

`lib/services/markdown_parser.dart`；`lib/ui/editor/link_target.dart`（新增）；
`lib/ui/editor/markdown_renderer.dart`；
`test/services/heading_anchor_test.dart`（新增 8 条）；
`test/ui/editor/link_target_test.dart`（新增 6 条）

### 验收标准

- [x] `#the-rules` 跳到 `## The Rules`
- [x] `#q--a` 跳到 `## Q & A`（标点丢掉，两个空格各成一个连字符）
- [x] `#中文标题` 跳得到，百分号编码的写法也跳得到
- [x] 收尾的 `##` 不算进名字
- [x] 找不到的锚点安静地什么都不做——**草稿里指向还没写的小节是正常状态**
- [x] 危险 scheme 的判断仍排在最前（`javascript:void#x` 是拒绝，不是锚点）
- [x] 变异三次：去掉 anchor 分支、把拒绝检查挪到锚点之后、锚点匹配不丢标点

### 一个被守卫拦下的错误

给 `anchorFor` 加 `@visibleForTesting` 时引入了
`package:flutter/foundation.dart`，`large_document_cost_test` 立刻红了：

**解析器必须能跨 isolate**——字数统计和大纲都在别的线程上解析，
它的 import 图里只要有一个 Flutter 包，那两条就退回主线程。
改成普通的公开方法，理由写在注释里。

## FEAT-136：`[^1]` 点了要能跳到注释

| 字段 | 内容 |
|------|------|
| **实现日期** | 2026-09-08 |
| **需求描述** | 点击脚注标记，滚动到它对应的注释 |
| **用户场景** | 读一篇带引用的文档，想看某条注释——而注释在文档末尾 |

### 它长得就像可点的

脚注标记画成**上标 + 主色**（就是链接色）。**而它只是一个 `Text`，
没有任何点击处理。** 看起来能点、点了没反应——比完全不做还差一点。

FEAT-135 是同一类：文档内跳转。所需的能力（`scrollToLine`）早就有。

### 与锚点的一处关键差别：标签不折叠

标题锚点按 GitHub 规则折叠大小写（`#The-Rules` 找得到 `## The Rules`）。
**脚注标签不能这样折叠**：

> 标签是作者自己起的标识符，`[^Method]` 和 `[^method]` 是两条不同的注释。
> 折叠它们会把读者送到**错的注释**，而不是送到没有。

送错比送不到更糟——读者不会怀疑。

### 其它判断

- **围栏里的定义不算**。讲脚注的文档里会有代码块示例，跳进示例是错的。
  实现上问的是解析结果而不是源文本，所以这一条自动成立
- **重名取第一个**（同锚点）
- **写了标记还没写注释 → 什么都不做，也不提示**。先写标记后补注释，
  正是脚注的写法
- **普通点击，不要求 Ctrl**。链接可能离开编辑器，所以要先问一句；
  这个只在读者已经在的文档里移动

### 一个测试上的陷阱

`targetScrollLine` **是一次性请求**：预览监听它，滚完就
`clearScrollTarget()`。所以测试读最终状态永远是 null——
改成**监听变化序列**，断言「请求过 7」。这也更贴切：要证明的是请求发出过。

顺带给可点区域加了 Key。标记所在的块**自己也有 onTap**（打开就地编辑），
它同样是那段文字的祖先，`find.ancestor` 会找到两个而必须靠猜。

### 涉及文件

`lib/services/markdown_parser.dart`；`lib/ui/editor/markdown_renderer.dart`；
`test/services/footnote_jump_test.dart`（新增 5 条）；
`test/ui/editor/footnote_jump_wired_test.dart`（新增 2 条）

### 验收标准

- [x] 点标记跳到定义那一行
- [x] `[^Method]` 找不到 `[^method]` 的定义（不折叠）
- [x] 围栏里的 `[^1]:` 不是定义
- [x] 没有定义的标记：不跳、不提示
- [x] 变异三次：标记不可点、标签折叠、找不到时乱跳

## FEAT-137：切换标签页回来时，回到原来读到的位置

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-137 |
| 实现日期 | 2026-09-09 |
| 优先级 | P1 |
| 难易度 | 中 |
| 状态 | 已完成 |

### 需求描述

每个窗格都以它显示的标签页为 key，切换标签会销毁编辑器、新建一个 offset 为 0 的
滚动条。在长文档里读到一半，切到另一个标签查点东西再切回来，**回到文档顶部**，

VS Code、Typora、上游 MarkText 都记住每个标签的位置。

### 这是怎么发现的

不是从功能清单上看出来的，是**扫描「声明后全库只出现一次的名字」**扫出来的，
先看到 `EditorNotifier.updateScroll` 和 `EditorState.scrollOffset` 全库只有声明。

顺藤摸下去，`TabInfo` 里是**一整套**：

| 字段 | 状态 |
|------|------|
| `scrollOffset` | 已标 `@Deprecated`，指向下面四个 |
| `sourceScrollOffset` | 死 |
| `previewScrollOffset` | 死 |
| `splitScrollOffset` | 死 |
| `splitSourceScrollOffset` | 死 |

五个字段、构造参数、`copyWith` 管线一应俱全，还完成了一次「从单字段迁移到按模式
分字段」的设计演进——**没有一个被写过或被读过**。这是本库已知第五例
「写好了却没接上」，也是迄今最完整的一例。

> 顺带一条教训：第一次 `grep scrollOffset` 只找到那个被弃用的单字段，
> 因为另外四个里是大写的 `ScrollOffset`。**camelCase 的词边界会让字面量扫描
> 自信地漏掉东西**，这类扫描要不分大小写。

### 实现方案

**位置存在哪里**：`EditorNotifier` 上的两个普通 Map（源码一份、预览一份），
挨着撤销栈放。**不进 `EditorState`，也不进 `TabInfo`**：

- 写进 state 会让每个 watch 标签列表的部件在切换时重建
- 窗格是在**被拆除时**记录的，那不是通知任何人的时机——那正是 BUG-337
  （构建期间修改 provider）的形状

Map 不通知任何人，只有重建中的那个窗格会去读它。释放走 `forgetHistory`，
而它由 `_releaseTab` 对**每一条**关标签路径统一调用。

**什么时候记**：滚动时存进一个普通字段，拆除时交给 provider。
不能在 dispose 里读控制器——那时 `hasClients` 已经是 false，问它什么也答不出来
（这一点是实测出来的，第一版就栽在这里）。滚动过程零 provider 写入。

**什么时候恢复**：

| 窗格 | 时机 | 理由 |
|------|------|------|
| 源码 | 首帧之后 | 但**「跳到某一行」的待处理请求优先**——那是有人明确要求去某处，胜过上次碰巧停在哪 |
| 预览 | **整篇画完之后** | 预览跨帧填充，刚建好时滚动范围只覆盖首批区块，此时恢复会被夹到那个高度，把读者丢回文档上方 |
| 分屏的预览 | **不恢复** | 那里位置归源码窗格所有，预览跟着它走；两边各自恢复会打架 |

预览那条还踩了一个坑：`_finishedFilling` 触发时所有区块**已构建但未布局**，
`maxScrollExtent` 还是上一帧的值。提前一帧放弃会停在半路（实测 8625，应为 17773）。
所以在它之后再等一帧、做最后一次尝试，然后才不再等。

### 涉及文件

- `lib/providers/editor_provider.dart`（新增两个 Map 与 `rememberScroll`/`recallScroll`；删除死掉的 `scrollOffset` 与 `updateScroll`）
- `lib/ui/editor/source_editor.dart`
- `lib/ui/editor/markdown_renderer.dart`（新增 `tabId` 参数）
- `lib/ui/screens/home_screen.dart`（把 `tabId` 交给预览窗格）
- `lib/models/tab_info.dart`（删除五个死字段与它们之间的弃用指向）
- `test/ui/editor/tab_switch_keeps_your_place_test.dart`（新增）

### 验收标准

1. 源码模式下滚到中间，切走再切回，回到原处
2. 从没滚过的标签切回来仍在顶部（记住 0 和什么都没记必须表现一致）
3. 预览模式同上，且长文档要落在真正的位置而不是首批区块的高度
4. 分屏模式下预览不自行恢复
5. **应用真的把 `tabId` 交给了两个窗格**——单独一条守卫读 `home_screen.dart` 核对，
   否则前四条都能在功能被摘掉后继续全绿

### 已知不在守卫内的一处

`_restoreScroll` 里的夹取：换成裸 `jumpTo(saved)` 后全套测试仍绿。
Flutter 会把超界的位置强制设上再用弹道模拟收回范围内，settle 之后两种写法落点相同，
差别只在中间那一帧的回弹。夹取保留（也与 `_scrollToTargetLine` 一致），
但如实记下它没有测试保护。

## FEAT-141：右侧栏是一场对话，不是一问一答

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-141 |
| 实现日期 | 2026-09-09 |
| 优先级 | P1 |
| 难易度 | 中 |
| 状态 | 已完成 |
| 提出人 | 用户（「我对某一次的结果不满意，还可以继续追加要求让其优化才对」） |

### 需求描述

面板原本是一问一答：问「要我怎么写」→ 给出结果 → 结束。
**对结果不满意，只能关掉抽屉、从头把要求再描述一遍。**

### 实现方案

抽屉里保留整场来往，底部常驻一个输入框。

**关键在于不用改插件**。插件的 `subject(ctx)` 是这样写的：

```lua
local function subject(ctx)
  local selection = ctx.selection
  if selection ~= nil and selection ~= "" then return selection, selection end
  return ctx.document or "", ""
end
```

它把「选中的文字」当作要处理的对象。所以追加一轮时，宿主把**上一次的结果
当作选区**传回去、把你的新要求当作回答——插件收到的还是它熟悉的那两样东西，
**它不需要知道这是第二轮**。`runInto` 为此加了一个 `about` 参数。

### 三处容易做错的地方

| 处 | 做法 |
|----|------|
| **「采用」替换谁** | 始终是**第一轮**记下的 `replaces`。追加一稿仍然替换它当初要替换的那段原文，而不是它自己的上一稿——那段文字根本不在文档里 |
| **前面几稿要不要留** | 留。看不到上一稿，就看不出这次要求改了什么 |
| **什么时候才有输入框** | 有了第一个答案之后。还在问第一个问题时不该出现 |

新增文案 `pluginFollowUpHint`，**12 种语言齐备**。

### 涉及文件

- `lib/ui/widgets/plugin_command_actions.dart`（`runInto` 加 `about`）
- `lib/ui/widgets/right_side_bar.dart`（会话状态、输入框、`_run` 抽出复用）
- `lib/core/i18n/l10n/app_*.arb`（12 个文件）
- `test/ui/widgets/right_sidebar_test.dart`（3 条）

### 验收标准

1. 第一次回答后，抽屉底部出现输入框
2. 输入「再简短些」并发送 → 新结果基于**上一次的结果**（测试用回显插件断言 `shorter of long of DOC`）
3. **前一稿仍在**
4. 追加之后「采用」仍然可用（说明 `replaces` 没被覆盖成不在文档里的文字）
5. 还没有答案时，不出现输入框

## FEAT-142：一个输入框，一场对话

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-142 |
| 实现日期 | 2026-09-09 |
| 优先级 | P1 |
| 难易度 | 中 |
| 状态 | 已完成 |
| 提出人 | 用户（「右侧边栏还是没有变成聊天框样式啊！」） |

### 为什么还不算聊天

FEAT-141 已经能追加要求了，但形态仍是「**表单 → 结果 → 追加框**」：

1. 点开面板，抽屉被一张**提问卡片**占满（问题 + 选项 + 它自己的输入框 + 确定/取消）
2. 回答后卡片消失，换成结果
3. 结果下面才出现追加输入框

**同一场对话，读者要在两个不同的地方打字。** 这就是「还不像聊天」。

### 实现方案

| 之前 | 现在 |
|------|------|
| 提问是一张占满抽屉的表单 | 提问是**对话里的一条消息** |
| 提问有自己的输入框和确定按钮 | 答复走**底部同一个输入框** |
| 追加框只在有结果后出现 | 同一个框，从第一次提问就在 |
| 选项是表单里的按钮 | 选项是输入框上方的**快捷标签**，点一下即发送 |
| 两个控制器 `_answer` / `_follow` | 一个 `_say` |

删除了 `_AskInDrawer`。

1. **发送按钮在等你回答时是灰的。** `busy: _running`——而命令**正等着你回答**

2. **`_send` 开头 `if (_running) return;`。** 同样的道理，回答会被直接丢掉。

两处都改成：**等读者回答不算忙**。

- `test/ui/widgets/right_sidebar_test.dart`（三条随形态更新）

2. 建议以标签形式排在输入框上方，点一下即发送
3. 回答后结果出现在问题下方，输入框仍在，可以继续说

## FEAT-143：插件可以用 HTML 画自己的界面

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-143 |
| 实现日期 | 2026-09-10 |
| 优先级 | P1 |
| 难易度 | 困难 |
| 状态 | 已完成（待人工测试） |

### 需求描述

`ui.webview` 这个权限**早就声明了**：编辑器里有它的常量、有蕴含 `network.request`
的规则、有给读者看的描述「打开它自己的网页」，SDK 用 12 种语言列在权限表里，
还有一份 290 行、专门为它写的 `PluginProxy`（注释开头就是「为插件自己渲染的东西
提供出网通路」）。

**唯独没有任何插件能真的打开一个网页。**

### 用户场景

插件作者想做一个编辑器没有设计过的界面——一张图、一个复杂表单、一段动画。
现有的 `ui` 节点树能画文字、输入框、标签、下拉框、复选框、Markdown、图片和按钮，
再复杂就没有了。

### 实现方案

**契约**：不新增动作，而是给窗格加第四种渲染方式：

```lua
return { pane = "<h1>hello</h1>", title = "我的界面", slot = "right", as = "web" }
```

这样**整套窗格管线直接复用**——四宫格、右侧抽屉、槽位、标题、追加，全都已经按
`render` 分支。加一个枚举值，两个运行时（Lua 与 JS）自动认得它，
因为它们都是从 `PluginPaneRender.values` 里按名字找。

**引擎用系统的**，不打包浏览器：Windows 走 WebView2、macOS 走 WKWebView。
这是「轻量级、占用低」与这个功能唯一能共存的方式。**按需创建**：
不打开这类插件就不产生任何浏览器上下文，启动路径一行都不多走。

**权限**：`render == web` 的窗格另外要 `ui.webview`；同时让 `ui.webview`
蕴含 `ui.sidebar`——一个网页是以窗格的形式出现的，只申请引擎而不申请窗格，
等于拿到了读者没同意过的那块地方。

**日志**：权限承诺「编辑器记录它访问了哪里」。原以为要靠 `PluginProxy`，
**实测桌面三端都没有实现 `ProxyController`**（只有 Android 有），挂不上去。
改用引擎自己的 `onLoadResource` 回调（三端都有），把每个资源的
`scheme://host` 写进应用日志——少一跳，也不需要中间人证书。

**回退**：没有可用引擎时（如未装 WPE WebKit 的 Linux、以及所有测试环境），
显示一句点名该插件的话，而不是空白窗格——空白看起来像是插件坏了。
这句话有 12 种语言。

### 过程中的两个硬发现

**一、Linux 那份测试版会让主包编译不过。**
你选的是「系统引擎 + Linux 测试版」。`flutter_inappwebview_linux 0.1.0-beta.1`
会把 `flutter_inappwebview_platform_interface` 拉到 `1.4.0-beta.3`，
而**主包 6.1.5 与这个 beta 接口编译不过**（缺实现、签名不匹配）。

`flutter test` 直接报了出来，不需要完整构建。所以现在是：
**Windows 与 macOS 可用，Linux 走回退**。要 Linux 也能用，得等上游把
beta 接口与主包对齐——这一条我留在这里，不是忘了。

**二、依赖数守卫的边界假设被我自己撞破了。**
为了把接口钉在稳定版，我加了 `dependency_overrides:`，它落在
`dependencies:` 和 `dev_dependencies:` 之间——而
`readme_dependency_count_test` 的取法正是「从前者到后者」，
于是**覆盖项被算成了直接依赖**。

改 README 的数字治不了这个：守卫本身的边界写死了某一个小节名。
改成停在**下一个顶层小节**（不管它叫什么）之后才对上：直接依赖 26 → 27。

## FEAT-144：AI 的回答边生成边显示

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-144 |
| 实现日期 | 2026-09-10 |
| 优先级 | P1（读者提出） |
| 难易度 | 中等 |
| 状态 | 已完成（待人工测试） |

### 读者提出的

> 我发现这个功能还没有流式输出，我们调用大模型应该是流式的吧？
> AI 助手的功能应该也要实现流式输出才对！

### 用户场景

模型要跑几秒到几十秒。这几秒里，为答案打开的那个窗格**一直是空的**——
读起来像是命令什么也没做。

### 实现方案：宿主推流，插件契约不动

三种做法里选了代价最小的一种：

| 做法 | 插件要改吗 |
|------|-----------|
| **宿主直接把流写进窗格，`on_result` 仍在结束时调一次** | **不用改** |
| 加 `on_stream(ctx, chunk)` 回调 | 要改，旧插件要能不实现 |
| 把 `on_result` 改成会被多次调用 | 所有插件都得改 |

于是**12 种语言的 SDK 文档和已发布的插件一个字都不用动**，
而读者立刻看到字在长。

### 三个部分

**一、增量解析**（`AiChatService.deltaFrom`）——单独成函数，因为这是最容易错、
也最值得测的一段：两家提供方把文字放在不同的地方，而且**都不在**「完整答案」
解析器看的位置。

10 条测试覆盖：OpenAI 的 `choices[].delta.content`、
Anthropic 的 `content_block_delta`、以及**一切不是答案的东西都要返回 null 而不是抛异常**——
`[DONE]` 结束标记、心跳注释、空行、被读断的半条记录、没见过的形状。

> 在自己的结束标记上抛异常会**丢掉整个答案**。

**二、请求与读取**——`complete` 接受 `onChunk`；**有人看才请求流式**
（没有接收方的调用方不必为解析付代价）。

**三、画进窗格**——续跑那条路（`pane` 带 `nextPrompt`，正是官方插件写作走的）
把累积文本推给两条绘制路径：右侧栏的 sink，或宫格的 `panes.show`。
**只推给这一轮打开的那个窗格**——读者关掉它就是说不看了，
一片一片地把它塞回去会让关闭按钮形同虚设。

### 验证

| 变异 | 结果 |
|------|------|
| 拿掉 `onChunk` 那一段 | 红：`Found 0 widgets with text "one"`——「第一个片段到了就该画出来」 |

测试用一个 `Completer` 把模型卡在中途：先断言片段已经画出来，
再放行，最后断言**插件仍然只被调用一次、拿到的是完整答案**。

### 顺带

测试替换点（BUG-402 加的）改成 `(prompt, emit)`——**它现在也能吐片段**，
这才让「读者看得见的那一半」可测。

### 涉及文件

- `code/lib/services/ai_chat_service.dart` — `deltaFrom`、`onChunk`、`stream: true`
- `code/lib/ui/widgets/plugin_command_actions.dart` — 画进窗格
- `code/test/services/ai_stream_delta_test.dart`（新增，10 条）
- `code/test/ui/widgets/right_sidebar_test.dart` — 流式那条

### 验收标准

1. 增量解析对两家提供方都正确，非答案的行不抛异常 ✓（测试）
2. 第一个片段到达就画出来 ✓（测试）
3. 插件仍只被调用一次、拿到完整答案 ✓（测试）

## FEAT-146：`get_state` 报出常驻内存

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-146 |
| 日期 | 2026-09-11 |
| 优先级 | P2 |
| 难易度 | 低 |
| 状态 | 已完成 |

### 需求描述

这个编辑器的第一条承诺是「占用低」，而**没有任何办法在任意时刻问它占了多少**。

唯一的来源是预览写的那条日志，且**只在分批那条路上打**——
小到能一次解析完的文档根本不产生日志。结果是：
**开着大文档时读得到，关掉之后读不到**。而唯一值得问的问题恰恰是后者——
**它降回来了吗**。

### 用户场景（实机遇到的）

2026-09-11 在真实客户端上量大文件表现：一篇 148 KB 的文档
把常驻从 207 MB 推到 580 MB，绘制 4900 个块用了 2090 ms。
关掉它之后我想知道内存是否回落——**问不到**。
换小文档强制重绘也没用，因为小文档不走那条会打日志的路。

### 实现方案

`get_state` 增加 `residentMB` 字段，取自已有的 `ResidentMemory.megabytes()`。
**平台不肯说时整个字段省略**，而不是报 0——「0 MB」读起来像一次测量，
而没有测量不是一次测量。

工具说明里写明用法：**开大东西前后各问一次**。

### 涉及文件

- `code/lib/providers/mcp_provider.dart`
- `code/lib/services/mcp_tools.dart`（说明）
- `code/test/services/mcp_state_is_true_test.dart`（新增 1 条）
- `code/test/core/diagnostics/resident_memory_test.dart`（调用点计数 2 → 3）

### 这里遇到的一条守卫，值得记下

`resident_memory_test` 断言调用点**精确等于 2**（读一次内存要 10 µs，
进了每帧或每次按键的路径就会被它自己拖慢）。它的注释写着：

> 精确计数而不是留余量的上限：**有余量的上限会让第一个新调用者静默通过，
> 而那正是最该读这段注释的人。第三个调用者不一定是错的——它是一个先读这段话的理由。**

我就是那第三个。按它的要求把理由写进了那段注释里，并把计数改成 3。
**这是「守卫不只是拦，还能把人叫到该读的地方」的一个好例子。**

## FEAT-147：打开文档留下一行计时

| 字段 | 内容 |
|------|------|
| 编号 | FEAT-147 |
| 日期 | 2026-09-11 |
| 优先级 | P2 |
| 难易度 | 低 |
| 状态 | 已完成 |

### 需求描述

README 把 128 KB 称作「**还能在一秒左右打开**的最后一个尺寸」，
而**打开这件事从来没有被计过时**。

编辑器只写两处时间：启动追踪，和预览绘制。**而默认视图是源码模式**——
也就是说「打开一个大文件」这条最常走的路，一个数字都不产生。
读者说「打开好慢」，这边拿不出任何东西回应；改动让它变慢了，也不会有人知道。

### 用户场景（实机遇到的）

2026-09-11 在真实客户端上量大文件：148 KB 的文档预览绘制 2090 ms——
这个数字有。但那是**预览**，而默认是源码模式。
想知道「读盘+解码花了多久」时，发现没有任何来源。

### 实现方案

`FileService.readFileWithLineEnding` 里加一行：

```
opened notes.md — 148 KB, UTF-8, 147890 characters, read and decoded in 23 ms
```

**只覆盖这一半**（读盘、解码、换行归一），绘制那一半归预览那条日志。
**分开是有意的**——读者说「打开好慢」，第一件要知道的就是慢在哪一半。

**是日志不是断言**：墙钟上限宽到能容忍慢机器就什么也抓不到，紧了又会无故变红——
这是 `cost_stays_linear_test` 已经论证过的理由。

### 涉及文件

- `code/lib/services/file_service.dart`
- `code/test/services/opening_is_measured_test.dart`（新增 3 条）

### 验证

| 变异 | 结果 |
|------|------|
| 不再记这行 | 红 |
| 把字符数当千字节报 | 红 |

**第二个变异第一次没被杀掉**，值得记：那条测试原本只断言
「字节数和字符数在非 ASCII 下不相等」——**测的是编码 API 的性质，
不是那行日志**。改成用 GBK 造一段两数不同的文本，再核对日志里出现的是
字节那个数、且**不**是字符那个数，变异才被抓住。

> 这是记忆里那条「变异全过时先查 fixture 和层次」的又一例：
> 断言离被测对象隔了一层，就什么也没守住。
