## FEAT-126：单个插件窗格可以上下分割，方向由插件选

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-07 |
| 需求描述 | 标签页里只有一个插件窗格时，除了左右分割，还要能上下分割。默认左右；插件自己选；读者可以翻转。官方插件的 AI 写作与 AI 纠错用上下 |
| 用户场景 | 让模型改写一段话，改写结果与原文并排时是两条窄栏，要在两栏之间来回看才能对照。放在下面则行宽相同，眼睛往下扫就能比较——这正是 diff 工具把两版上下放的理由 |
| 实现方案 | 插件用它填的槽位表达方向：`bottom` 是上下，其它是左右（默认）。读者用窗格标题栏那个 `swap_vert` 按钮翻转，翻转后以读者的选择为准（`_paneBelow` 记住它）。三宫格早就有这个按钮，只是二宫格原先没有可翻的东西 |
| 涉及文件 | `lib/ui/widgets/plugin_panes.dart`；`test/ui/widgets/plugin_panes_layout_test.dart`；插件仓库 `plugin.lua`；`.claude/CLAUDE.md` |
| 验收标准 | 只填 `bottom` → 文档在上、窗格在下，宽度不被切；填 `right` 或 `corner` → 左右分割，高度不被切；两种形态下标题栏都有翻转按钮，按了真的换向 |

### 这条改掉了一条写着「定死，别再改」的规范

`.claude/CLAUDE.md` 原文是「**只填一个窗格时一律左右分割**——一个窗格就是一个窗格，不管它自称什么」，还有「二宫格没有第二行……所以那两种形态下不画这个按钮」。

那条理由对**哪一个**窗格成立（只填 `corner` 不该留两个空格子），对**哪个方向**不成立。人工测试指出来之后规范跟着改了，并在 CLAUDE.md 里写明了改动日期和原因——否则下一轮我会按旧规范把它改回去。

**还有一条测试的名字就是那条旧决定**：`one pane splits the width, whichever slot it claimed`。它现在叫 `one pane goes under the document when it asked for bottom`，注释里留着它原先为什么那样写。

## FEAT-127：插件可以画自己的界面（声明式组件树，第一期）

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-07 |
| 需求描述 | 插件此前只能返回字符串，编辑器把它当文本画出来。一个表单、一组选择、一个按钮都做不到。本期让插件返回一棵描述界面的树，由编辑器渲染成自己的 widget |
| 用户场景 | AI 写作需要「说明写什么」的输入框加几个常用建议；任何插件想做一个多字段的表单，此前都只能靠编辑器自带的单行提问一路问下去 |
| 实现方案 | 见下 |
| 涉及文件 | `lib/services/plugin_ui.dart`（新建）、`plugin_script_runtime.dart`、`plugin_js_runtime.dart`、`plugin_command_service.dart`、`lib/ui/widgets/plugin_ui_view.dart`（新建）、`plugin_tip.dart`、`plugin_command_actions.dart`、`lib/providers/plugin_provider.dart`；SDK 两份模块与 README |
| 验收标准 | Lua 与 JS 返回同样形状得到同样的树；按钮带回它旁边所有输入的值；换一棵树等于换一张表单；树过深、过大或含不认识的节点时整棵拒绝并报错 |

### 为什么不是 WebView

方案与取舍写在 `docs/design/plugin-drawn-ui.md`。一句话：**WebView 每个实例是一份浏览器上下文**，内存和启动时间直接撞上这个编辑器的卖点，而且 Linux 上不一定装了 `libwebkit2gtk`。组件树是编辑器自己的 widget——**启动零代价，自动跟主题，画不出容器之外**。

WebView 仍会作为逃生舱做进来（第三期），但它是可选的、懒加载的，而且网络要走宿主的本地代理以便记日志和走系统代理。

### 节点与事件

七种节点：`text` / `input` / `chips` / `button` / `row` / `column` / `spacer`。每个节点是一张只有一个键的表。

按下按钮或选中一个 chip，插件的 `on_event(ctx, id, values)` 被调用，`values` 是**这棵树里所有输入按 id 排好**的表。插件不必记住自己一步之前画了什么——那份状态编辑器本来就有，让插件再存一份，两份第一次重建就会不一致。

### 边界

| 限制 | 值 | 理由 |
|---|---|---|
| 嵌套深度 | 12 | 解析是递归的，**插件不该决定编辑器用多少栈** |
| 节点总数 | 500 | 一棵百万节点的树画不完 |
| 不认识的节点 | 拒绝整棵 | 见下 |

**拒绝整棵而不是跳过坏的那个**：半张表单比没有表单更糟——读者会把看得见的填完，然后去按一个根本没画出来的按钮。

节点的拼写没有构造器保护，也不需要：拼错会让整棵树被拒绝并抛出错误，这比一个只保证函数名对、字段名照样不检查的构造器更强。

### 变异

| 变异 | 结果 |
|---|---|
| 去掉深度限制 | 7 条挂 |
| 一个坏孩子只跳过不拒绝整棵树 | 8 条挂 |
| 按钮不带输入的值 | 点名「否则插件得自己记住一步之前画过什么」 |

有一条测试差点白写：两棵内容相同的 `const` 树会被 Dart 规范化成**同一个对象**，而视图正确地把「同一个对象」当作同一张表单——测试因此不加 `const`，理由写在注释里。

## FEAT-128：插件画的界面出现在启动它的那个容器里

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-07 |
| 需求描述 | 第一期把插件画的树统一放进悬浮卡片。但读者是从右侧边栏的抽屉点开的，答案却跑到卡片上——**他在看的是抽屉** |
| 实现方案 | `_run` 加第二个出口 `PluginUiSink`：能自己画的容器提供它，拿到树并返回读者用完之后的事件；不提供的仍然走卡片 |
| 涉及文件 | `lib/ui/widgets/plugin_command_actions.dart`、`right_side_bar.dart`；`test/ui/widgets/right_sidebar_test.dart` |
| 验收标准 | 从抽屉启动的命令，树画在抽屉里；输入的值随按钮回到插件；结果落回抽屉。从菜单或右键启动的仍画在卡片里 |

### 一条流程，两个出口

这是第一期那个 `PluginTextSink` 的同一个办法：**没有把流程复制一份到抽屉**。`_run` 现在有两个可选出口——文本一个、树一个——都不提供时一切照旧（卡片、宫格）。

抽屉关掉或切换面板时，等在树上的那次运行会被告知（`complete(null)`），和读者关掉提问卡片是同一回事。一个没人提交的表单就是一个被放弃的表单，不能让运行永远等下去。

### 端到端测试

装一个真的返回树的插件、点开抽屉、断言输入框出现在抽屉里、填字、按按钮、断言插件收到了 `id` 和输入值、结果回到抽屉。这条测试跑的是完整链路：lua 脚本 → 解析 → 渲染 → 事件 → 脚本 → 显示。

### 同一期补的三种节点

| 节点 | 为什么 |
|---|---|
| `select` | 选项多到 chips 放不下时的下拉框。**区别是地方够不够，而插件知道自己有多少地方** |
| `checkbox` | 值以 `"true"` / `"false"` 送回——插件收到的一切都是字符串，三种运行时才读得一样 |
| `markdown` | **这个最值得有**。插件要说的话通常本身就是一份文档（改写、翻译、摘要），此前只能当纯文本画出来，`##` 和 `**` 都露在外面。现在用编辑器自己的渲染器画，插件的答案看起来就像它所关于的那份文档 |

### `image`：先说不做，然后改了

第一轮我把 `image` 排除在外，理由是「网络图片会绕开权限系统」。**这个理由站不住**——用户已经决定放开插件的网络能力，前提是宿主能监听并走系统代理。那么正确的做法不是禁止，而是**让它可观测**。

`source` 三选一：

| 形式 | 从哪来 |
|---|---|
| `data:` URI | 就地解码，什么都不出这台机器 |
| 相对路径 | 插件自己的目录里；**绝对路径拒绝**——读用户磁盘上的文件是 `workspace.read` 的事，那是单独要的 |
| `http(s)` | **编辑器去取，不是插件**：跟着系统代理走，并把主机名、状态码、大小、耗时写进那个插件的日志 |

**只记主机名，不记路径**：查询串里可能带着插件送出去的东西，日志该说清「去了哪里」，而不该变成文档的第二份副本。

顺带加了 `ui.webview` 权限（WebView 本体在后面），它**隐含 `network.request`**并在权限列表里一起显示——网页视图里的页面想取什么取什么，一个只说「打开网页视图」的清单描述的是比实际授予的更小的东西，而读者是照着这份清单做决定的。

写文档时发现一个 API 用错：`UriData.fromString` 是**从内容构造** data URI，不是解析它——它老老实实返回了字符串 `"data:image/png;base64,…"` 本身的字节。测试当场抓到，换成 `UriData.parse`。

## FEAT-129：插件的网络经宿主、留日志、跟系统代理

> **先说清楚当前是什么状态。** 需求达成了，但**承载它的不是这个代理**。
>
> `PluginProxy` 是为 WebView 建的，而 WebView 本体在 `012eefd` 被 CI 退回
> （`desktop_webview_window` 要 webkit2gtk-4.0，现代发行版只有 4.1）。所以它
> **实现完整、测试齐全、production 零调用者**。
>
> 今天真正让插件流量「经宿主、留日志、跟系统代理」的是另外两处：
> `PluginImageLoader`（图片节点与 markdown 节点里的远程图片，检查
> `network.request`、只记主机名、走系统代理）和 `SystemProxyHttpOverrides`
> （进程级默认，覆盖 `Image.network` 和 `package:http` 这些够不到的调用点）。
>
> **手测时不必去找代理的行为**——没有插件能触发它。等 WebView 回来时它就位。
> 这段写在这里，是因为「写好了没接上」是本仓库出现过六次的模式，第七次至少要
> 在最显眼的地方自己说出来。

| 字段 | 内容 |
|------|------|
| 实现日期 | 2026-09-07 |
| 需求描述 | 允许插件自己联网（含将来的 WebView），但**主应用必须能监听它的请求，且插件的网络要走系统代理**——这样才好抓日志分析 |
| 实现方案 | 一个只监听 `127.0.0.1` 的本地代理：WebView 指向它，它再按系统代理设置转发出去。每个请求写进那个插件自己的日志 |
| 涉及文件 | `lib/services/plugin_proxy.dart`（新建，**当前无调用者**）；`test/services/plugin_proxy_test.dart`（新建）。实际承载：`lib/services/plugin_image_loader.dart`、`lib/core/net/system_proxy.dart` |
| 验收标准 | 普通 http 请求被转发且主机名进日志；CONNECT 隧道能双向搬字节且上下行字节数进日志；连不上时也留下记录；只监听回环 |

### 为什么是本地代理，而不是各平台的拦截 API

三个桌面平台的 WebView 拦截方式互不相同——WebView2 有 `WebResourceRequested`，WKWebView 要 scheme handler，WebKitGTK 发信号。**本地代理是三家都已经会说的那一种**，而且一次实现处处适用。

它同时买到两件事：系统代理（由宿主统一转发，而不是每个 WebView 自己找出路）和日志（每个请求都要从这里过）。

### 日志记得到什么，记不到什么

| 形式 | 有 | 没有 |
|---|---|---|
| `http` | 方法、主机、状态码、字节数、耗时 | — |
| `https`（CONNECT） | 主机、端口、上下行字节数、耗时 | **内容** |

看不到内容是 CONNECT 的性质：应答之后全是页面自己的 TLS。要看内容得做 MITM 自签证书，那既重又是真实的安全风险，**而「这个插件跟哪台服务器说了话」才是读者真正会问的问题**。想让宿主看全的插件可以走 `network.request`，那条路本来就是宿主代发。

**只记主机名，不记路径**——与图片加载同一条理由：查询串里可能带着插件送出去的东西。

### 三个真问题，都是测试当场抓的

**一个 Socket 只能被监听一次。** `_serve` 用 `await for` 读完请求头，`_tunnel` 再去 `client.forEach`——隧道能建立、能回「200 Connection established」，然后一个字节都不转发。改成把 `StreamSubscription` 交接下去。

**`transfer-encoding: chunked` 不能原样转发。** Dart 的 `HttpClient` 在交给我之前已经解码了分块，把那个头照抄出去，客户端就拿未编码的数据当分块解析——`104 is expected to be a Hex digit`。逐跳的响应头现在都跳过，用 `Connection: close` 标记结束。

**一条测不出东西的断言。** 我本来写「从 `0.0.0.0` 连不上代理端口」来证明只监听回环——但同一台机器上 `0.0.0.0` 解析到的就是回环，**这条断言两种实现都会通过**。改成让代理暴露 `address` 直接断言。今天第二次遇到这个形状（上一次是 `slot` 的默认值）。

### 还有一次被守卫拦住

`unawaited_guard_test` 要求每个 `unawaited(...)` 上方写明为什么不等——我写代理时两处都没写。那个守卫的注释写着「'发起后不等' 已经两次被证明是缺陷而不是选择」，这次是第三次有人（我）想不写理由就用它。

### 变异

| 变异 | 结果 |
|---|---|
| CONNECT 之后不转发客户端字节 | 4 条挂 |
| 不记日志 | 5 条挂 |
| 把路径也记进日志 | 5 条挂——这条专门验证「只记主机名」不是说说而已 |

## FEAT-130：命令面板收录全部命令

| 字段 | 内容 |
|------|------|
| **实现日期** | 2026-09-08 |
| **需求描述** | Ctrl+Shift+P 打开的命令面板应当能搜到编辑器做得到的每一件事，而不是九条 |
| **用户场景** | 想放大字号又记不住键位的人，在命令面板里搜 "zoom" 什么也搜不到，会以为编辑器没有这个功能——而菜单里明明有 |

### 现状

命令面板注册了两类命令：

- **格式动作**：52 个，从 `FormatAction.values` 逐个列出，是全的
- **窗口动作**：**手写九条**（新建、保存、三种视图模式、专注、打字机、侧边栏、标签栏）

于是 zoom、打印、导出 PDF、全屏、设置、新窗口、退出、重新加载图片、
查找上一个/下一个、关闭标签——**十六条命令在面板里搜不到**。

这是 BUG-330 那批动作的**第四份手写清单**（前三份：快捷键表、窗口处理器的
switch、各菜单项）。BUG-330 把前三份合成了一份，这一条把第四份也并进去。

### 实现方案

命令面板的窗口命令改为从 `WindowActions.all` 生成：

```dart
registry.registerAll([
  for (final action in WindowActions.all)
    if (action.name != 'commandPalette')   // 在面板里再开面板没有意义
      Command(
        id: 'window.${action.name}',
        label: actionLabel(action.name, l10n),
        description: KeybindingService().keybindings[action.name] ?? '',
        execute: () => action.run(context, ref),
      ),
]);
```

**标签没有新增 ARB 键**：设置界面早已为全部 62 个可绑定动作准备了译名
（12 种语言都有），那段 switch 原本是 `SettingsScreen` 的私有方法，
现在提为 `actionLabel(action, l10n)`，设置界面与命令面板共用。

**描述位显示该命令当前的快捷键**——这比再写 24 条描述文案更有用，

## FEAT-131：MCP 能运行插件命令

| 字段 | 内容 |
|------|------|
| **实现日期** | 2026-09-08 |
| **需求描述** | 读者要求「用 MCP 做全自动化测试，插件的内容和功能都要测到」。而 MCP 没有运行插件命令的能力 |
| **用户场景** | 一个 agent 连上编辑器，要验证 AI 翻译插件能不能跑通，除了截图什么也做不了 |

### 前情

BUG-328 把 `run_plugin_command` 从 schema 里撤下了——它被宣称了几个月，
实现从来不存在。当时写下的理由是：

> 接上它值得做，但那是一次功能改动……运行一个插件命令需要 `BuildContext`
> （窗格、卡片、提示条都从它来），得由 widget 层向这里注册一个处理器

**现在读者要求了，就按那句话接上。**

### 实现方案

| 层 | 做什么 |
|----|--------|
| `McpController` | 一个可空字段 `runPluginCommand`，由别人填 |
| `HomeScreen` | 在 build 里注册它（它有 `context` 和 `ref`）——与截图能力同一个形状 |
| `McpAction` | 加回 `runPluginCommand('run_plugin_command')`，switch 由编译器强制覆盖 |

一个 agent 拿错了命令名，最该拿到的是正确的那份名单。

`await` 命令跑完再回话：问一个问题的命令会停在那里等回答，
**这和读者面对的是同一种等待**。

## FEAT-132：让「大文件表现」可测量

| 字段 | 内容 |
|------|------|
| **实现日期** | 2026-09-08 |
| **需求描述** | 「加载快、支持大文件」是这个编辑器的第一条主张，而没有任何东西记录它是否成立 |
| **用户场景** | 有人说「大文档卡」，或者一次改动让它变慢了，双方都拿不出数字 |

### 起因：一次失败的测量

读者授权用 MCP 连他的机器，于是第一次能在真机上量大文档。
造了 11 万字符（176 KB）的文档，量「切到预览」的往返时间：

| 文档大小 | 切到预览 |
|---------|---------|
| 0 | 111 ms |
| 4 000 | 100 ms |
| 30 000 | **3 128 ms** |
| 111 300 | **266 ms** |

**11 万字符比 3 万字符快十倍。** 同一台机器，前后隔几秒。

这不是文档的代价——**预览是跨帧填充的**（首批 50 块，之后每帧翻倍），
所以从外面提问，量到的是「这个问题落在了哪一帧」。三秒和四分之一秒
都是等一个帧边界，跟文档没关系。

**从外面测不出来。** 而编辑器自己什么也不说。

### 实现方案

填充开始时起一只表，填满时记一行：

```
[DEBUG] [preview] preview drew 300 blocks in 47 ms
```

- **块数和毫秒都要**：只说耗时，两次测量之间没法比
- `debug` 级：查日志的人要得到它，读插件输出的人不被它打扰
- **一次批就画完的文档不记**——没有填充可计时，
  而每个短文档都留一行「0 ms」是噪声

### 涉及文件

`lib/ui/editor/markdown_renderer.dart`；
`test/ui/editor/preview_reports_its_cost_test.dart`（新增，3 条）

### 验收标准

- [x] 需要填充的文档留下恰好一条，含块数与毫秒
- [x] 一批画完的文档什么也不留
- [x] 只说一次，不是每帧一次
- [x] 变异「填完不报告」→ 红

### 老实说

另外两处变异**没有被守住**：不清空秒表、小文档也起表——两者删掉行为都不变，
它们是防御性的（防止秒表被下一份文档复用、少一次分配）。
留着，但不假装它们被验证过。

## FEAT-133：启动数据也要能远程问到

| 字段 | 内容 |
|------|------|
| **实现日期** | 2026-09-08 |
| **需求描述** | 「秒启动」是第一条主张，而它的数据到不了远程 |
| **用户场景** | 读者说「启动变慢了」，或者要确认一次改动有没有拖慢启动——双方都要拿得到数字 |

### 同一个缺口，第二处

FEAT-132 补的是「预览画多久」。这一条是它的兄弟：

`StartupTrace` 一直在测，40 个标记点，写去两个地方——

| 出口 | 远程能看到吗 |
|------|-------------|
| `debugPrint` | **不能**。Windows release 是 GUI 子系统程序，没有 stdout |
| `startup-trace.log` | **不能**。文件在读者机器上 |

**`read_logs` 是远程唯一的窗口**，而它对自己的介绍是
「用它了解刚发生了什么」——启动了多久正是刚发生的事之一。
实测读者机器，那里只有一行「MCP server listening」。

### 实现方案

**只有里程碑进日志**，一共 2 个（`app root built`、`home screen first build`），
各带一个毫秒数。40 个细节标记不进——**日志只留几百行，
四十条会把插件的输出挤出去**，而它们在文件里一条不少。

### 涉及文件

`lib/core/diagnostics/startup_trace.dart`；
`test/core/diagnostics/startup_reaches_the_log_test.dart`（新增，3 条）

### 验收标准

- [x] 里程碑进日志，**带毫秒数**（没有数字的里程碑回答不了「多久」）
- [x] 同一个里程碑标两次仍然只有一行
- [x] 细节标记不进日志
- [x] 三个变异一对一：不记里程碑、细节也记、重复也记
